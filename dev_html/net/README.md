# 联机测试部署说明（Windows / 腾讯云）

给 RTS 原型加上**多人同屏**能力，用于快速验证玩法。设计目标是「一个下午跑通」，
所以刻意砍掉了反作弊、断线重连、状态压缩等一切不属于「能不能连上、能不能打起来」的东西。

> **本文只讲部署与排错。**
> 架构决策、协议、踩过的坑、测试体系 → [`../docs/multiplayer.md`](../docs/multiplayer.md)
> 版本变更 → [`../docs/CHANGELOG.md`](../docs/CHANGELOG.md)

---

## 〇、最省事的走法：不上传，一台电脑当服务器

如果两台电脑在**同一个 WiFi**，根本不用碰云服务器：

```powershell
# 在其中一台上（管理员 PowerShell 放行防火墙，然后就够了）
New-NetFirewallRule -DisplayName "RTS 8080" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow -Profile Any
cd C:\path\to\dev_html
py net\serve.py --port 8080
```

查本机局域网 IP（找 `192.168.x.x` 或 `10.x.x.x`）：

```powershell
ipconfig | Select-String "IPv4"
```

然后两台电脑都打开 `http://<那个局域网IP>:8080/rts-prototype.html#net=1`
（同内网延迟几乎为零，比绕公网快得多）。**不用改安全组、不用上传任何文件。**

下面第二节起是**跨网络**的情况。

## 一、部署（照着做，约 5 分钟）

### 步骤 1：把代码放到服务器

```powershell
# 服务器上
mkdir C:\rts
cd C:\rts

# 传整个 dev_html 目录上来（scp / RDP 拖拽 / git clone 都行）
# 关键文件：net\serve.py、rts-prototype.html（单文件版，已内联全部 JS/CSS）
```

单文件版 `rts-prototype.html` 是**自包含**的（CSS/JS 全部内联），所以静态托管
一个文件就够了 —— 不需要 `js/`、不需要任何前端工具链。`net/serve.py` 会一并
把它们托管出去。

### 步骤 2：在**腾讯云控制台**放行安全组（最容易漏的一步）

> ⚠️ 这一步在 Windows 里面**完全看不到**。90% 的「连不上」死在这里。

```
腾讯云控制台 → 云服务器 → 实例 → 安全组 → 入站规则 → 添加规则：
    来源       0.0.0.0/0
    协议端口   TCP:8080
    策略       允许
```

**⚠️ 不要用 80 / 443。** 中国大陆地域的腾讯云，80/443 绑公网 IP 需要 **ICP 备案**，
没备案会被拦截。`8080` 这类非标端口**可以立刻测试，免备案**。

### 步骤 3：放行 Windows 防火墙（管理员 PowerShell）

```powershell
New-NetFirewallRule -DisplayName "RTS 8080" -Direction Inbound `
  -Protocol TCP -LocalPort 8080 -Action Allow -Profile Any
```

### 步骤 4：启动服务器

```powershell
cd C:\rts\dev_html
python net\serve.py --port 8080
```

> **如果 `python` 报错或直接没反应**：那多半是 Windows 应用商店的占位符
> （`python --version` 返回 9009 = 找不到）。改用 `py`：
> ```powershell
> py net\serve.py --port 8080
> ```
> 也可以加 `--verbose` 打印每条转发的消息，排查时很有用。

看到这段就说明起来了：

```
 静态根目录 : C:\rts\dev_html
 监听       : 0.0.0.0:8080
 健康检查   : http://<本机IP>:8080/health
 房主打开   : http://<本机IP>:8080/rts-prototype.html#net=1
```

### 步骤 5：验证链路（**不用先开游戏**）

在你自己的电脑浏览器里打开：

```
http://<服务器公网IP>:8080/health
```

应该看到 `{"ok": true, "time": ..., "rooms": 0, "peers": 0}`。

**这一步把「网络问题」和「游戏代码问题」彻底分开了** —— 先让它通，再去开游戏。

### 步骤 6：进游戏

| 谁 | 打开这个地址 |
|---|---|
| **房主**（第 1 个打开的人） | `http://<IP>:8080/rts-prototype.html#net=1` |
| **客机**（其他人） | `http://<IP>:8080/rts-prototype.html#net=1&room=default` |

- 第 1 个进房间的自动成为**房主**（阵营 `p1`），之后的是客机（`p2`、`p3`…）。
- 想开多局就换 `room` 名：`#net=1&room=abc`。
- **不带 `#net=1` 就是纯单机**，和以前完全一样。

### 步骤 7：让它别在你断开 RDP 后死掉

`python net\serve.py` 是前台进程，关掉 RDP 就没了。用计划任务让它常驻：

```powershell
schtasks /create /tn "RTS-Serve" /sc onstart /ru SYSTEM /rl HIGHEST `
  /tr "py C:\rts\dev_html\net\serve.py --port 8080"
schtasks /run /tn "RTS-Serve"
```

## 二、架构：为什么是「房主权威 + 中继」

```
       房主（第 1 个进房间的浏览器）
         │   跑完整的游戏逻辑（main.js 一行没改）
         │   ↓ 每 20Hz 广播权威快照
         │   ↑ 接收客机的操作意图
    ┌────┴───────────────────────────┐
    │  net/serve.py                  │  零第三方依赖（Python 标准库）
    │  · 静态托管                     │
    │  · WebSocket 握手 + 帧编解码     │
    │  · 内存房间表                   │
    │  · 两条转发规则：               │
    │      客机的 cmd → 只给房主       │
    │      房主的 snap → 广播给其他人   │
    └────┬───────────────────────────┘
         │   ↑↓
       客机（其他人）
            update() 被冻结 —— 不跑逻辑，只发意图、收快照、插值渲染
```

### 三个关键设计决定

**1. 为什么权威必须只有一份？**
如果每个客户端各跑一局再互相同步，那就是「两个人各玩各的」——
两边的状态会各自漂移，永远不会收敛。所以房主跑逻辑，其他人看结果。

**2. 为什么服务器不跑游戏逻辑？**
因为服务器一旦要跑逻辑，就得 `import` 游戏模块。而 `main.js` 最后两行是
`initDom(); init();` —— 模块一被 import 就需要 `document`，Node 里没有。
要么把 `main.js` 拆成 DOM 层与逻辑层（半天重构），要么把
`unit.js`+`path.js`+`building.js` 在服务端语言里重写一遍（一周，还得再踩一遍 A*、
超覆盖 DDA、拆墙选点那些坑）。

**服务器保持「哑的」→ 就不可能出「服务端规则与客户端规则不一致」这类最难查的 bug。**

**3. 客机为什么冻结 `update()` 而不是自己也算一遍？**
同样是为了只有一份权威。客机的相机、选中、HUD、绘制仍然照常跑，
所以操作手感是即时的；只有世界状态是等房主的（延迟约 50ms + 插值缓冲 100ms）。

### 同步了哪些数据

| 数据 | 字段 | 说明 |
|---|---|---|
| 单位 | `id / faction / kind / px / py / hp / moving / facing / hotkey` | 坐标保留 2 位小数 |
| 建筑 | `type / tx / ty / owner / hp` | 整表替换 |
| 区块 | `owner / progress` | 每阵营各自累计 |
| 其他 | `resources / ownedTiles / time` | |

**同步的是「结果」，不是「路径」。** 客机右键只发「哪些单位、走到哪个像素点」，
路径由房主算 —— 房主才知道最新的城墙位置，这样也天然避免了路径欺骗。

**实测单次快照约 1.6KB**（6 个单位 + 20 段墙的规模），20Hz 下单人下行约 **32KB/s**。
1~2Mbps 上行的服务器带 6 个玩家没问题，所以**不做增量同步、不做二进制压缩**。

### 满员 8 人的实测数据

`tools/net-load-test.mjs 8097 8` 的结果（1 房主 + 7 客机，快照 1.96KB/条）：

| 指标 | 实测 |
|---|---|
| 服务器转发丢失 | **0%**（每个客机收到 67/67 条快照） |
| 每客机下行 | 32.8 KB/s |
| 8 人合计下行 | 229.8 KB/s |
| 最大快照间隔 | 66 ms（理想 50 ms） |
| 连接存活 | 8/8 全部保持 |

**两个值得知道的结论：**

1. **转发层是可靠的** —— 零丢失，且 `cmd` 严格不广播（客机收件箱里只有 `snap`）。
2. **瓶颈在「房主打包快照」，不在网络** —— 测试里 Node 的 20Hz 定时器实际只跑到
   16.7Hz，因为每条快照要做约 2KB 的 JSON 序列化。换算到真实浏览器，客机会以
   66ms 而不是 50ms 收到快照；**100ms 的插值缓冲足够覆盖**，观感不受影响。
   真要提上去，优化方向是「减少序列化量」（增量同步 / 二进制），而不是换协议。

## 三、排错清单

### 连不上时按顺序查这五项

| # | 检查 | 命令 / 位置 | 通了是什么样 |
|---|---|---|---|
| 1 | 服务器进程活着吗 | 看 `serve.py` 的窗口，或 `Get-Process py` | 有进程、窗口没报错 |
| 2 | 本机能访问吗 | `Test-NetConnection 127.0.0.1 -Port 8080` | `TcpTestSucceeded : True` |
| 3 | 外网能访问吗 | 在**你自己电脑**上 `Test-NetConnection <公网IP> -Port 8080` | `TcpTestSucceeded : True` |
| 4 | 安全组 | 腾讯云控制台 → 安全组 → 入站规则 | 有 `TCP:8080` 允许 `0.0.0.0/0` |
| 5 | Windows 防火墙 | `Get-NetFirewallRule -DisplayName "RTS 8080"` | `Enabled : True` |

**判据很干脆**：第 2 项通、第 3 项不通 → **100% 是安全组或防火墙的问题，不是代码问题。**
这个判断能省你一小时。

### 页面打开了，但世界是空的 / 不动

| 现象 | 原因 | 处理 |
|---|---|---|
| 页脚日志出现「已切换为单机模式」 | 连不上 `/ws`，前端自动退回单机（**不会白屏**） | 回到上面的五项检查 |
| 日志说「等待世界同步…」但一直不动 | 房主没在跑，或者房主也掉线了 | 让房主刷新页面重进 |
| 房主掉线后客机还在动 | **这是对的** —— 服务器会把下一位提升为新房主 | 无需处理 |
| 两个人都看到自己能动，但看不到对方 | 两个人不在同一个 `room` | 检查地址里的 `room=` 是否一致 |

### 关于 `#net=1`

不带这个参数时**完全不会尝试连接**，就是纯单机。
所以「联机开关」是这个 URL 片段，不是代码开关 —— 出问题时先把 `#net=1` 去掉，
确认单机模式正常，那就能确定问题在联机层而不在游戏本身。

## 四、已知限制（有意不做，别当成 bug）

| 限制 | 说明 |
|---|---|
| **房主是一个人，不是一台服务器** | 房主卡 → 全员卡；房主关页面 → 这局结束（客机会接任，但世界状态会重新同步） |
| **没有反作弊** | 快照由房主生成，客机无法伪造（服务器会盖章 `f` 字段），但房主自己能看到全局 |
| **没有断线重连** | 掉线就退出，重新打开会作为新玩家重新同步 |
| **客机约 150ms 延迟** | 50ms 快照周期 + 100ms 插值缓冲。**没有客户端预测** —— 点下右键后单位会稍后才动 |
| **没有状态压缩** | 整包快照。玩家多了或地图大了要改成增量同步 |
| **`ws://` 不加密** | 测试用够了。上域名 + HTTPS 时必须是 `wss://`，且 `https://` 页面连 `ws://` 会被浏览器直接拦掉 |
| **单格单建筑** | 一个地块只能有一个建筑，两个玩家抢同一格会失败（原型规则） |

### 对战规则（v0.5）与它的边界

| 规则 | 默认值 | 怎么改 |
|---|---|---|
| 是否要双方准备才开战 | 开 | `CONFIG.pvp.requireReady` |
| 准备后的倒计时 | 3 秒 | `CONFIG.pvp.countdownSec`；设 0 立即开打 |
| 大本营可被摧毁（打掉 = 分胜负） | 开（仅联机） | `CONFIG.pvp.destructibleBase`；单机恒为"保底 1 血" |
| 阵亡后复活 | 8 秒 | `CONFIG.pvp.respawnSec`；设 0 则不复活 |
| 对局时长上限 | 600 秒 | `CONFIG.pvp.timeLimitSec`；0 = 不限时 |

### ★ 准备界面（v0.6）

进房间后**先停在准备界面**，双方都点「准备」（或按 `R`）后房主宣布开战、倒数 3 秒，
然后才建出世界。一局结束后同一个按钮变成「↻ 再来一局」，不用刷新页面。

它顺带从结构上消灭了一类事故：

> 房主先进房间时名单有 8 个席位、但**只有 p1 有基地**。早期实现拿"名单人数"当胜负判定的
> 分母，于是第 0 帧就算出「8 个玩家只剩 1 个活着」→ **直接判 p1 获胜**。
> 线上表现就是两个玩家一打开页面就显示"P1 赢了"。
>
> 现在**只有一个人在场时永远不会放行**，世界也不会被建出来，那段窗口从根上没有了。

`startMatch()` 还有个结构性好处：它按同一份名单、同一套确定性规则（`spawnLayoutFor`）
为**每一方**建基地与部队 —— 房主和客机各自算，结果必然一致，不依赖"谁先谁后"。

**中继新增两条规则**（`net/serve.py` 的 `route()`）：

| 消息 | 方向 | 说明 |
|---|---|---|
| `ready` | 任意客户端 → 广播给全房间 | 带上服务器盖章的 `f` 阵营；也会回到发送者本人（用于刷新界面） |
| `start` | **只认房主** → 广播给其他人 | 客机伪造的 `start` 会被丢弃 |

**已知边界（有意不做）：**

- **无限复活** → 胜负只能靠拆家。想要"杀光对方算赢"需要给单位加生命次数。
- **阵营固定是 p1/p2** → 没有队伍/结盟概念，每个阵营各自为战。
- **没有战争迷雾** → 客机能看见全场（包括对手位置）。真要做，权威侧必须按阵营裁剪快照，
  那一步会把"房主权威"推向"服务器权威"。
- **建造免费** → 双方可以无限堆墙，对战平衡要先把 `CONFIG.economy.enabled` 打开。
- **不能拆除大本营，但可以被摧毁** —— 这两条路径在 `removeBuilding(state, b, force)`
  里靠 `force` 区分；改这块代码时别把 `force` 丢了（否则会出现"基地 0 血却不消失"）。

# 真实 WebSocket 往返（含准备界面的 ready/start 转发）

py tools\smoke_test.py                      # 132 项（Python 镜像）
node tools\smoke-test.mjs                   # 143 项（真实模块）
node tools\integration-test.mjs             # 41 项（真实 main.js + DOM 桩）
py tools\lint_refs.py
py tools\check_js_syntax.py
py tools\verify_build.py
```

`net-integration-test.mjs` 覆盖的是**接线**（最容易出错的地方）：以 `#net=1` 加载真实
`main.js`，然后演一遍「房主启动 → 广播快照 → 服务器分配 p2 → 客机换阵营 → 客机右键
变 cmd → 收到快照覆盖世界 → 渲染 → 双方基地分离 → 阵亡复活 → 拆家分胜负 →
结算随快照同步 → 断线退回单机」。

它抓到过一批只有这条路径才会暴露的问题，都值得记住：

- `FACTION_ROSTER` 漏 import → **`#net=1` 页面直接崩**，联机功能根本起不来
- 快照广播写在 `updateNet()` 里，而它只被主循环调用 → `RTS.tick` 永远测不到广播
- `applyFactionLayout` 把 `state.units` 整个替换 → **房主手里只有一方的部队**，打不起来
- `removeBuilding` 的"大本营不可拆"守卫把**战斗摧毁**也挡住了 → 基地 0 血却还站着
- `init()` 先建的单机大本营没被清掉 → 两个大本营叠在同一格、归属停在 `'player'`
- 断线退回单机后阵营没切回默认 → 选不中任何单位、也建不了东西

`net-test.mjs` 里最值得看的三组断言：

- **A2「两个玩家互相索敌并真的打起来」** —— 双方将领互相锁定、6 秒内各自掉血
- **B3「防冒充」** —— 客机拿房主单位的 id 发命令时，房主找不到任何可操控单位
- **P1~P4「对战规则」** —— 基地分离且计算确定、8 秒复活在自家基地、可摧毁开关、
  以及**单机不开启对战规则**（防止对局逻辑泄漏进单机）

## 六、下一步（按性价比排序）

1. **出生点分离**：现在双方将领开局站在同一处（`GENERAL_SPAWNS`），
   是为了让「互相索敌」立刻可见。做正式地图时应分到地图两端。
2. **阵营胜负条件**：现在大本营血量保底 1 不会掉 0，所以分不出胜负（见 `building.js`）。
3. **观察者模式**：服务器已经知道谁是房主、有哪些人，加一个只收快照的 pid 即可。
4. **状态压缩**：玩家数上去之后，把快照改成「只发变化的单位」+ 坐标差分。
5. **客户端预测**：把客机的 150ms 操作延迟压下去。这是体验提升最大、也最难的一项。
