# 联机开发设计文档

> 记录 **v0.4 → v0.6** 这一轮联机开发：架构决策、协议、踩过的坑、测试与回归体系。
>
> 这份文档是联机部分的**权威说明**；`../README.md` 讲整体玩法，`../net/README.md` 讲部署与排错。
> 三者分工：**怎么玩 → README；怎么部署 → net/README；为什么这么设计 → 本文。**

---

## 一、一页结论

| 项目 | 结论 |
|---|---|
| **架构** | 房主权威 + 服务器中继 |
| **服务器** | Python 标准库，**零第三方依赖**；不 import 任何游戏模块，只转发字节 |
| **权威在哪** | 房主的浏览器。它跑完整游戏逻辑，20Hz 广播快照 |
| **客机做什么** | 冻结 `update()`，只发操作意图、收快照、插值渲染 |
| **同步内容** | 结果（单位/建筑/区块/资源/结算），**不是路径** |
| **快照体积** | 约 1.6 KB/次；20Hz 下单人下行约 32 KB/s |
| **协议** | JSON over WebSocket，手写 RFC 6455（服务器侧） |
| **新增代码** | `js/faction.js` 69 行、`js/net.js` 403 行、`net/serve.py` 约 460 行 |
| **测试** | 657 项断言 / 12 个套件（其中本轮新增 341 项） |
| **浏览器实测** | **未做** —— 本沙箱跑不了 Chromium，见第八节 |

## 二、演进：三个版本，各有各的边界

| 版本 | 加了什么 | 当时的边界 |
|---|---|---|
| **v0.4** | 阵营参数化（`p1`/`p2`）、快照同步、中继服务器 | 双方共用同一个大本营、开局贴脸；死了就没了；没有胜负 |
| **v0.5** | 双方各自基地、阵亡 8 秒复活、拆家分胜负 | 一进房间就开打 → **出现线上事故：一开局就判 P1 赢**（见 6.6） |
| **v0.6** | 准备界面（双方都准备才开战）、再来一局 | 当前版本 |

**版本演化本身就是文档的一部分**：v0.5 的那个事故不是"实现写错了"，而是**流程缺了一个阶段**。
补上准备界面之后，问题从结构上消失，而不是靠补丁压住。

## 三、架构：为什么是「房主权威 + 服务器中继」

### 3.1 被排除的三个方案

| 方案 | 权威在哪 | 为什么不用 |
|---|---|---|
| **纯中继** | 每个客户端各跑一局 | 就是"两个人各玩各的" —— 状态永远不收敛，**等于没实现联机** |
| **服务器权威** | 服务器进程 | 服务器要跑逻辑就得 `import` 游戏模块，而 `main.js` 顶层 `initDom()` 需要 `document`。要么拆 DOM/逻辑层（半天重构），要么把 `unit.js`+`path.js`+`building.js` 在服务端语言里**重写一遍**（一周，还得把 A*、超覆盖 DDA、拆墙选点那些坑再踩一遍） |
| **P2P** | 无 | 判定与同步都要自己写，工作量只多不少 |

### 3.2 选定方案

```
      房主（第 1 个进房间的浏览器）
        │  跑完整游戏逻辑（main.js 的 update 一行没改）
        │  ↓ 每 20Hz 广播权威快照 (snap)
        │  ↑ 接收客机的操作意图 (cmd)
   ┌────┴────────────────────────┐
   │  net/serve.py               │  零第三方依赖
   │  · 静态托管                  │
   │  · WebSocket 握手 + 帧编解码  │
   │  · 内存房间表                │
   │  · 只做转发，不碰游戏规则      │
   └────┬────────────────────────┘
        │  ↑↓
      客机（其他人）
        update() 冻结 —— 只发意图、收快照、插值渲染
```

### 3.3 两条关键决定

**① 服务器保持"哑的"。**
它不 import 任何游戏模块，所以不可能出现「服务端规则与客户端规则不一致」这类最难查的 bug ——
因为服务端根本没有规则。

**② 权威必须只有一份。**
客机如果也跑一遍 `update()`，两份状态会各自漂移，几秒后就出现"我看到的位置和实际不一样"。
所以客机**冻结模拟**，但相机、选中、HUD、绘制照常跑 —— 操作手感是即时的，
只有世界状态要等房主。

## 四、协议与消息

### 4.1 消息表

| 消息 | 方向 | 服务器行为 | 载荷要点 |
|---|---|---|---|
| `hello` | 客户端 → 服务器 | 分配 id / 阵营 / 是否房主，回 `welcome` | `room` |
| `welcome` | 服务器 → 客户端 | — | `id / isHost / faction / roster / peers` |
| `peer` | 服务器 → 房间 | — | `event(join\|leave) / id / peers` |
| `cmd` | 客户端 → 服务器 | **只发给房主**，并盖章 `f`、附 `from` | `kind(move\|build\|spawnEnemy) / f / ids / x / y / tx / ty` |
| `snap` | 房主 → 服务器 | **广播给其他人**（非房主发的直接丢弃） | `units / buildings / zones / res / owned / time / match` |
| `ready` | 任意 → 服务器 | **广播给全房间**（含发送者本人），并盖章 `f` | `ready` |
| `start` | **只认房主** → 服务器 | 广播给其他人（客机发的丢弃） | `countdown` |
| `error` | 服务器 → 客户端 | — | `msg` |

### 4.2 快照同步了哪些字段

| 数据 | 字段 | 备注 |
|---|---|---|
| 单位 | `id / faction / kind / px / py / hp / moving / facing / hotkey` | 坐标保留 2 位小数（`toFixed(2)`） |
| 建筑 | `type / tx / ty / owner / hp` | 整表替换，按 `(type,tx,ty,owner)` 对齐以减少闪烁 |
| 区块 | `owner / progress` | 每阵营各自累计（`progressBy`） |
| 其他 | `resources / ownedTiles / time` | |
| 结算 | `match: { over, winner, elapsed }` | 胜者由房主判定，客机只显示 |
| **不同步** | `terrain`（地形）、`camera`、`view`、`log`、`ui` | 本地的东西，同步了反而会打架 |

### 4.3 三个刻意的"不做"

| 不做 | 理由 |
|---|---|
| **不发路径，只发结果** | 客机右键只发"哪些单位、走到哪个像素点"，**路径由房主算** —— 房主才知道最新的城墙位置。顺带避免了路径欺骗 |
| **不做增量/二进制压缩** | 整包约 1.6 KB，20Hz 下单人 32 KB/s。**先跑通，卡了再优化** |
| **不做客户端预测** | 客机约 150 ms 延迟（50 ms 快照周期 + 100 ms 插值缓冲）。预测是体验提升最大也最难的一项，留到后面 |

## 五、阵营模型（`js/faction.js`）

### 5.1 取值

| 取值 | 含义 |
|---|---|
| `'p1'` … `'p8'` | 玩家席位（第 1 个进房间的是 p1，即房主） |
| `'enemy'` | NPC / 调试用测试敌人 |
| `'player'` | **单机默认阵营**，等价于 P1 —— 保留是为了让单机行为与 v0.3 逐位一致 |

### 5.2 两条方向相反的规则（别搞混）

| 函数 | 问题 | 用途 |
|---|---|---|
| `isPlayerFaction(f)` | 这个阵营是不是**玩家控制的一方**？ | 是否索敌 / 占区块 / 回血 |
| `sameSide(a, b)` | 这两者是不是**同一方**？ | 是否互相攻击、城墙是否放行 |

**城墙语义**：`blocks(faction)` 的判定基准从「是不是 `'player'`」改成「是不是**我自己人**」。
只有两个阵营时这两种写法等价（所以单机行为不变），但联机下 `p2` 的城墙对 `p1` 必须阻挡 ——
旧写法会错误地放行。

### 5.3 「主阵营」由名单顺序决定，不由"我是谁"决定

```js
const primary = roster[0];          // ★ 不是 myFaction
const layout = spawnLayoutFor(map, faction, primary);
```

**为什么**：客机的 `myFaction` 是 `p2`，但名单第一个是 `p1`。
如果拿 `myFaction` 当主阵营，客机会把 p2 摆到地图中央，而房主那边 p1 也在中央 ——
**两边算出不同的世界**，快照一同步就全乱。

## 六、踩过的坑（这一轮最主要的产出）

> 这些坑**没有一个是纯逻辑测试能抓到的** —— 它们全都出现在"真实 `main.js` 跑起来"这条路径上。
> 这也是 `net-integration-test.mjs` 与 `bundle-run-test.mjs` 存在的全部理由。

### 6.1 `FACTION_ROSTER` 漏 import → `#net=1` 页面直接崩

`main.js` 用了 `FACTION_ROSTER` 却没写进 import 列表。原生 ESM 下这是运行时 `ReferenceError`，
**任何联机页面一打开就崩**，联机功能等于不存在。

**为什么之前没发现**：所有测试都从 `net.js` 的函数或服务器协议入手，没有一条"以 `#net=1` 加载真实 main.js"。

### 6.2 快照广播从未被测到

广播写在 `updateNet()` 里，而 `updateNet()` **只被主循环 `loop()` 调用**。
`RTS.tick()` 走的是 `update()` —— 所以测试里"1 秒应广播 20 条"得到的是 **0 条**。

**修法**：新增 `RTS.frame(dt)`，跑一整个主循环帧（`update` + `updateNet`）。

### 6.3 `applyFactionLayout` 把 `state.units` 整个替换 → 房主手里只有一方的部队

房主为 p2 建基地时，`state.units = createGenerals(state, 'p2')` 把 p1 的部队**全部顶掉**。
结果是「双方基地都在，但地图上只有 p2 的兵」，**根本打不起来**。

**修法**：多阵营共存时**追加**本阵营的部队而不是整体替换；
只有"我换阵营"才走 `setLocalFaction()`（清空重建）。

### 6.4 `removeBuilding` 的"大本营不可拆"守卫把战斗摧毁也挡住了

`removeBuilding` 里有 `if (b.type === 'base' && !force) return false` ——
那是给**玩家主动拆除**（X / Delete）用的。但**战斗摧毁**走的是同一条路径，
于是出现「大本营 hp=0、胜负已判，但它还站在地图上」的坏状态。

**修法**：加 `force` 参数，战斗摧毁传 `true`；玩家拆除走默认（仍然禁止拆大本营）。

### 6.5 `init()` 先建的单机大本营没被清掉 → 两个大本营叠在同一格

`enterLobby` / `startMatch` 之前，`init()` 按单机建了一个 `owner = 'player'` 的大本营。
联机接管后它成了孤儿（不匹配任何玩家阵营），但**占着格子**，导致新大本营建不上、
`owner` 还停在 `'player'` —— 胜负判定与城墙通行规则一起错乱。

**修法**：清理陈旧大本营时同时处理 `owner === 'player' && faction !== 'player'` 这种孤儿。

### 6.6 ★ 线上事故：一打开页面就显示"P1 赢了"

**症状**：两个玩家打开网址，立刻看到结算横幅"P1 赢了"，无法游戏。

**根因**：胜负判定的**分母用错了**。

```
FACTION_ROSTER = ['p1'..'p8']       ← 名单有 8 个席位
但开局只有房主 p1 进了房间           ← 也就只有 p1 有基地
checkVictory 拿"名单人数"当分母       ← 于是得出"8 个玩家只剩 1 个活着" → 判 p1 获胜
```

复现（零操作探针，推 1 帧）：

```
=== 推 1 帧后 ===
  match = over:true winner:p1
  日志: '★ 对战结束：玩家1 获胜！'
```

**修法（两层）**：

1. **直接修**：分母改为**在场的阵营**（`spawnedFactions()` = 已建出基地的那些），
   并要求 `players.length >= 2` 才谈输赢。
2. **结构性修（v0.6 准备界面）**：只有一个人在场时**根本不放行**、世界也不建出来，
   那段窗口从根上没有了。

> 这个坑的教训值得单独记：**我用"名单"当"在场玩家"，是一个语义偷换。**
> 在"双方都已建好基地"的测试里完全看不出来 —— 真实场景是"房主先进、客机后进"，
> 中间只有一方在场的那段窗口才是关键，而我的测试全都跳过了它。

### 6.7 复活功能泄漏进单机

`respawnSec` 默认 8，单机也生效了 → 单机里被打死的测试敌人 8 秒后复活，
`integration-test.mjs` 的"敌人被击杀并从单位表里移除"直接红。

**修法**：加 `state.pvpEnabled` 总开关，**只在联机时打开**；单机保持 v0.3 行为（死了就是没了）。

### 6.8 `resetMatch` 里阵营比较写反

```js
if (u.faction === 'enemy') { ...; continue; }   // 本意是"跳过敌人"，结果跳过了所有玩家单位
```

后果：重开一局后**一个单位都不剩**。

### 6.9 收到缺字段的旧快照把已结算画面打回进行中

`applySnapshot` 原本把"快照里没有 `match`"当成"未结束"。正确行为是**保持本地状态不变** ——
否则一条不含该字段的包（旧版本房主、或将来某个精简包）会把结算画面重置掉。

### 6.10 我自己在测试里犯的错（同样值得记）

| 错误 | 教训 |
|---|---|
| 断言"地图上 0 个大本营"，实际准备阶段会为自己的阵营建 1 个 | **准备阶段"世界为空"是错的期望** —— 你总得站在某处 |
| 把"准备界面"一节插在第 4 节后，它建出世界，导致后面"客机右键"那节拿到 p1 的单位 | 节与节之间的**隐式状态依赖**已经咬过我三次；现在每节自带前置 |
| 用"墙钟时间 × 20Hz"当丢包率分母，得 20.9% 假丢包 | **完全一致的丢失率不是丢包**，是基准算错。改用"实际发出条数"当分母后丢失 0% |
| 断言 `p2 的城墙让 p1 的 A* 返回 null` | 两格间距总有绕行路线；正确断言是"p1 的路径不含该格、p2 的含该格" |

### 7.2 三个"最关键"的测试（如果只能留三个）

1. **`net-integration-test.mjs` 第 11a 节** —— 模拟真实开局时序（`initNet()` 刚跑完、
   只有 p1 有基地），断言**第 0 帧不判胜负**。这就是 6.6 那个线上事故的回归。
2. **`net-integration-test.mjs` 第 12 节** —— 阵亡 → 8 秒 → 在自家大本营满血复活。
3. **`net-test.mjs` 的 B3「防冒充」** —— 客机拿房主单位的 id 发命令时，
   房主找不到任何可操控单位。

### 7.3 为什么必须有"产物级"测试

`verify_build.py` 只做**文本比对**（每个模块剥离模块语法后是否逐字出现在产物里），
它**证明不了产物能运行**。单文件版把 11 个模块按顺序拼进一个 `<script>`，于是多了一类
只存在于产物中的风险：

- 模块顺序错了 → `const` 不像函数声明那样提升，A 模块顶层引用 B 模块的 `const` 会直接
  `ReferenceError`（原生 ESM 下不会，因为 `import` 会先求值）
- 剥离 import/export 时漏了某个语法形态
- 拼接后出现重复顶层标识符

`bundle-run-test.mjs` 用 `node:vm` 在 DOM 桩里**真正执行**产物，并断言开局不自判胜负。

### 7.4 为什么单机测试要独立进程

`fallbackToSinglePlayer()` 带一个**一次性闩锁**（`usingFallback`，防止反复弹提示）。
如果单机测试和联机测试挤在同一个进程里，联机测试为自洽调过 `netGoOffline()` 会把这个闩锁提前烧掉，
于是"断线退回单机"那一段永远测不到真实行为。

**结论：不同启动配置（带/不带 `#net=1`）的测试必须分进程。**

### 8.3 一个被纠正的错误判断

第一次跑 8 人负载，7 个客机**统一丢失 20.9%**。我没有直接去优化网络，而是先质疑了这个数字 ——
完全一致的丢失率不像丢包。查下来是**基准算错**：拿"墙钟时间 × 20Hz"当分母，
把 Node `setInterval` 的抖动误判成了网络丢包。

改用"房主实际发出的条数"当分母后：**丢失 0%**。
由此得到两个真实结论（已写进 `net/README.md`）：

- **转发层可靠** —— 零丢失，`cmd` 严格不广播给客机
- **瓶颈在"房主打包快照"，不在网络** —— 20Hz 定时器实际跑到 16.7Hz，因为每条快照要序列化约 2 KB JSON。
  要提升应减少序列化量（增量/二进制），而不是换协议

## 九、排错

### 9.1 连不上：按顺序查

| # | 检查 | 命令 / 位置 | 通了是什么样 |
|---|---|---|---|
| 1 | 服务器进程活着吗 | 看 `serve.py` 窗口，或 `Get-Process py` | 有进程、窗口没报错 |
| 2 | 本机能访问吗 | `Test-NetConnection 127.0.0.1 -Port 8080` | `TcpTestSucceeded : True` |
| 3 | 外网能访问吗 | 在**自己电脑**上 `Test-NetConnection <公网IP> -Port 8080` | `TcpTestSucceeded : True` |
| 4 | 云控制台安全组 | 腾讯云 → 安全组 → 入站规则 | 有 `TCP:8080` 允许 `0.0.0.0/0` |
| 5 | Windows 防火墙 | `Get-NetFirewallRule -DisplayName "RTS 8080"` | `Enabled : True` |

**判据**：第 2 项通、第 3 项不通 → **几乎一定是安全组或防火墙，不是代码**。

### 9.2 页面打开了但不对

| 现象 | 原因 | 处理 |
|---|---|---|
| 日志出现「已切换为单机模式」 | 连不上 `/ws`，前端**自动退回单机**（不会白屏） | 回 9.1 五项检查 |
| 一直停在准备界面、等不到对手 | 两人不在**同一个 `room`** | 核对地址里的 `room=` 是否一致（默认 `default`）；只有 `#net=1` 而对方带了 `room=xxx` 就连不到一起 |
| 准备界面显示"只有你一个人" | 同上，或对手还没打开页面 | 让对方打开同一地址 |
| 客机能动但看不到对方 | 快照没到（服务器没转发 / 房主没在跑） | 看房主页面是否还开着 |
| 房主掉线后客机还在动 | **这是对的** —— 服务器会把下一位提升为新房主 | 无需处理 |

### 9.3 诊断三件套

```js
RTS.netStatus()    // { active, isHost, connected, faction, peers, snaps, error, fallback }
RTS.lobbyState()   // { active, started, roster, ready, countdown, canStart }
RTS.matchState()   // { over, winner, elapsed, logged, limitSec }
```

### 9.4 关于 `#net=1`

不带这个片段时**完全不会尝试连接**，就是纯单机。
出问题时先把 `#net=1` 去掉，确认单机正常 —— 那就能确定问题在联机层而不在游戏本身。

## 十、后续扩展点

按性价比排序：

| # | 事项 | 要点 |
|---|---|---|
| 1 | **建造消耗** | 填 `CONFIG.building.*.cost` + 打开 `CONFIG.economy.enabled`。现在建造免费，双方可无限堆墙，对战平衡无从谈起 |
| 2 | **数值平衡** | 复活 8 秒、拆家时长、基地血量（1000 / 每次 40 伤）都还没实测调过 |
| 3 | **观察者模式** | 服务器已知道谁是房主、有哪些人；加一个只收快照的 peer 即可 |
| 4 | **战争迷雾** | 客机现在能看见全场。要做的话权威侧必须**按阵营裁剪快照** —— 这一步会把"房主权威"推向"服务器权威" |
| 5 | **状态压缩** | 玩家数上去后改增量同步 + 坐标差分 |
| 6 | **客户端预测** | 压低客机 150 ms 操作延迟，体验提升最大也最难 |
| 7 | **断线重连** | 需要会话恢复 + 世界重同步 |
| 8 | **反作弊** | 目前服务器只给 `cmd` 盖章发送者阵营，房主本身能看到全局 |
