## 一、Godot 环境事实（已实测）

### 1.1 ★ 必须用 `_console.exe` 跑命令行，否则拿不到输出和退出码

```powershell
# ✅ 正确（★ 用 mono 版：工程里有 C# 群体内核，普通版加载不了，见下）
C:\D\GodotEngine\gd4.7.2mono\Godot_v4.7.2-stable_mono_win64_console.exe --headless --path <项目> --script res://tests/test_smoke.gd

# ❌ 错误：GUI 版会 detach，stdout 抓不到、$LASTEXITCODE 是空的
C:\D\GodotEngine\gd4.7.2mono\Godot_v4.7.2-stable_mono_win64.exe --headless ...
```

实测对比：

| 可执行文件 | `--version` | `--headless --script` 的输出 | 退出码 |
|---|---|---|---|
| `..._win64.exe`（GUI） | 打印但**异步**、抓不稳 | **抓不到** | 空 |
| `..._win64_console.exe` | 正常 | **完整** | **正确**（失败时 1） |

所以 `tools/run-tests.ps1` 里**写死用 `_console.exe`**。
顺便：项目 `project.godot` 声明的是 `4.7`，本机装的是 **4.7.2 stable**（`official.ed1daf0bf`）。

### 1.1b ★★ 必须用 **mono(.NET) 版**引擎，普通版跑不了 C# 内核
工程根下有 `daeem.csproj` 和 `logic/crowd/*.cs`（1000 单位群编的性能前提）。
**普通版 Godot 只加载 `project.godot`，不会加载 C# 程序集**，于是：

| | 表现 |
|---|---|
| 游戏 | 不崩：`crowd_bridge.gd` 发现自己拿不到内核 → **自动退回 `logic/collision.gd`**，只是慢约 200 倍 |
| `test_csharp_bridge.gd` | **直接红**（它有一条断言专门钉「内核可用」，就是防这种静默降级） |

- mono 版位置：`C:\D\GodotEngine\gd4.7.2mono\Godot_v4.7.2-stable_mono_win64_console.exe`
  （同一个 commit `ed1daf0bf`，只是带了 .NET）
- 改完 C# 必须重新构建，否则跑的还是旧程序集：
  `dotnet build daeem.csproj -c Debug`（产物落在 `.godot/mono/temp/bin/Debug/daeem.dll`）
- 首次构建会用到 `NuGet.config` 里那个**本机路径**的本地包源（引擎自带 `GodotSharp/Tools/nupkgs`）；
  本机没有外网到 nuget.org，所以不能删那个源
- C# 文件名必须 == 类名（PascalCase），所以 `logic/crowd/` 下的文件名与项目里
  GDScript 的 snake_case 约定不同 —— 那是引擎硬要求，不是笔误

### 1.6 ★★ 基准必须带「环境漂移」参照——沙箱持续负载后 CPU 会限频

**实测**：同一段固定计算（30 万次 `sqrt`），在一次基准运行的开头是 **4.9 ms**，
跑到末尾变成 **31.2 ms**（**x6.35**）。后果：同一个进程里**后跑**的场景，
每帧耗时会看起来「越跑越慢」—— 待命场景实测从 6 ms 一路爬到 40 ms，
看着像游戏有严重的累积性问题（查了半天对象数、内存、事件队列，全都没有增长），
实际是机器在变慢。

**怎么防**：
- `tests/bench_crowd.gd` 在开头 / 末尾各跑一次参考负载并打印倍率，超过 1.3 就告警；
- 要比大小就**一个进程只跑一个场景**：`DAEEM_ONLY=move` / `DAEEM_ONLY=idle`；
- 看到「越跑越慢」**先看漂移倍率**，别急着去优化一个不存在的问题。

### 1.7 ★ GDScript 里「无类型的参数」= 每次成员访问都是动态查找

`func f(u): return u.hp` 里的 `u.hp` 是**动态查找**（成员哈希 + 类型检查），
而 `func f(u: UnitRes)` 的成员访问由编译器静态解析。
`logic/combat.gd` 的 `update_unit` 每单位要读二十来个字段，是个典型受害者。

⚠️ 用 preload 常量当类型是允许的（项目里一直这么用）；但**两个文件不能互相 preload**
（Godot 会报 `Could not resolve script`）—— 所以需要 `UnitRes` 类型的那一边不能反过来
被 `unit.gd` preload：`tick_frame` 因此放在 `combat.gd` 里，而不是 `unit.gd`。

顺带一条同类的：**逻辑层的分段计时不要写在「每单位」的循环里**。
`_prof()` 即使关着也要付出一次方法调用；1000 单位 × 4 次就是每帧 ~0.8 ms 白交。
正确做法是整段只留一个 `if not world.profile_on: <快路径>; return`。

### 1.8 ★★★ 单帧卡顿的头号来源是「同一帧里几百个单位做同一件昂贵的事」

**症状**：1000 个单位行军攻击，实机 **avg 85 ms / p50 30 ms / p95 240 ms / max 267 ms**
（12~20 fps）。注意 `avg` 远大于 `p50` —— 这个形状本身就说明问题在**少数帧**上，
而不是「每帧都慢」。只看平均分项永远找不到它。

**根因链**（每一环都实测过，别再走一遍）：

1. **索敌是批量算的**（`crowd_bridge.refresh_targets`，为了消掉 O(n²) 的逐单位扫描），
   于是几百个单位**天然在同一帧**锁定目标 —— 这是「同步」的来源，不是巧合。
2. 刚锁定的单位走 `update_combat` → `move_to(目标位置)`。而**追击的落点就是敌人脚下那一格**，
   敌人正站在那儿 → `_arrival_congested` 必然为真 →
   每次都白跑一遍 `_find_arrival_slot`：
   `reachable_tiles()` 建全图可达掩码（C# 内核约 0.5 ms）+ 十几个候选点各扫一遍
   `world.units`（1000 个单位）= **单次约 226 µs**。
   几百个单位同帧 → **单帧 200+ ms**（实测 `mv/slot` 峰值 222 ms）。
3. 同一批 `move_to` 还都走「以目标格为终点的**距离场**」：每个不同的敌人所在格都要一张新场，
   而建场是一次**全图 Dijkstra**，LRU 只有 4 张 → 120 帧里建了 70 张，**峰值帧 21.5 ms**。

**怎么修**（三条都在，缺一条就还会卡）：

- `move_to(..., settle = false)`：追击**不需要落点空位** —— 进入攻击距离就
  `update_combat` → `halt()` 站住开火，轮不到落点判定。「挑空位」是给
  「玩家点一个点、一群人都走过去站好」服务的，所以是**分流**不是删功能。
- `unit.chase_to()`：目标够近且**直线可切**时直接走直线，不建场、不拉直、不圆角；
  直线被墙挡住就原样退回 `move_to`（安全性靠 `segment_clear`，不是靠信任）。
- `combat.needs_repath()`：**只有目标真的挪过地方才重算路径**。原来是无条件
  「每 repath_sec 秒一次」：打站着不动的目标（墙 / 建筑 / 站定的单位）时全是白费。

修完：**avg 85 → 22 ms、max 267 → 30 ms、>120 ms 的帧 35/120 → 0**，
距离场建场 70 次 → 2 次，`move_to` 46 次/帧 → 5.5 次/帧。

**量这类问题必须这么量**（这次差点被自己的量具骗过去）：

- 打印**每个分项的逐帧最大增量**，不要只打平均 —— 平均会把尖峰摊平。
  `per-frame PEAK by phase` 这一行直接指到了 `mv/slot = 222 ms`。
- 打印**帧分布直方图**：`avg ≫ p50` 时，答案全在「>120 ms 的那几帧」里。
- **离屏/未发生**的场景会骗人：无头 am 基准里敌人离得太远，180 帧只走了 3 秒，
  实测 `engaged units: 5`、`repath calls/frame: 0.4` —— 它量的是**没有交战的行军攻击**，
  所以只报 8.6 ms。**基准必须断言「要测的事情真的发生了」**（交战数 / 寻路次数）。
- 关剖析的开关必须**验证真的关掉了**：`_env_int` 里有 `maxi(1, …)`，
  所以 `DAEEM_FPS_PROFILE=0` 被抬成 1，一直没关 —— 差点据此得出错误结论。
  开关要用单独的 `_env_flag()`。
- 别急着怪环境：`ref1/ref0` 漂移参照显示 **x1.00**，那些 250 ms 的帧是真的。

### 1.2 `_initialize()` 里 `root.add_child()` 静默失效

实测：`_script`（`extends SceneTree`）的 `_initialize()` 阶段，
`root` 对象**存在且非 null**（`root:<Window#...>`），但此时 `add_child()` 挂上去的节点
`is_inside_tree()` 仍然是 **false** —— 不报错、不警告，**静默失效**。

```gdscript
func _initialize() -> void:
    var n := Node2D.new()
    root.add_child(n)
    print(n.is_inside_tree())   # ❌ false —— 没挂上，但没有任何报错
```

**正确写法**：等一帧。

```gdscript
func _initialize() -> void:
    await process_frame                       # ★ 关键
    var n := Node2D.new()
    root.add_child(n)
    print(n.is_inside_tree())   # ✅ true
```

**影响**：纯逻辑断言测试（`tests/test_*.gd`）**不受影响** —— 它们本来就不建节点。
只有在写「无头跑真实主循环」的集成测试时才会撞上。
本轮不做那类测试，但**如果哪天要做，先看这一条**。

### 1.3 无头模式确实能跑主循环

实测：`extends SceneTree` 的 `_process(delta)` 在 `--headless` 下**会被真实调用**，
可以数到 20 帧；`Camera2D` 等类也都存在（`ClassDB.class_exists("Camera2D") == true`）。
所以「不开窗口跑完整主循环」这条路是通的，M4 级集成测试将来可以做。

`FileAccess.file_exists("res://data/config.json")` + `FileAccess.get_file_as_string()` 可用。

### 1.5 沙箱里的无害噪音（别当成自己的 bug）

受限环境下跑 Godot 会稳定打出两条与本项目无关的报错：

```
ERROR: Failed to read the root certificate store.   （get_system_ca_certificates）
ERROR: Cannot save file '.../AppData/Roaming/Godot/editor_settings-4.7.tres'
```

第一条是读系统证书库，第二条是沙箱不让写 `%APPDATA%`（`user://` 也写不了，所以还会有
`Failed to open log file for writing: user://logs/godot.log`）。
**都不影响脚本执行与退出码**，本项目的测试脚本也不会因此失败。
排查问题时先把这几条过滤掉，免得被误导。

### 1.5.1 `--quit` 在 M0 阶段必然报「no main scene defined」

```
Error: Can't run project: no main scene defined in the project.   [exit code: 1]
```

这是**预期的**：M0 时项目里还没有任何场景。所以「启动整个项目」的命令在 M0 一定失败，
**M0 只能用 `--script` 跑测试脚本**（那条路径不依赖主场景）。
M1 建好主场景之后就正常了（`--headless --quit-after N` 退出码 0）。

### 1.5.2 ★ 主场景必须是一个 `.tscn`，不能直接把 `run/main_scene` 指向 `.gd`

实测（4.7.2）：

```
run/main_scene="res://view/main.gd"
→ ERROR: Failed loading scene: res://view/main.gd.   [exit code: 1]
```

`run/main_scene` 走的是「载入 `PackedScene`」这条路，**裸脚本不是场景**。
解决办法是加一个**最小**场景文件（`view/main.tscn`，正文只有 4 行：
`[gd_scene]` + 一个 `ExtResource` 指向 `view/main.gd` + 一个 Node2D 节点）。
节点树照旧全部在 `view/main.gd` 的 `_ready()` 里用代码搭，所以这个 `.tscn` 不会长大 ——
「纯文本、可 diff、HUD 也在代码里搭」这个取舍仍然成立，只是多了一个 4 行的胶水文件。

### 1.5.3 ★★ `--script` 模式下**全局 `class_name` 表不可用**（影响一切引用风格）

这是本轮花时间最多的一条，实测结论很硬：

| 写法 | `--script` 下 |
|---|---|
| 文件里写 `class_name Foo` + 类型注解 `-> Foo` | ✅ OK（自己文件内解析） |
| 同文件里 `Foo.new()` 实例化自己 | ❌ `Identifier "Foo" not declared` |
| 别的文件写 `func take(h: Foo)` | ❌ `Could not find type "Foo"` |
| `const H = preload("res://.../foo.gd")` + `h: H` | ✅ OK |
| `extends "res://tests/test_case.gd"` | ✅ OK |
| `extends TestCase`（靠 class_name） | ❌ `Could not find base class` |

原因：`--script` 启动时**没有编辑器生成的全局类缓存**
（`.godot/global_script_class_cache.cfg`），class_name 根本没有被注册。

**因此全项目的引用约定是**（改了会满屏 Parse Error）：

1. 文件内**不写 `class_name`**（写了也没用，反而容易误用）
2. 跨文件一律用**自己文件里的 preload 常量**：`const GridRes = preload("res://logic/grid.gd")`
3. 自己实例化自己用隐式 `new()`（自引用类名不安全）
4. 声明变量别用 `:=` 去接「返回 Variant 的函数」（`dict.get()` / 无类型对象的成员调用），
   用 `=` 或写显式类型 —— 否则报 `Cannot infer the type of "x"`
5. `logic/` 与 `view/` 之间也走 preload；**不要**指望 `class_name` 帮忙

### 1.5.4 ★ 一个编译不过的脚本会让 Godot CLI **卡住**

`--script` 或 `--check-only` 遇到**编译失败**时可能不打印错误就挂死（等不到退出码）。
所以：

- `tools/check-syntax.ps1` 对每个文件都带超时，超时即判失败（`[HANG]`）
- 排查语法问题**首选** `--check-only`，它比跑整个测试更早、更准地报行号：
  ```powershell
  & '<Godot>_console.exe' --headless --path <工程根> --check-only --script res://logic/grid.gd
  ```
- 一旦某个文件出现「无输出 + 超时」，先去修它的 Parse/Compile Error，别怀疑引擎

### 1.5.5 中文字体：拷进 `assets/fonts/` 之后**还需要被导入**

Godot 默认字体没有 CJK 字形（HUD 全是方框）。踩到的顺序是这样的：

1. `tools/setup-font.ps1` 把系统字体拷进 `assets/fonts/`（该目录**不进 git**）
2. 但新文件在 Godot 里**还没有 `.import` 记录** → `ResourceLoader.exists("res://assets/fonts/x.ttf") == false`
   → 首次跑游戏仍然报「没找到中文字体」
3. 两条解法（本项目两条都实现了，见 `view/font_loader.gd`）：
   - 跑一次导入：`--headless --path <工程根> --import --quit`（之后 res:// 路径可用）
   - **`FontFile.load_dynamic_font("C:/Windows/Fonts/simhei.ttf")` 绕开导入系统直接读磁盘**
     （实测 4.7.2 可行：`get_font_name() == "SimHei"`、`has_char('军') == true`）
4. 两条都失败也不能崩：退回引擎默认字体，只是中文变方框

### 1.6 项目还没加进 PATH

`godot` 不是可识别命令。要么写全路径，要么用 `$env:GODOT_EXE` 覆盖
（`tools/run-tests.ps1` 与 `tools/check-syntax.ps1` 都支持）。
**不要**为了图省事把引擎拷进工作区（会让仓库变脏）。

### 1.7 沙箱下跑带渲染的窗口也是可以的

`--quit-after N`（不带 `--headless`）在本机沙箱里能正常初始化渲染、跑满 N 帧、退出码 0。
只有 `user://` 写不了（`Can't create shader cache folder` / `Failed to open log file`），
那是环境限制，**不影响渲染与逻辑**。想确认「画面这条路没炸」时，这是最省事的办法。

## 二、Godot 特有的坑（本项目架构下最可能踩的）

### 2.0 ★★ `draw_circle` / `draw_arc` **不参与 2D 合批**——对象一多就线性堆 draw call

**实测**（1000 单位、100×100 图、1920×1080 窗口、关垂直同步）：

| 每帧的图元 | 增加的 draw call | 增加的帧时间 |
|---|---|---|
| `draw_circle` ×1000（单位本体） | **+997** | **18.4 ms** |
| `draw_arc` ×1000（描边） | **+997** | **10.2 ms** |
| `draw_line` ×1000（朝向线） | **+1** | ≈ 0 ms |
| 同一张贴图的 `draw_texture_rect` ×1000 | **合批** | ≈ 1 ms |

**根因**：`draw_circle` / `draw_arc` 每次调用都**自成一批**，Godot 的 2D 合批接不上；
而 `draw_line` / `draw_texture_rect` 能合批。

**修法**（`view/unit_view.gd`）：单位本体改成「预生成一张圆盘贴图、
把黑描边一起烘进贴图里，再 `draw_texture_rect`」。
结果：1000 单位的 draw call **3194 → 1195**，整帧 **42.7 → 14.5 ms**，
显存 **450 → 75 MB**（draw call 爆掉时显存会跟着爆）。

**推论（应当写进设计里）**：**任何「每单位 / 每对象一次」的绘制都必须用能合批的图元**
（贴图矩形、线段、多边形），否则对象数一上去就是线性堆 draw call。
写之前先用 `Performance.RENDER_TOTAL_DRAW_CALLS_IN_FRAME` 量一眼
（`tests/bench_fps.gd` 会打印它）。

### 2.0b ★ 每帧重画的「静态形状」要拆成单独节点

`zone_view` 原来在同一个 `_draw` 里既画**静态**的区块底色 + 地块边界轮廓，
又画**每帧变**的占领进度条。而形状是**按地块**画的 —— 100×100 图上就是
**每帧 1 万次 `draw_rect` + 4 万次 `zone_at`**，实测 **23 ms/帧**
（当时整帧 26 ms，而逻辑只有 0.16 ms）。

**修法**：形状挪到子节点上，只在**归属变化**时 `queue_redraw()`（用一串 owner 做签名），
进度条仍每帧重画。整帧 26.3 → 3.6 ms。

⚠️ 注意子节点的 `z_index` 是**相对父节点**的（`z_as_relative` 默认开），
所以子节点设 -1 只会落到「父节点之下一层」，不会掉到地形下面去。


### 2.1 逻辑层偷偷依赖场景树

只要 `logic/` 里出现一处 `Node` / `get_tree()` / `@onready`，
「不开窗口跑测试」和「将来复用逻辑写服务器」就同时废掉。

**怎么防**：写完一个里程碑就搜一遍 —— `logic/` 目录里不该有这些词。
`RefCounted` 不需要手动 `free()`（引用计数自动释放），这也正是选它的原因。

### 2.2 把 `TileMapLayer` 当权威地图

地形可以用 `TileMapLayer` **画**，但通行性判定必须读 `map_data`。
否则换一张图集/改一个图块属性，就会悄悄改变玩法（而且这种 bug 极难查 —— 看起来只是换了个贴图）。

### 2.3 每帧重建节点

HTML 版每帧把建筑表整表替换（那里便宜，因为是纯数据）。
Godot 里 `queue_free()` + `new()` 每帧跑会明显卡顿。
**做法**：`view/` 持有 `id → Node2D` 的映射，只在集合变化时增删。

### 2.4 命名撞车

Godot 有一批内置/常用类名。**但本项目最终一个 `class_name` 都没用** ——
原因见 1.5.3（`--script` 下全局类名表不可用）。取而代之的是每个文件顶部的
`const XxxRes = preload(...)`。类名只在注释里出现，用来指代「哪个文件」。

### 2.5 信号里改集合

`unit_died` 之类的信号回调里如果直接删 `world.units` 的元素，会一边遍历一边改集合。
**做法**：逻辑层不用信号（纯函数调用 + 返回事件数组），
`world.tick()` 先把本帧事件收集成数组，返回给 `view/` 消费。见 [`architecture.md`](architecture.md) 第三节。

### 2.6 ★ 「收尸」函数不能拒绝处理**已经死了**的对象

本轮实测踩到，而且症状很隐蔽（见 5.2）：建筑被打到 0 血时会在
`take_damage()` 里**就地**标成 `alive = false`（这样同一帧里后续的攻击者就不会重复报销），
真正的摘除留给 `world.tick()` 末尾统一做。于是「摘除」这一步收到的东西**必然是
`alive == false` 的**。第一版在 `remove_building()` 开头写了
`if not b.alive: return false`（想做成幂等），结果**没有任何建筑能被摘掉**：
被打死的城墙永远留在建筑表与格子网格里，那一格永远不可通行，敌人卡在墙前不动。

**规矩**：收尸 / 清理这类函数的判据应当是「它已经被标记为死了吗」，
而不是「它还活着吗」。幂等性应当来自「从集合里摘掉」这个操作本身，
而不是来自拒绝处理。

### 2.7 逻辑对象上的「纯表现字段」要显式声明

`view/` 会在单位上写一个 `selected` 标志（选中是纯本地状态，不进快照）。
如果 `logic/unit.gd` 里**没有** `var selected: bool`，运行时才会报：

```
SCRIPT ERROR: Invalid assignment of property or key 'selected' ... on a base object of type 'RefCounted (unit.gd)'
```

**这一条已经被 `tests/test_view.gd` 盯住**（它真的挂主场景、真的注入选中与命令）。
新加这类「逻辑对象上的表现字段」时，记得两件事：
在 `logic/` 里声明它（写上「这不是权威状态」的注释），并在 `test_view.gd` 里覆盖到。

## 三、从 HTML 版继承的坑（不要重犯）

> 下面每一条都有出处，都在 HTML 版真实发生过。**迁移时最危险的不是新坑，是把修好的旧坑重新踩一遍。**

### 3.1 ★ 坐标单位混用（最危险的一条）

**症状**：点选/射程/HUD 全部错位 —— 画面看着正常，但判定在别处。
**根因**（HTML 版）：canvas 后备缓冲按 dpr 放大，但绘制前没做 DPR 变换，
画面只画在左上角 `1/dpr` 区域，而鼠标换算是按 CSS 像素算的。
**另一次同类**：把地块坐标当像素坐标用，敌人一路走向地图左上角。

**Godot 里怎么防**：逻辑坐标一律「格」（`float`），像素只在 `view/` 出现，
换算只有一个函数（`logic × CELL_SIZE`）。**任何时候在 `logic/` 里看到 `64` 或 `* CELL`，就是错。**

### 3.2 ★ 寻路：`moveTo` 原地不动也返回 `true`

**症状**：敌人站在墙边发呆，永远不拆墙。
**根因**：调用方用「`moveTo()` 返回 true = 已经到位了」来判断，
但原地不动时它也返回 `true`。「到了就继续赶路」和「到了就找墙拆」**必须分开判断**。

### 3.3 ★ 可达性判定必须过滤「从起点真走得到」

**症状**：用城墙拦断路线后，敌人站在出生点一动不动。
**根因**：`nearestReachable()` 是「从目标往外扩圈找最近的空格」，
BFS 第一圈返回的往往是墙/山**另一侧**的格子 → 寻路必然失败 → 敌人以为哪都去不了。
**修法**：加一层 `reachable_tiles(from)` 过滤。
**同时**：「该拆哪段墙」不能只在身边 2 格内找 —— 敌人离墙 9 格时就判定「没墙可拆」。

### 3.4 A* 要处理「起点本身不可通行」

单位可能正站在**后来被建筑占住**的格子上（脚下盖了箭塔）。
所以：起点所在格不检查通行性，否则单位永远走不出来。
`segment_clear` 也是同理（起点格不检查）。

### 3.5 直线拉平的「超覆盖」判定

用普通 DDA 枚举线段经过的格子，会漏掉「只在线段上碰到一个角」的格子，
于是单位能从两座山/两段城墙的夹缝里**穿过去**。
**必须用超覆盖版**（Amanatides & Woo 的加强版）：正好穿过格点时，对角两侧都得让得开。

### 3.6 快照缺字段不能当成「默认值」

HTML 版踩过：一条不含 `match` 字段的旧快照把**已经结算的画面打回进行中**。
**正确行为**：字段缺失 = 保持本地现状不变，而不是当成 `false` / `0`。

### 3.7 阵营的两条规则方向相反，别搞混

| 函数 | 问题 | 用途 |
|---|---|---|
| `is_player_faction(f)` | 这个阵营是不是**玩家控制的一方**？ | 是否索敌 / 占区块 / 回血 |
| `same_side(a, b)` | 这两者是不是**同一方**？ | 是否互相攻击、城墙是否放行 |

城墙的判定基准必须是 `same_side(faction, owner)`（「是不是我自己人」），
**不是** `faction == 'player'`。两个阵营时两者等价（所以单机行为不变），
联机下写错会让 p2 的城墙错误地放行 p1。

> **审查中发现的现存问题**：HTML 版 `js/building.js` 的**箭塔索敌**用的是
> `u.faction === b.owner`，而警戒（`unit.js`）和城墙（`building.js` 的 `blocks`）都用 `same_side()`。
> 单人下行为等价（每个玩家是不同字符串），但这是**偏离了它自己声明的规则**，
> 一旦引入「结盟/组队」就会变成箭塔打队友。
> **Godot 版统一用 `same_side()`**，不要复制这个不一致。

### 3.8 单机与对战必须有总开关

HTML 版的复活（`respawnSec = 8`）一开始**泄漏进单机** —— 单机里被打死的测试敌人 8 秒后复活。
修法是加 `state.pvpEnabled` 总开关，只在联机时打开。

**Godot 版**：`config.json` 里也可以留着 `respawn_sec`，但必须有运行时的 `pvp_enabled` 总开关，
**而且所有「判断是否生效」的地方都要读这个开关，不能读常量**。

> **审查中发现的现存 bug**：HTML 版 `js/main.js` 的阵亡日志用常量判断
> （`CONFIG.pvp.respawnSec > 0` → 打印「8 秒后复活」），而真正的复活判定用运行时开关
> `state.pvpEnabled`。默认单机下开关是 false、单位当场被清除，
> **但日志和弹窗仍然告诉玩家「8 秒后复活」** —— 对玩家说了假话。
> **Godot 版**：日志文案与实际行为必须读同一个来源。

### 3.9 大本营「不可拆」的守卫不能挡住战斗摧毁

`remove_building(b, force)` 的 `force = false` 是给**玩家主动拆除**用的（禁止拆大本营）。
**战斗摧毁必须传 `force = true`**，否则会出现「基地被打到 0 血、胜负已判，但它还站在地图上」。

### 3.10 重建世界时的两类「孤儿」

- `init()` 先按单机建了一座 `owner = 'player'` 的大本营，联机接管后它成了孤儿 ——
  不清掉就会和新大本营**叠在同一格**，`owner` 还停在 `player`（胜负判定与城墙通行一起错乱）
- 为某个阵营重建基地时，**不能把 `units` 整个替换** —— 否则房主为 p2 建基地时会把 p1 的部队全顶掉，
  结果是「双方基地都在，但地图上只有一方的兵」

### 3.11 区块占领要「每阵营独立累计」

旧实现只有一个全局进度：两个玩家同时站在同一区块会**互相抵消**（一个加、一个减），谁也占不下来。
现在每阵营各记各的（`progress_by[阵营]`），谁先到 1 谁拿走。

> **审查中发现的现存问题**：HTML 版的**快照只发单一 `progress`**，不发 `progress_by`，
> 所以「每阵营独立累计」这个能力**在客机上根本体现不出来**（客机只能显示领先者的进度条）。
> 功能没坏，但文档的表述比实际能力大。
> **Godot 版第 1 轮**：要么把 `progress_by` 真的同步过去，要么把文档改准确。

### 3.12 其余零散修正（审查确认，迁移时顺手改掉）

| 项 | HTML 版的问题 | Godot 版怎么做 |
|---|---|---|
| 玩家席位与配色 | 阵营到 `p8`，但配色表只到 `p4`，p5~p8 全部退化成 p1 的黄色 | 配色表与席位表**同源**（由 `config.json` 一处生成），或干脆本轮只做 p1/p2 |
| 建筑对区块的归属 | 一个大本营**瞬间**把整个区块收归己有 → 出生区的「站 4 秒占领」玩法失效 | 第 0 轮先照搬（可玩性后议），但**把这个开关放进 `config.json`** 且注释写清副作用 |
| 攻击线的颜色拼接 | 用 `${前缀}${alpha})` 拼 rgba，要求每个配色项都以逗号结尾（脆弱） | 直接用 `Color` 对象 + `modulate`/`a`，不要拼字符串 |
| 死代码 | `unit.radius`（永远读不到，实际用 `radiusFactor`）、`keepDead`（从未置 true）、`lastSnapTime`（只写不读）、`RESOURCES`/`manhattan`/`claimedBy`/`progressLead`（无读者） | **不要复制**；等于白送给自己的技术债 |
| 说谎的注释 | 两处注释说插值由 `lastSnapTime` 驱动，实际用的是每单位的 `net_at` | 注释与代码不一致时，先改注释再动代码 |

## 四、写文档的坑

### 4.1 数字要对账

**三种真实发生过的数字错误**，都是"文档写得挺自信，但算错了"：

| 类型 | 实例 | 教训 |
|---|---|---|
| **条数漂移** | `docs/multiplayer.md` 一处写「657 项断言 / **12** 个套件」，另一处写 13 个 —— 同一份文件里自相矛盾 | 改测试数量时**搜一遍所有文档**，别只改你正在看的那一段 |
| **统计口径不一致** | 同一份 `main.js`，有的工具数出 1635 行、有的数出 1636 行（是否计入结尾空行） | 引用行数时**注明口径**，或只以一处表格为准（见 [`porting.md`](porting.md) 第二节的说明） |
| **拿废弃数据算** | 注释里说双方出生点「相距约 16.6 格」，但那是按一组**从未启用**的坐标（`PVP_POINTS[0]`）算的；实际 P1 用的是地图中心，真实距离是曼哈顿 10 格 | 算之前先确认**哪个数据是真正生效的** —— 死数据算出来的结论比不算更糟 |

> 第三条尤其值得记：当时它被列成了"文档 bug"，后来核对才发现**文档是对的、注释是过时的**。
> 差点把一条正确的文档"修"成错的。

**Godot 版**：测试项数、里程碑编号、地图尺寸、行数这类数字，**改代码时顺手搜一遍文档**；
不确定就直接跑一遍命令把数字测出来，别凭印象写。

### 4.2 中文 Windows 的控制台编码

HTML 版的测试 runner 因为打印 `✔`（U+2714）在 GBK 控制台直接抛
`UnicodeEncodeError` 而**整个崩掉**，等于一键测试不可用。
**Godot 版 runner**：显式设 UTF-8 输出，或干脆只用 ASCII 的 `OK` / `FAIL`。
Godot 自己打印的中文（`print`）在 `_console.exe` 下是正常的。

### 4.3 不要忘记引擎路径本身也是「环境知识」

`C:\D\GodotEngine\...` 这个路径只在本机成立。文档里写全路径没问题，
但 `tools/run-tests.ps1` 里应该允许用环境变量覆盖（`$env:GODOT_EXE`），
否则换台机器就全跑不了。

### 4.4 ★ 带 BOM 的 `.ps1` 与「脚本里不许写中文」是两件事

本项目的 runner **是纯 ASCII 的**，中文说明放在 [`../daeem/tools/README-tools.md`](../daeem/tools/README-tools.md)。
原因是实测踩到的：中文 Windows 的 **PowerShell 5.1 会把无 BOM 的 `.ps1` 当 GBK 解码**，
脚本里任何中文字面量都会变成乱码，然后**整个脚本解析失败**（`意外的标记 "}"` 之类）。

- 只加 BOM 能解决，但任何一次「编辑 → 保存」都可能把 BOM 悄悄去掉（本仓库的
  编辑工具就发生过），于是脚本又会莫名其妙地坏掉 —— 这种「时好时坏」最难查
- 所以定下来的规矩是：**`.ps1` 里只写 ASCII**，中文输出交给 Godot 脚本去 `print`
  （Godot 自己打印中文在 `_console.exe` 下是正常的），或写进 `.md`

顺带一条：`tools/run-tests.ps1` 只用 `$LASTEXITCODE` 与 `[regex]` 判定成败，
**不解析中文输出**，这样它跟引擎的语言/编码设置完全解耦。

### 4.5 ★★ 千万不要用 PowerShell 的 `Get-Content -Raw` + `Set-Content` 改 `.gd` 文件

**症状**：用一条 PowerShell 替换命令批量改两个测试文件里的中文，结果**整个文件的中文变成
乱码**（`实测` → `瀹炴祴`），而且**丢字节、吞换行**，连 GDScript 都解析不过
（`Parse Error: Unexpected "?" in class body`）。

**根因**：与 4.4 是同一个坑的另一面 —— 中文 Windows 的 PowerShell 5.1
`Get-Content -Raw` 会**按 GBK 解码** UTF-8 文件，于是每个中文字符被错误地两两配对，
再 `Set-Content -Encoding UTF8` 写回去，就得到一份「UTF-8 编码的 GBK 乱码」。
更糟的是：
- GBK 是双字节，UTF-8 的中文是三字节 → **配对会错位**，错位处整块字符丢失；
- 错位的尾字节还会把后面的**换行**当成配对字节吞掉 → 两行并成一行；
- 丢失的字节落在字符串引号附近时，引号被吃掉 → 语法直接坏掉。

**为什么难救**：拿回来的字节流已经是有洞的，`U+FFFD` 标记的就是丢字节的位置，
**反向还原（encode('gbk') → decode('utf-8')）只能救回一部分**，
每丢一个字节还会连累后面一两个字符。**没有备份就只能重写文本**。

**修法（照做，别自己发明）**：
1. 改 `.gd` / `.md` 这类含中文的文本，**只用编辑工具（read / edit / write）**，
   绝不用 shell 的文本替换管道；
2. 万不得已要在脚本里读写中文文件，用 **Python**（`io.open(..., encoding='utf-8')`）
   或显式 `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)`，
   **不要**用 `Get-Content` / `Set-Content`；
3. 工作树里绝大多数文件是**未提交**的（`git status` 一片 `M`），
   所以「弄坏了就 `git checkout` 恢复」**不成立** —— 那会退回很久以前的版本。

## 五、本轮（第 0 轮）实测记录

> 这一节全部是本轮真的发生过的事，按「症状 → 根因 → 修法」记，方便下次直接对照。

### 5.1 单格城墙证明不了「拦断」（测试设计的坑）

**症状**：写了一个「城墙把敌人路线切断」的断言，结果怎么都失败。
**根因**：在**四连通**地图上，一段孤立的城墙永远可以绕过去 ——
测试想验的是「拦断」，但造出来的场景根本没有拦断。
**修法**：要真正切开地图，必须拉一条**从地图一侧连到另一侧**的长墙
（`tests/test_logic.gd` 的 `_build_full_wall_row()` 会在第 9 行铺满一整行）。
顺带一个推论：测「墙拆了出现缺口」这类行为时，也要用长墙，否则缺口本来就不存在。

> ⚠️ 八方向之后这条仍然成立，但**多了一层新风险**：斜着错开的墙本来也能漏人。
> 现在 `pathfinder.diagonal_step_allowed()` 用「斜走时两个正交邻格都必须可通行」把它堵住了
> （见 5.8），所以上面这条用例在八方向下依然有效。

### 5.2 ★ 死掉的建筑摘不掉，敌人卡在墙前（真 bug）

**症状**：敌人对着城墙打了 200 秒，墙一直 300 血、一点没掉；日志里重复的事件也没有。
**排查过程**（值得记，因为它靠猜是猜不出来的）：
把 `take_damage` 里临时加一行 `print`，打出**每次伤害的来源 id 与当前血量**，
才看见真相 —— 墙其实早就被打到 0 了，那一帧有**三个将领**各打了它一次，
血量直接从 20 掉到 0 再到 0，而 `world.building_list` 里它一直没被摘掉。
**根因**（两层，都要改）：
1. `take_damage()` 返回的是「它现在**还活着**吗」（HTML 版语义），
   于是同一帧里第二个攻击者打一具尸体也会返回 `false` → **重复广播 `building_down`**。
   改成返回「**本击是否造成摧毁**」，只在首次摧毁时广播。
2. `remove_building()` 开头写了 `if not b.alive: return false`，而收尸逻辑收到的
   必然是 `alive == false` 的东西 —— 于是**没有任何建筑被摘掉**（见 2.6）。
3. 收尸判据原来写的是 `if b.alive or b.hp > 0: continue`，也应改成只看 `alive`。
**修法**：三处一起改（`logic/building.gd` 的 `take_damage`、`logic/world.gd` 的
`remove_building` 与 `_collect_destroyed_buildings`），并补了四条断言：
掉血量是 `combat.building_damage` 的整数倍、从建筑表移除、从格子索引移除、那一格立刻可通行。

### 5.3 ★ 敌人贴着墙不拆（AI 时序的坑，和 HTML 版那个 bug 同款症状）

**症状**：`target_building` 被设上又立刻被清掉，敌人站在原地一下也不拆。
**根因**：`enemy_ai.update()` 里「已经贴到据点就 `stop()`」这一支写在**拆墙判定之前**。
敌人走进大本营相邻格后，每帧都被这一支先 `stop()` 按住，
而 `combat.update_building_combat()` 那一帧又 `halt()` 一次 —— 两头一夹，谁也不动手。
**修法**：「贴到据点就停」必须先问一句「我还欠着一段没拆的墙吗」；
有墙就先锁墙、`continue`，别停。
**教训**：HTML 版文档里那句「`moveTo()` 原地不动也返回 true，所以要分开判断」是对的，
但**只把返回值判断分开还不够** —— 两个模块各自「合理地」让单位停下，
合起来照样能让它发呆。改 AI 时要把两侧的停手机制一起看。

### 5.4 测试被「正确的防守行为」骗了（两次）

**症状**：两处断言假失败 —— 「城墙在掉血」永远不成立、「箭塔不误伤己方」总是掉血。
**根因**：
1. 城墙用例里将领站在敌人与基地之间，敌人会**先跟将领打**（这是对的），
   2 秒的窗口里它根本没碰到墙；后来将领把敌人一路咬死，墙一次都没挨打。
2. 箭塔用例把将领挪进射程后又让它挨了敌人的打，掉的血被误判成「箭塔打自己人」。
**修法**：把测试场景**收窄到只验一件事** ——
拆墙用例把将领全部移出战场；「不误伤」单独建一个没有敌人的世界来测。
**教训**：一个世界里同时放「玩家单位 + 敌人 + 箭塔」时，
任何「谁掉了多少血」的断言都不可靠，因为伤害来源不止一个。
要么隔离场景，要么断言「来源 id」（这轮就是靠打印来源 id 才看清 5.2 的）。

### 5.5 GDScript 的 `:=` 会从 Variant 推断，而且**被当成错误**

`dict.get(...)`、无类型对象的成员调用（`u.move_to(...)`、`b.center()`）返回 Variant，
写 `var x := ...` 会直接报：

```
Parse Error: The variable type is being inferred from a Variant value, so it will be typed as Variant.
(Warning treated as error.)
```

**规矩**：接这类返回值时用 `=`（无类型），或显式写类型 `var x: Vector2 = b.center()`。
本项目的 `tools/check-syntax.ps1` 会对每个文件做一次 `--check-only`，这类问题会在
**写代码的当下**就被抓住，不用等到跑测试。

### 5.6 滚轮缩放方向：「凭直觉写」连错两次，最后靠断言钉住

**症状**：滚轮方向反了（向上滚变成拉远）。
**过程**：改第一次 —— 又反了。两次都是同一个毛病：**凭直觉推断 Godot 的 zoom 语义**。
第二次我甚至是对着一句自己写下的错误结论改的（「Godot 里 zoom 越小画面越大」），于是原样再反一次。
**真相**：Godot 4 的 `Camera2D.zoom` 是**放大倍数** —— 值越大，画面里的东西越大。
所以「向上滚 = 放大」就是 `zoom *= zoom_step`，「向下滚 = 缩小」就是 `zoom /= zoom_step`。

**结论**：这种一改就错的东西不能靠眼睛猜，也别把自己推断出来的结论写进注释当依据。
做法是**写一条真的构造滚轮事件的断言**
（`tests/test_view.gd` 的 `_test_zoom_direction`：造 `InputEventMouseButton`
→ 调 `handle_mouse_button` → 读回 `cam.zoom.x` 比较），顺便把上下限也钉住。

**通用教训**：凡是「方向 / 正负号 / 单位」这种只能靠观察确认的东西，
**先把断言写出来，再去改实现** —— 否则每一次修改都是在赌。

### 5.7 三个「手感」bug：一个像素阈值、一个格心落点、一个一帧转向

这三条都是**手玩才能发现**的（自动化断言跑不出来，因为断言原本就是照错误行为写的），
修完各自补了回归（`tests/test_path_feel.gd`，25 项）。

**① 点得越准，单位越不动**（`logic/unit.gd`）
起点与终点在同一格时 A* 返回空路线，代码走 `elif pos.distance_to(dest_pt) > 0.5` 分支 ——
而 `0.5` 是**像素**口径的阈值，在「格」为单位的坐标系里它等于**半格**。
于是点 0.05 / 0.2 / 0.45 格外全都不动，而且 `order_move` 还返回 `true`。
修法：换成 `EPS = 0.001`（格），并在文件头写明「任何『够不够近』的阈值都必须按格来写」。
**教训**：`docs/pitfalls.md` 3.2 早写过「原地不动也返回 true」，我还是踩了同一类坑 ——
**返回值不能当成功判据**这件事，要连着「阈值单位」一起检查。

**② 点建筑 / 山时落点被钉在格心**（`logic/pathfinder.gd` 新增 `nearest_reachable_point`）
原来走 `nearest_reachable()`（从目标往外扩圈找最近的可达格），拿回来的是**那一格的格心**，
所以点大本营格的右半边，停点离你点的地方还有 1.077 格 —— 看着就是「贴不上去」。
修法：把点击位置投影到目标格内「离点击最近的可达点」上。
⚠️ 这里有个**必须连带的改动**：贴边落点就在（不可通行的）目标格边缘上，
而 A* 的终点必须是可通行格 —— 所以函数要连**落点所在的格**一起返回。
第一版只返回了点，调用方拿目标格去寻路 → 直接失败，连山都点不动了。

**③ 拐角生硬：转向集中在一帧里**（`logic/pathfinder.gd` 新增 `round_corners`）
拉直（string pulling）只**减少**路径点，单位却是「走到路点才允许转向」，
所以直角弯处单帧转角实测 **58°**。
修法：在每个拐点前后各切一小段，用二次贝塞尔曲线连过去，并**细分成 8 段**。
为什么必须细分：只放两个切点的话，`step_along_path` 会把它当成两条普通线段，
转向仍然集中在一两帧（实测只从 58° 降到 30.6°）；细分后每一步只有整段转角的 1/8，
实测 **58.1° → 8.5°**，而且因为抄了近路，总帧数还少了几帧（177 → 174）。
安全性：贝塞尔曲线**落在三个控制点的凸包内**，而这三点都在已验证过的折线上，
另加一次 `segment_clear(P, Q)` 兜底；不通过就保留硬拐角（宁可生硬，不可穿墙）。

**这一节的通用教训**：凡是「方向 / 阈值单位 / 数值口径」这类只能靠观察确认的东西，
**先在测试里写成断言再去改实现**；而且断言要用**真实跑出来的轨迹**去算，
不能拿路径点算 —— 路径点好看不代表单位走得好看（我自己就被这个骗过一次：
只看路径点以为圆化生效了，其实单帧转角没变，因为转向集中在切点那一帧）。

### 5.8 ★ 八方向改动的两处「能跑通但感觉怪」

八方向是**有意偏离** HTML 版「四连通」规则的一处（理由与开关见 [`route.md`](route.md) 第七节）。
它只有两个地方会出错，而且都不报错、只是「感觉怪」，所以各写了一条断言
（`tests/test_diagonal.gd`，44 项）。

**① 步进代价与启发式必须成对改**（最容易漏）
斜走一步的长度是 √2，不是 1；启发式也必须从曼哈顿换成 **octile**
（`max + (√2-1)·min`）。只改一个的后果：A* 会偏爱斜线、给出**明显绕远**但仍能走通的路径。
为什么必须换启发式：八方向下曼哈顿会**高估**（对角一步覆盖了曼哈顿距离 2、却只花 1.414），
高估的启发式会让 A* 不再保证最优。断言的写法是「实际路径代价 == octile 距离」+
「octile 永不超过曼哈顿（即可采纳）」。

**② 对角不许穿角**（八方向才存在的问题）
```
山 草
草 山      ← 两个可通行格只在一个角上相碰
```
四连通下这种缝物理上走不过去；八方向若只看目标格，单位就能从两座山的尖角之间挤过去。
**这不只是观感问题**：斜着一格错开的墙会因此挡不住人 —— 等于把玩家造的每一道防线都悄悄削弱。
修法：斜走时要求**两个正交邻格都可通行**（`pathfinder.diagonal_step_allowed()`），
而且这条守卫要在 **A* 与 `reachable_tiles()` 里用同一份实现** ——
否则会出现「BFS 说走得到、A* 却找不到路」，表现就是单位站在原地发呆（和 3.3 同款症状）。

> **顺带记一条**：真正「任意方向」（像 SC2 那样斜着贴墙走）是**做不到**的，
> 只能无限逼近 —— 只要地图是格子，单位就只能在格心之间走折线。
> 八方向 + 拉直 + 圆角已经是格子方案的上限；再往上要么加路点（navmesh），
> 要么放弃格子（那就得重做整个地图与建造系统）。

### 5.9 单位碰撞与局部避让：三条「不写断言就不会报错」的规则

做碰撞（`logic/collision.gd`，软分离 + 谁给谁让路）时，最容易错的不是数学，而是**取舍**。
三条都写成了断言（`tests/test_collision.gd`，33 项）：

**① 单位**绝不能**进寻路**（这条最重要，也最反直觉）
自然的想法是「被占住的格不能走」——**错了**。真那样做的话：
两队兵会互相把对方判成墙 → 双方都认为无路可走 → **死锁**；
而且单位每动一格路径就过期，要么每帧重寻路，要么走一条已经失效的路线。
所以：**寻路只看地形与建筑，单位之间靠局部推挤解决**（与 SC2 同一个取舍）。
`test_collision.gd` 里专门有一条**反向**断言盯着这件事
（「路中间站着一个单位时，寻路结果与没有它时一致」）。

**② 推力权重不能都是 0，而且「谁给谁让路」必须显式定义**
配置是 `unit.push_moving_weight : push_idle_weight = 1.0 : 0.2` ——
**有移动命令的单位推得动待命的单位**，反过来推不动。
如果不定这条规则（两边各推一半），队首堵在窄口时会**全体卡死**：谁都等对方先让。
两个权重都配成 0 也不会报错，只会静默变成「谁也推不动谁」，所以断言里查了这一项。

**③ 推挤只改位置，不改意图**
被推的单位如果连 `path / moving / goal` 一起被改掉，表现就是「被撞一下就发呆」——
忘了自己要去哪。所以 `collision` 只写 `pos` 与 `tx/ty`，
`test_collision.gd` 有一条断言专门验「被推之后仍然在走，且目标点没变」。

> 另外一条实测手感数据（三个单位被点到同一个目标点）：
> 162 帧内全部到位，最远的离目标 0.34 格，最近的一对互距 0.248 格（软下限 0.252），
> **停稳后 120 帧漂移 0.0000 格** —— 不抖、不互相顶。
> 这个数字值得记：如果哪天把 `collision_iterations` 调小、或把 `slack` 调没，
> 单位会在目标点附近来回微抖，而那是「看着烦」但不会报错的一类退化。

### 5.10 ★ 加第三种兵种时，「是将领吗？不是就当敌人」会静默给错数值

**症状**：无。亲兵能跑能打能选中，**只是血量是 60、伤害是 10**（测试敌人的数值）。
**根因**：`unit.gd` 里两处二元判断：

```gdscript
u.hp_max = cfg.unit_hp_max if p_kind == KIND_GENERAL else cfg.enemy_hp     # ← 亲兵掉进 else
return cfg.general_damage if kind == KIND_GENERAL else cfg.enemy_damage     # ← 同上
```

加了 `subordinate` 之后，凡是「不是将领」的都会拿到敌人的数值。
另外 `cfg.unit_radius_of(_kind)` **根本没看参数**，直接返回将领半径。
**修法**：全部改成按 kind 查表 —— `cfg.unit_hp_of(kind)` / `unit_speed_of(kind)` /
`unit_combat_of(kind)` / `unit_radius_of(kind)`，并在 `test_retinue.gd` 里加一条
「亲兵没有退化成测试敌人的数值」的断言。

**教训（值得单独记）**：凡是 `if A else B` 形式的**数值分配**，
在加第三种类别的那一天就是一个 bug —— 它不会报错，只会让新类别的数值**看起来合理但其实是别人的**。
同一类问题还有：`unit_radius_of()` 忽略参数、以及本文档 3.7 记的
「箭塔索敌写成 `u.faction == b.owner` 而不是 `same_side()`」。

### 5.11 加单位数量之后，老断言会成片假失败（隔离助手）

**症状**：给将领配了 3 个亲兵之后，`test_logic.gd` 一次性红了 14 条。
**根因**：不是功能坏了，而是三类断言被旁观者搅乱：

| 类型 | 具体例子 |
|---|---|
| 数量/种类断言 | 「开局 3 个将领」现在是 12 个单位；「所有单位都该是将领」必然假失败 |
| 血量断言 | 「0.5 秒内不会连打」—— 亲兵一起开火，敌人几帧就死了，冷却断言反而不成立 |
| 状态断言 | 「站满 4 秒完成占领」—— 亲兵站在角落里**也在占区块**，区块归属变成敌人 |

**修法**：给测试一个统一的隔离助手 `_isolate(world, keep)` —— 把不关心的单位
**真的从 `world.units` 里摘掉**。两个细节是被实测逼出来的：

1. **不能只是挪到地图角落**：亲兵挪到角落仍然会占区块进度（第三条就是这么假失败的），
   也仍然会被碰撞推挤影响轨迹。
2. **不能图省事写 `world.units = [u]` 就把别的单位丢掉**——那样它们从世界里消失，
   碰撞与战斗都找不到它们，「隔离」看着生效了，其实测的是一个不完整的世界。
   对**单个**被测单位用 `w.units = [u]` 是可以的（`test_path_feel.gd` 就是这么做的），
   但要保留多个单位时必须用 `_isolate` 这种「保留 keep、其余摘掉」的写法。

**教训**：这个坑本项目已经踩过三次（将领干扰箭塔测试、将领把测试敌人打死、亲兵占区块）。
**加任何「默认在场」的单位之前，先想一遍哪些断言会被它搅乱**，
并给测试一个隔离手段 —— 否则你会花时间怀疑功能，而问题在测试的假设上。

### 5.12 ★★ 「到达后互相挤着转」：不是停止距离，是四层机制叠在一起

这轮最值钱的一条。**提问的人猜的是「停止距离没设置好」——那个猜测是错的**，
但正是这个猜测把我引到了真正的问题上。先把实测数字摆出来（12 个单位点到同一点）：

| 指标 | 修之前 | 修之后 |
|---|---|---|
| 全部停下 | **2000 帧都没停下来** | 307 帧 |
| 移动单位·帧累计 | 12734 | 2791（理想 ≈ 2400） |
| 方向反转次数 | 5708 → 8064 | 185 |
| 停下后 300 帧 | 持续以 0.16 格/帧漂移、朝向每帧变 36° | **漂移 0.0000 格、朝向变化 0.0°** |

根因是**四层叠在一起**，每一层单独看都「合理」，合起来就永不收敛。修的时候按顺序剥：

**① 「路径空了」被当成「到达了」**
路径的**最后一个路点就是终点本身**。所以单位中途被队友挤到「已经在终点附近」时，
`path.is_empty()` 成立 → 直接吸附到终点、结束移动（哪怕它才走了三分之一）。
修法：到达判定必须用**距离**（`pos.distance_to(goal) <= 本帧剩余预算`）。

**② 多个单位共用一个精确目标点**
整队被点到同一点时，**每个人领到的目标是同一个像素点**，于是每帧
「吸附到该点」与「被碰撞推开」互相打架，谁也不肯让。
修法：到达那一刻判断「终点是否已被别人占着」，是就**就近找一个空位**落位
（`_find_arrival_slot`）。谁先到谁占住，后来的人落在旁边 —— 这才是人群该有的样子。

**③ 到达之后 `path` 是空的，所以 `step_along_path` 整个函数都不会执行**
调用处是 `if not u.path.is_empty(): u.step_along_path(...)`。
于是**被推走的单位没有任何机制走回去**，只能一直被推着漂
—— 实测将领就这样漂了 2000 帧、总行程 83 格（本该 8 格）。
修法：到达时记住落点（`settled_goal`），每帧 `reclaim_settled_spot()` 发现被推远就回去，
**并且回位次数要有上限**（挤不进去就就地待着，否则又变成无限努力）。

**④ 推挤一帧能推走 ~0.25 格，而单位自己一帧只走 0.04 格**
数量级差 6 倍 → 人群里「最后一段」**永远走不完**：它一直 `moving = true`、
`path` 非空，却一步也没靠近终点。所以光看「路径空了」永远等不到。
修法：加**进度停滞检测**（`stuck_timer`）—— 连续 `jam_giveup_sec`（默认 0.6 秒）
没有更接近终点就认账，就近落位。

**顺带修掉的两个衍生 bug**（都是修①②时自己引入的，各自被断言抓住）：

- 落位时又补了一段位移 → 最后落位那帧走了 `0.04 + 0.024 = 0.0644`，超过速度预算 0.04。
  根源是 `recenter`（本帧预算快照）没有跟着循环一起消耗。
  修法：**`recenter` 与 `remaining` 同步递减**。
- `move_to()` 里调了 `clear_settled_spot()` → **回位动作自己把「最多回位 3 次」的计数器清零**，
  于是上限永远不生效，直接退化成 12 个单位永远 `moving = true`。
  修法：清零只放在 `order_move()`（真正的玩家新命令）里，不放在 `move_to()` 里。

> **两条可以带走的教训**：
> 1. **「抖」和「转」要分开查**：位置抖是碰撞与吸附打架，朝向转是**移动逻辑**在反复
>    重选方向。我一开始以为朝向被写歪了，量了两次才发现朝向一直是对的
>    （是我的期望值算错了）—— **先量，再猜**。
> 2. **凡是「让单位自己走到某处」的机制，都要有「走不到怎么办」的出路。**
>    没有出路时它会永远努力（`moving = true` 永不结束），表现就是「一直在动但哪也没去」。
>    出口有两种：**换个近一点的目标**（就近落位），或者**认账停下**（jam_giveup）。

### 5.13 顺带修正的**箭塔索敌**与**配色表**（HTML 版审查遗留）

- 箭塔索敌统一走 `same_side()`（HTML 版写的是 `u.faction == b.owner`，
  单人下等价，但引入结盟就会变成「箭塔打队友」）
- 阵营配色表补齐 `p1`..`p8` 与 `enemy`，全部集中在 `config.json` 一处，
  代码通过 `Palette`/`Config.faction_color()` 取色 —— 不再有「配色表只到 p4」这种漂移

### 5.14 ★ 命令产生的事件会**静默消失**（UI 改版时才发现的真 bug）

**症状**：城墙建起来了、兵也招出来了，但事件日志里**什么都没有**。
逻辑全对、画面全对，只有「提示」不见了 —— 这类 bug 靠手玩很容易被当成「日志本来就不记这个」。

**根因**：`world.tick()` 开头是 `_events = []`，而命令是**输入事件**触发的，跑在两次 tick 之间：

```
输入事件 → command_processor → world.push_event(...)   # 事件进了 _events
   ↓ 同一帧稍后
world.tick(dt) → _events = []                          # ← 刚刚那条被清掉了
```

于是 `building_built` / `building_demolished` / `build_rejected` / `enemy_spawned`
（以及这轮新增的 `unit_recruited` / `recruit_rejected`）**永远到不了 HUD**。

**修法**：清空从「开头」挪到**末尾**（把本帧的与两次 tick 之间的**一起**交出去再清），
并在 `tests/test_ui.gd` 的 `_test_command_events_reach_log` 里钉住：
「命令 → 事件 → 底栏日志」这条链必须通。

**教训**：「事件数组」这种跨帧缓冲，**清空的位置就是它的语义**。
写在开头 = 「只保留 tick 内部产生的事件」，写在末尾 = 「保留到被消费为止」。
选哪个都行，但必须说得出为什么 —— 因为两种写法都不会报错。

### 5.15 ★ 写好了却没接线的 `set_mouse()`：边缘滚屏一直是死的

**症状**：`camera_rig` 里明明有边缘滚屏的代码与参数，鼠标推到屏幕边缘却纹丝不动。

**根因**：`_edge_scroll()` 的第一行是 `if not _edge_scroll_on or not _mouse_inside ...: return`，
而唯一的写入者 `camera_rig.set_mouse()` **从来没有被调用过** ——
`_mouse_inside` 永远是 `false`。手玩清单里那条「鼠标推到窗口边缘会滚屏」因此一直是假通过。

**修法**：在 `main.gd` 每帧接上。⚠️ 接的时候有个必须先想清楚的问题：
新 UI 的底栏把屏幕下沿整个盖住了，如果**所有 HUD 面板**都算「鼠标在 UI 上，别滚」，
那底边就**永远滚不到地图下方**（鼠标只要在下方就是在 UI 上）。
所以判定的口径必须是「**可点的控件**」（部队行 / 命令卡 / 页签 / 设置），
纯文字面板（详细信息、阵营占位）照样让鼠标滚屏 —— 见
`view/ui_layout.gd` 的 `interactive_rects()` 与 `tests/test_ui.gd` 的 `_test_hit_test`。

**教训**：`if flag:` 这种守卫如果没人写 flag，是**静默失效**而不是报错。
新增「只有某处会写」的状态时，顺手搜一遍「谁写它」。

### 5.16 无头模式下根视口是**正方形**（几何断言会假通过）

**症状**：`tests/test_ui.gd` 里「贴屏幕下沿」的面板位置怎么都不对 ——
详细信息面板出现在 y=1680 而不是 840。headless 下 `root.get_visible_rect()` 实测是
**1920×1920**（没有真实窗口，拉伸模式给出的设计空间是方的）。

后果有两种，都很难看：断言**假失败**（以为布局写错），或者把断言写成「无所谓」而**假通过**。

**修法**：在测试里显式把设计空间钉成参考图尺寸，再断言坐标：

```gdscript
root.size = Vector2i(1920, 1080)   # ← 钉住设计分辨率
await process_frame                 # 让锚点重新结算
```

这样「详细信息 = 1030×240 且在 (400, 840)」才是真的被验证过的。
顺便还能在同一条测试里把窗口改成 2560×1080，验证**超宽时贴右下角**这条规则
（`view/ui_layout.gd` 的 `apply_rect(..., anchor_right, anchor_bottom)`）。

**教训**：几何断言一定要先钉住「设计空间是多少」。
拿一个由运行环境（甚至由「有没有窗口」）决定的尺寸去断言坐标，等于在断言随机数。

### 5.17 ★ 「整格阻挡」与「本体阻挡」混在一起，会长出「看着能过、实际被挡」

**背景**：需求要「大本营 / 箭塔居中缩小，本体挡敌方、不挡己方，敌方能从建筑空隙穿过」，
而在这之前，建筑对 A* 来说是**整格**不可通行（`building.blocks(faction)` 直接喂给 `passable()`）。

**最容易写错的版本**：把 `blocks()` 改成「本体挡不挡」，然后继续拿它喂 A*。
后果是**两套语义被压进一个函数**，而它们的粒度根本不同：

| 问题 | 整格口径下 | 本体口径下 |
|---|---|---|
| A* 能不能走进这一格 | 不能 | 能（缝要能走） |
| 单位能不能与本体重叠 | 无所谓（格都进不来） | 不能 |

压在一起之后，任何一处改动都会同时影响「寻路」和「碰撞」，而且**都不会报错**：
把 `blocks()` 写成「本体挡」→ 格子被整格封死，缝隙白留（表现：敌人死活不从缝里过）；
反过来只把 `passable()` 放开而不加本体碰撞 → 单位直接站在建筑**正中**（表现：兵叠在箭塔上）。

**做法**（`logic/building.gd` 文件头也写了）：两个函数、两个名字、各喂一边 ——
`blocks(faction)` 只给 A*（格级），`body_blocks(faction)` 只给移动碰撞（本体级），
本体尺寸只有一个来源（`config.building.<type>.body_scale`），**渲染也读它**
（`palette.building_rect()` 不再自己写内缩量，否则视觉与碰撞会各走各的）。

**顺带三处必须一起改，否则会冒出「贴着本体蹭」的退化**：

1. `segment_clear()`（拉直）要判「这条线有没有切进本体」，否则平滑后的直线从本体正中穿过去；
2. A* 要给建筑格加代价（`path.building_penalty`），否则敌人一条直线从箭塔正中穿过去；
3. `_can_stand()` / `_slot_ok()` 要认本体，否则推挤或落点会把敌人塞进本体里。

**为什么斜向的缝要单独放行**：两个**对角相邻**的建筑之间，缝是穿过「四格交汇的角」的，
而八方向的守卫（5.8）原本一律禁止斜穿两个障碍格。缝宽 = 两块本体到那个角的最近点距离，
≥ 单位直径才放行 —— 城墙本体就是整格（净宽 0），所以**城墙那条守卫一字未变**，
`tests/test_diagonal.gd` 的「不能从墙缝钻进大本营」仍然成立。

### 5.18 ★ 玩家的命令与「这一帧在打谁」压在一个字段里，「打完继续走」必然失效

**背景**：需求要「右键点敌人 = 优先攻击它」「右键双击 = 行军攻击（走到该点，路上遇敌就打，打完继续走）」。
这需要在单位上记两件事，而它们**看起来**是同一件事：

| 记什么 | 字段 | 什么时候被写 |
|---|---|---|
| 玩家点名要打的目标 | `ordered_target` / `ordered_building` | 只在玩家下令时写 |
| 这一帧在打谁 | `target` / `target_building` | 自动警戒、玩家命令、AI 都会写 |

**最容易写错的版本**：只留一套字段，或者「目标没了」时顺手调 `clear_target()`。
后者会把命令一起清掉，于是**行军攻击打死路上第一个敌人之后就把自己的命令取消了** ——
表现是「走两步就停下」，不报错、也不崩，只是那个功能等于没做。
（这里第一次实现就是这么写的，被 `test_attack_orders.gd` 的「打完继续走到目标点」当场抓住。）

**做法**：两个层次、两个函数 ——
- `drop_engagement()`：只清「当前交战」（`target` / `target_building` / `anchor`）；
- `clear_target()`：连玩家的命令（`ordered_*` / `has_attack_move`）一起清，
  只在**明确的覆盖命令**（普通移动、停止）和**点名目标已完成**时调用。

另外两条同源的坑，一起记在这里：

1. **`ordered_target` 必须跳过 leash 判定**：追击上限是「它自己追出去多远」的限制，
   玩家点名的目标不该受它约束（否则右键点一个远处的敌人，单位追一半就自己放弃了）。
   实现上就是 `order_attack_unit()` 把 `anchor` 置空 + `update_combat()` 里判一句 `ordered_target == null`。
2. **行军攻击要在移动中索敌**：普通警戒只在「静止且没目标」时跑，
   而行军攻击的全部意义就是**边走边找**。第一版漏了这条，单位一路无视敌人走到终点。
   一行 `if not u.moving or u.has_attack_move:` 解决，但没那条断言根本不会发现。

**第三次踩到同一族（手玩报的 bug，已修）**：右键点名拆建筑时，
「自动警戒」会在单位**刚站定那一刻**把玩家的命令顶掉 ——
因为警戒的触发条件正是「静止就索敌」，而单位走到建筑旁边会 `halt()`：

```
右键点箭塔 → 一路走过去（moving = true，警戒不跑，一切正常）
          → 到达，halt()（moving = false）
          → 下一帧警戒分支开跑：「附近有个敌人！」→ 转火
          → 表现：走到箭塔附近之后随机打周围的敌人，玩家点的箭塔反而没人管
```

**修法**：把「玩家点名的建筑还活着」提到警戒分支**之前**，单独一支、并跳过整个警戒，
直到那栋建筑被摧毁（与 SC2 一致：明确点名的目标不会被路过的敌人顶掉）。
`tests/test_attack_orders.gd` 的 `_test_ordered_building_not_distracted` 钉住它 ——
旁边那个敌人会打我们，而我们全程一次都不许还手。
**去掉修复后这条断言立刻变红（实测 528 帧里转火 121 次）**，说明它测的正是这个 bug。

**这一族坑的共同形状**：只要「自动行为」与「玩家命令」都能写同一个状态字段，
就必须有一条**明确的优先级规则**并落在代码结构里（谁先谁后、谁覆盖谁），
不能指望「已经设了目标就自然不会被改」。三次翻车（打完就忘命令、行军攻击不索敌、
站定就转火）其实是同一件事的三个面。

### 5.19 ★ 绝对矩形与「节点局部坐标」的矩形：居中偏移被悄悄吃掉

**症状**：大本营 / 箭塔没有在格子里居中，而是贴在格子**左上角**（城墙看不出来，
因为它是 1.0 格）。逻辑层的 `body_rect()` 明明是居中的，上一轮还专门为「居中」写过断言。

**根因**：渲染路径上有**两个坐标系**，而断言只验了其中一个：

```gdscript
# building_view.gd（错的那版）：节点原点 = 自己那一格的左上角
var r := PaletteRes.building_rect(building, cfg)   # 绝对矩形（含居中偏移）
var local := Rect2(Vector2.ZERO, r.size)           # 只取 size → 偏移丢了
```

`building_rect()` 返回的是**绝对**矩形，里面那个 `position` 就是居中留白；
只取 `size` 从 `(0,0)` 开始画，等于把留白全丢到右下角去。
上一轮的断言验的是绝对矩形（`px.get_center() == 体心`）—— 它是对的，所以**测试全绿、画面是错的**。

**做法**：把「绝对 → 局部」的换算也收进 `palette.gd`（新增 `building_local_rect()`），
渲染只调它，并且**断言按局部矩形写**（中心必须是格心）。
**通用教训**：凡是「同一块东西在两个坐标系里各有一份坐标」，两处都要有断言 ——
只验其中一个，另一个错了也照样绿灯（与 5.6 那条「靠眼睛猜不如写断言」是同一类问题）。

### 5.20 ★ 视图自己发明了一条判定规则，于是「抢别人的地」没有进度条

**症状**（手玩报的）：
> 「当己方单位在没有敌方单位的区块上时，没有占领条，而是在一段时间后直接将该区块变为己方」

占领逻辑一直是对的（`zone.update()` 老老实实按 4 秒推 `progress_by`），
**缺的只是那一根条**。两层原因：

1. `zone_view._draw()` 自己写了一条判定：**只在 `owner == ""` 时画进度条**。
   于是「抢一块已经有主的区块」全程没有任何反馈 —— 画面上就是「过一会儿突然变成我的」。
   为什么会遇到「有主的区块」？因为地图上那 4 个守军（NPC 也参与占领）站着不动就把自己那一格
   占成了敌方的；玩家把守军清掉再走进去，面对的正是「有主、但场上没有敌方单位」。
2. 更隐蔽的一层：视图读的 `z["progress"]` **语义随状态变化** ——
   无主时是「领先者的进度」，有主时是「**主子**的进度」（= 1.0）。
   所以光放开第 1 条的判定，还会画出一根一上来就满格的假条。

**为什么视图会写错**：因为「该看谁的进度」这条规则**逻辑层从来没有提供过**。
视图只能自己从 `owner` / `progress` 这两个字段里猜，而 `progress` 又是个被压扁的汇总值
（把「谁在推」这个维度丢掉了）。这类错误不会崩、不会报错，只是**看不见正在发生的事**。

**做法**：把规则收回逻辑层 —— 视图只做「取色 + 画」，判定（该不该画、画谁的、什么状态）全在逻辑层。
**通用教训**：**只要一个字段的语义随状态变化**（同一个 `progress`，有主/无主含义不同），
就不要让视图直接读它 —— 要么提供语义明确的查询接口，要么把汇总维度一起给出。
判断标准很简单：视图里如果出现了 `if owner == ...` 这种**业务规则**，
那说明这条规则本该在逻辑层（与 5.19 一样，问题都出在「两个地方各有一套口径」）。

**这条坑的第二次翻车（同一批手玩反馈）**：改成「逻辑层决定该看谁的进度」之后，
**只返回一条「领先者」**仍然不够 —— 双方单位同时站在区块里时，那一条会在两方之间来回跳
（实测：我方 0.50 → 0.75 → 一占下来就变成对方的 0.75 并开始回落；对手先到的话更糟，
条全程只显示对方的）。玩家报的原话就是「无法进行读条或读条停止」。
**第三次（最终定案）**：手玩把完整规则写了出来，才发现**两版实现都把规则理解错了** ——
真正的规则是「**同一时刻只有一方能读条**」：

| 情形 | 读条 |
|---|---|
| 区块里只有一方单位 | 读它的条 |
| 双方同场 | **谁都不涨**：正在读的那条**冻住**（不涨不降） |
| 有进度但人不在场（移出 / 被打光） | 按 `decay_per_sec` 缓慢回落 |
| 别人还有没归零的进度 | **严格阻塞**：新来的一方不开读（等它退完） |

所以正确的是**一条条 + 一个状态**（`reading` / `frozen` / `decaying`），而不是两条并列。
上一版「逐阵营独立累计、谁先满谁拿」的模型是**我自己想当然**的：它看起来很合理
（对称、无阻塞、好实现），但它不是需求。

**教训（值得单独记，三条）**：

1. **「谁领先」这种汇总会把「有几个人在抢」这个维度压掉**：多方同时作用于同一对象的状态
   （占领进度、争夺中的资源点、抢旗），显示层要的是「**这一方现在能不能读、读到哪**」，
   而不是一条「当前领先者」。
2. **不要把「对称/优雅」当成需求**：独立累计实现起来更干净，却直接违反了「双方同场不能读条」
   这条玩法规则。规则没写清楚时**先问**，不要挑一个自己觉得合理的模型就开工。
3. **状态机要显式写出来给 UI**：`capture_state` 这种字段放在逻辑层，UI 只取色。
   这次连「冻住」这个状态都是后加的 —— 如果 UI 自己从 `owner` + `progress` 推，它推不出来。

### 5.21 地图编辑器这一批：区块不再是矩形，于是「包围盒」这个偷懒的地方全露出来了

地图编辑器（`dev_gd_a/tools/map_editor/`）把区块从「6×4 均分的矩形」变成了
「作者逐格划出来的**任意形状**」。这一改，三处「拿包围盒当区块」的地方就站不住了：

1. **`zone_view._draw()` 按 `x0/y0/x1/y1` 画一整块矩形** —— L 形区块会把地图外的空地
   也涂成领地。改成按 `z["tiles"]` 逐格画底色、沿地块边界画轮廓。
   （老地图的均分区块地块刚好填满包围盒，所以画出来与从前**逐像素一致** ——
   这也是为什么改动没有惊动任何一条老断言。）
2. **`tile_count` 曾经 = 包围盒面积**。地块是任意形状时这个数会偏大，
   而它是要拿去算资源产出的（`owned_tile_count`）—— 于是「形状奇怪的区块白送资源」。
   现在两条建法都按**真实地块数**填 `tile_count`。
3. **`world.zones.zone_at()` 以外的代码不许再假设「区块是矩形」**：
   `tests/test_zone_capture.gd` 里那个 `_neutral_spot()` 助手当初就是靠包围盒中心找地的 ——
   它现在仍然能用（包围盒只是变紧了），但**新写的代码不要这么干**，要遍历 `z["tiles"]`。

**教训**：「占位实现」里的每一个近似（均分、包围盒、面积 = 地块数）都会在地图编辑器
落地的那一天变成 bug。写占位逻辑时至少把「这里假设了矩形」写进注释 ——
`zone.gd` 当年那句「后续地图编辑器只需要提供一张 zoneId 网格」把**替换点**标出来了，
所以这次改起来只动了两处；没标出来的那几处（渲染、tile_count）才是真正花时间的地方。

### 5.22 GDScript 判 JSON 数组的「形状」不能只看首项类型

`exists` 网格允许三种写法，`_read_exists()` 里最初这么判：

```gdscript
if typeof(first) == TYPE_INT or typeof(first) == TYPE_FLOAT:
    # 按行铺开的扁平数组
```

结果 `[[1,0],[1,1]]`（每行是数组）没问题，但**只有一行的写法和扁平数组分不开** ——
首项是数字时，`[(1,0),(1,1)]` 与扁平 `[1,1,0,1]` 长得一样，只看首项类型根本判不出来。

**正确做法**：先按「每行是不是一个**行容器**（Array 长度 == cols / String 长度 == cols）」判二维，
判不出来再当扁平数组（行优先）读：

```gdscript
if typeof(first) == TYPE_ARRAY or typeof(first) == TYPE_STRING:
    _read_exists_rows(data)   # 每一行自己是一个数组 / 字符串
    return
# 到这里是扁平数组：第 i 个元素 = 第 (i / cols) 行、第 (i % cols) 列
```

**顺带一条实测事实**：Godot 的 `JSON.parse_string()` 解析出来的**所有数字都是 `float`**
（`typeof()` 返回 3），不会自动变成 `int`。所以从 JSON 读进来的值一律要 `int(...)` 转换，
别写 `typeof(v) == TYPE_INT` 这种判断（永远为假）。

**还有一个「差点自己骗自己」的教训**：这一条最初是断言失败报出来的，而失败的真正原因是
**我把测试标签写反了**（`[1,1,0,0,1,1]` 的第 1 行是 `[0,1,1]`，不是 `[1,0,1]`）。
在 `_read_exists()` 里打一行 `print(data)` 才两分钟就看清了。**测试报红时先怀疑测试本身**，
但**验证方式必须是打印真实数据**，不是盯着自己的期望值反复推理。

### 5.23 ★★ tk 的 Treeview 在「新建 / 销毁」时就会派发 `<<TreeviewSelect>>` → 无限递归

**症状**（用户报的）：「点了地块按钮再点区块按钮，程序就无响应」（必现，且是真死循环不是卡慢）。

**实测栈**（`faulthandler.dump_traceback_later(8)` 打出来的，一眼就看清了）：

```
on_zone_select → refresh_sidebar → _build_zone_sidebar → ttk.Treeview(...)   ← 又回到新建控件
```

也就是：**点页签 → 重建侧边栏 → 新建 Treeview 的那一步，tk 自己派发了一次选区事件
→ 事件处理里又去重建侧边栏 → …** 无限递归，窗口再也不响应。

**为什么原来的 `_suppress_zone_event` 挡不住**：那个标志的语义是「**填充列表期间**别响应」，
它在 `tree.insert()` 循环之前置 True、循环之后置 False；而事件是在**建控件那一步**
（甚至在 `insert` 之前）就发出来的 —— 时机对不上。这类「用一个布尔挡事件」的写法，
只要事件的**触发时机**和控制流不完全重合，就一定会漏。

**修法（两层，都要）**：

1. `refresh_sidebar()` 里加**重入闸**（`_rebuilding`）：正在重建时再来请求直接返回；
2. `on_zone_select()` 里：`_rebuilding` 或 `_suppress_zone_event` 或「选中的还是同一个人」
   → 一律直接返回（不做任何事、**也不重建侧边栏**）。

**通用教训**：视图控件的**生命周期事件**（创建 / 销毁 / 映射 / 首次选中）不能当成
「用户操作」来响应。凡是「事件处理里会重建发出事件的那个控件」的形状，都必须有重入保护 ——
否则递归只在特定顺序下出现（这里是「先点地块再点区块」），本地随手一试经常试不出来。
`tests/test_app.py::t_zone_tab_with_real_map` 现在把这条钉住了（含手动触发那个递归事件）。

**顺带一条性能教训（同一批反馈的「有点卡」）**：界面卡不卡，先量再改。实测三件事最关键：
①鼠标事件回调整体**合并重绘**（拖动 100 个事件从 100 次全量重绘 → 1 次，2 秒 → 0 毫秒）；
②缩小时**别画上万个虚线格**（0.4 倍时 4000 格/20ms → 整张虚线网格/0.4ms；再小就不画）；
③**已经画了地块的格子不要再画虚线框**（画了也被盖住，纯浪费）。
数字与实测表在地图编辑器的 `README.md` 里。

### 5.24 ★★ 「有点卡」的元凶往往不是重绘，而是**每次点击把控件全重建一遍**

**背景**：需求是「操作上要像参考编辑器一样流畅」。画布那套重绘早就优化过了
（合并重绘 + 缩小不画格子），所以第一反应是「重绘应该没问题」——于是**先写基准再改代码**，
结果和直觉相反。

**实测（`tools/map_editor/bench_app.py`，1280×800，一次事件 = 回调 → 重绘 → `update_idletasks()`）**：

| 操作 | 耗时 |
|---|---|
| 画布全量重绘（空画布 721 图元 / 画满地 / 缩到 0.35 倍） | 2.2 ~ 6.4 ms |
| 拖动一帧、滚轮一次 | 2.9 ~ 3.1 ms |
| **左键点一下建一格（含侧边栏刷新）** | **18 ~ 31 ms（最坏 48 ms）** |

拆开看那一下：`refresh_sidebar()` 占 **22.7 ms**，其中真正「填地块属性那几个控件」只有 5.3 ms，
剩下 17 ms 是 `destroy()` 20 来个控件 + 重建 + 重新布局。**卡的是销毁/创建控件，不是画图。**

**修法（两条，缺一不可）**：

1. **能就地改值就别重建**：`refresh_tile_panel()` 只 `configure()` 那几个 label/button 的
   文字与颜色（19 ms → 3.6 ms）；只有「面板**结构**变了」——也就是
   「这一格从虚线格变成了有地块（或反过来）」——才转 `refresh_sidebar()` 整条重建。
2. **节流要贴着一帧定**：悬停高亮的重绘节流原来是 40 ms。既然一次重绘只要 3~5 ms，
   40 ms 就是白白让高亮落后光标两帧半（肉眼就是「框在追鼠标」）。定成 16 ms 后既跟手，
   重绘次数也没上去。**节流值要拿「一次重绘多久」来除，不能拍脑袋。**

**同族第二处（区块页，同一批改的）**：区块页一开始是「任何改动都 `refresh_sidebar()`」，
而重建那一页要**重新 new 一个 24 行的 `ttk.Treeview` 并逐行 insert** —— 实测一页 300+ ms。
于是「点一下地块划给区块」「在列表里换个区块」都卡。修法与上面同构：
`refresh_zone_panel()` 就地改那一行的名字/地块数 + 图例 + 详情，
**只有「行数变了」（加/删区块）才整条重建**。
顺带把 `set_page()` 加了「同一页直接返回」：点自己已选中的页签不该白重建一遍 ——
测试里「地块 ↔ 区块 来回切 3 轮」因此从 3.5~5.3 s（偶发超阈值）掉到 2.1 s。

**顺带修掉的一处观感 bug**：拖动平移时鼠标底下的格子一直在换，而 `hover` 还留着旧值 ——
于是画面里会画出一个**跟不上手的高亮方框**，一闪一闪。修法：开始平移（中键 / 空格）时把
`hover` 清掉。

**两个「基准程序本身」的坑（这次踩了，值得记）**：

- **`canvas.update_idletasks()` 必须算进计时**：tk 是**攒着**画图命令一起下发的，
  只调 `redraw()` 量到的是「把命令排进队列」的时间，不是「画到屏上」的时间 —— 差着一倍，
  很容易把 16 ms 的活量成 8 ms 然后觉得「没问题」。
- **假事件要带齐真实事件有的字段**：FakeEvent 少给了 `.delta`，`on_wheel` 会半路抛异常，
  于是整组滚轮数字全是假的（而且看着还挺快）。**基准跑出来「特别快」时先怀疑基准。**

**通用教训三条**：
1. **先量再改**：这次直觉（重绘慢）和实测（控件重建慢）刚好相反，按直觉改会白干一天。
2. **高频路径上不许整建整销控件**：`tk` 的 `destroy()` + 重建比画一千个图元还贵
   （Treeview 更贵，建行本身就要几百毫秒）。判断标准很简单 ——
   这个操作设计师一秒会做几次？会做几次的，就走「就地改值」。
3. **同一个不变量只在一个地方判**：面板「结构变了要重建」的闸门，一开始放在调用方
   （点格子的那一步），于是「右键删格 / 撤销 / 导入」都绕过了它，留下一个
   「按钮看着还能点、点下去没反应」的旧面板（`test_app.py` 当场抓住）。
   闸门挪进 `refresh_tile_panel()` 之后，所有调用点自动都对。

### 5.25 ★ 给编辑器加「阵营大本营」时，别自己发明一套阵营 id

**背景**：需求是「在上边栏加一个阵营页签，可以创建阵营并为阵营配置大本营地点」。
最省事的写法是编辑器自己编号（阵营 1、阵营 2…）再配个名字。这里没有那样做，
理由值得写下来：

- Godot 侧的阵营**已经是字符串**（`logic/faction.gd`：`player` / `p1`…`p8` / `enemy`），
  而基地、区块归属、索敌全都按这个字符串比。编辑器要是自己编号，就得维护一张
  「编辑器编号 ↔ 游戏字符串」的翻译表 —— 而**这张表一定会漂**（游戏加了 p9 呢？名字改了呢？）。
- 直接**用游戏那套字符串当 id** 之后，导出的 `faction_bases` 长这样：
  `{"player": [12,8], "p2": [4,4]}` —— Godot 按 id 直接查得到，
  **双方都不需要任何翻译**，`spawn_layout_for()` 只多了一句 `if faction_bases.has(faction)`。

**顺带定下的三条接口规矩**（都是「改一个字就静默出错」的地方）：

1. **新字段优先、旧字段当兜底**：`faction_bases` 里有这一方就用它，没有就退回原来的规则
   （主阵营用地图中心的 `base`、其他阵营按序号轮流用 `pvp_points`）。
   于是**老地图（没有这个字段）的行为一字不差** —— `test_smoke.gd` 里专门钉了这条。
2. **只在真的有阵营时才写新字段**：没有阵营的地图导出后与从前**逐字节一致**，
   这比「写一个空对象占位」重要得多（`test_model.py` 有断言）。
3. **一格只能是一方的大本营**：设给新阵营时从原来那方手里拿走。允许两方共用一格的话，
   Godot 里就是两座基地叠在同一格上，而且**没有任何报错**。

**顺带一条同类教训（同一批需求里的框选）**：批量操作要**一步一撤销**。
「选 12 格改地形」在撤销栈里压 12 次快照的话，用户按一次 `Ctrl+Z` 只退一格，
得按十二次 —— 那不是撤销，是折磨。做法很简单：整批操作**只 push 一次**快照，
循环改完再统一刷新界面（`batch_set_terrain` / `batch_set_zone` / `batch_delete_tiles`）。

### 5.26 ★★ tk 的鼠标事件不保证带修饰键位，也不保证发的是 `<B1-Motion>`

**症状（用户报的）**：「Shift + 鼠标左键拖拽选中一片格子」完全没有反应 ——
没有报错、也没有任何提示，就像那个手势不存在。

**实测出来的两件事**（都在真窗口上量的，不是推测）：

```
按下 Shift 之后再按鼠标：  ('down', state='0x0')   ← Shift 位根本没跟过来！
拖动期间发的是：          ('Motion', state='0x100') ← 带 B1 位，但走的是 <Motion> 绑定
```

1. **鼠标事件的 `state` 可以没有修饰键**：把 Shift 与鼠标事件分开送进 tk 时，
   `<ButtonPress-1>` 的 `state` 是 `0x0`。原来「Shift + 拖拽 = 框选」只看这个位，
   于是这一手势被当成普通拖拽 —— **静默失效**（用户看到的就是「没生效」）。
2. **拖动期间不一定发 `<B1-Motion>`**：带 B1 位的 `<Motion>` 走的是 `<Motion>` 那条绑定。
   原来的框选预览只更新在 `<B1-Motion>` 里，于是**预览矩形停在起点不动**
   （终点倒是对的，因为抬起时用的是当时的鼠标位置 —— 所以只看结果还以为没问题）。

**修法（两条都要）**：

- **Shift 从键盘事件跟踪**：绑 `<KeyPress-Shift_L/R>` / `<KeyRelease-Shift_L/R>` 维护
  `self.shift_held`，与鼠标 `state` 的位**取「或」**（任一说按住就算按住）。
  顺带处理「拖到一半松开 Shift」：把已经拖出来的矩形先落地，不留僵尸预览。
- **拖动分派放进 `on_motion`**：按 `state` 的 B1 位决定走「框选预览」还是「平移」，
  不再依赖 `<B1-Motion>` 一定会来。

**通用教训两条**：
1. **别把「修饰键状态」只挂在一个事件源上**：键盘、鼠标、焦点变化都可能丢信息。
   两个来源取「或」是廉价的保险，而漏掉的代价是一个**完全没反应**的功能。
2. **合成事件测不出这类 bug**：`event_generate(..., state=0x1)` 是我自己把位填进去的，
   它当然能过；`FakeEvent` 更是我想填什么就填什么。**这类问题的验证必须用真事件**
   （`event_generate` 不带 state 地发、或者人手点），并且**先怀疑测试造的事件是不是太理想**。
   这次「测试全绿但用户说没反应」的根因就在这里。

### 5.27 ★ 改了数据模型，就要回头把每一条校验的语义重读一遍

**症状（用户报的）**：`test_map.json` 里两个阵营的大本营都设好了，导出时仍弹
「大本营点位没设（Godot 会退回地图中心）」。

**根因**：这句话检查的是 JSON 里那个单数的 `base`（默认点位）。加了阵营大本营之后，
它的语义已经从「地图的出生点」变成「**某个没设大本营的阵营的兜底**」——
所有阵营都有自己的大本营时，Godot 的 `spawn_layout_for()` 根本不会看它。
于是这句警告既**不该出现**，文案也**是错的**（游戏不会退回地图中心）。

**修法**：`_base_problems()` 按「有没有人在用」来判：

| 情况 | 该不该提醒 |
|---|---|
| 没有阵营，默认点位没设 | 提醒（它是唯一出生点，老行为） |
| 有阵营、每方都设了自己的大本营 | **不提醒**（默认点位用不到） |
| 有阵营、有某一方没设（要靠默认点位兜底） | 提醒，并**点名是哪一方** |

**通用教训**：一个字段的语义变了，**所有读它的地方都要重读一遍** ——
尤其是「校验 / 警告 / 默认值」这几类：它们不参与主流程，测试也常常只钉主流程，
所以最容易留下语义过期的一句话。而**一句不该出现的警告比没有警告更坏**：
它会把用户带去改一个本来没问题的东西。

### 5.28 ★★ 「中立障碍」这种东西一出现，所有「谁是自己人」的判定都要重看一遍

**背景**：用户要「区划中心」——一格任何单位都进不去、无血量、无敌、没有攻击手段的建筑。
最省事的实现是把它做成一栋 `owner = ""` 的建筑：
`same_side(任何人, "")` 恒为 false，于是它**对谁都阻挡**，而且天然「不属于任何人」。

这一招很有效，但**每一处拿 `same_side` 当「是不是敌人」用的地方都变成了坑**：

| 位置 | 原来的写法 | 症状（实测） |
|---|---|---|
| `combat.nearest_enemy_building()` | `if same_side(b.owner, u.faction): continue` | 「不是自己人」= 敌人 → 将军把区划中心当敌方建筑，**一路走去「拆」它**；而它拆不掉，单位就永远停在那儿。表现是「点了移动，单位却往中心走」 |
| 箭塔索敌 | 同上 | 箭塔会对着一根拆不动的柱子开火 |
| 拆除命令 | 「不是自己人 → 拒绝」 | 这条**恰好**是对的（无主 = 拆不了），但那是碰巧，不是设计；所以补了一条显式的 `is_invulnerable()` 判断 |
| 建筑索敌的「最近」比较 | 只看距离 | 中心会参与比距离，把真正的敌方建筑挤掉 |

**教训**：引入「无主 / 中立」的建筑类型时，**不要**指望 `same_side` 的现有用法自动表达
「它不是敌人、只是障碍」——`same_side` 只能回答「是不是同一方」，回答不了「该不该打」。
`combat.gd` 现在统一用一条显式的守卫：

```gdscript
if String(b.owner) == "" or b.is_invulnerable():
    continue                      # 中立 / 无敌：不是可打的目标
```

**同步要记住的第二件事**：这类建筑一旦占格，**单位出生的站位规则必须避开它**。
`_ring_tile()` 原来只判「地形 + 建筑放行」，而区划中心是「对谁都放行不了」的格级阻挡，
所以 `passable()` 会挡住它 —— 但**预置建筑**（大本营 / 箭塔）对己方是放行的，
于是「站在大本营那一格上的亲兵」这种问题又出现了。现在的规则是：
**新出生的单位既避开「被别的单位占着」的格，也避开「那一格上有建筑」**。

### 5.29 ★★ 出生顺序：建筑要在单位之前就位

**症状**：开局有一个亲兵**卡在区划中心那栋建筑里**（`test_retinue` 抓到：
「亲兵没卡在不能站的建筑里：general-1-1」）。

**根因**：`world.reset()` 的顺序原来是「先建各阵营的基地与部队 → 再落区划中心」。
单位找站位时会避开**已经存在**的建筑，而中心那一刻还没建 —— 于是亲兵正好挑中了
中心那一格，中心随后压上去，两者重叠。

**修法**：把顺序改成

```
大本营 / 城墙 / 箭塔 → 地图预置建筑 → **区划中心** → 将领 + 亲兵 → 地图预置单位
```

并把「建某一方的部队」从 `apply_faction_layout()` 里拆出来（`spawn_faction_units()`），
在 `reset()` 里统一排在建筑之后调用。

⚠️ 还有一条**不能动**的契约：`world.units` 的**前几个永远是将领**（快捷键 `1/2/3`
与按序号取将领的代码都靠它）。所以顺序是「**先各方的将领与亲兵，再放地图预置单位**」——
反过来写（先放预置单位）会把前三个占掉，`test_retinue` 的「顺序契约」那条当场失败。

### 5.30 ★ 「改口径」的性能/行为优化，先想想它会不会让**另一条**机制失效

**背景**：敌人绕着一堵墙走的时候，直线距离会**先变大再变小**。而「挤不过去就认账」那套
（`jam_giveup_sec`）用的是「到终点的直线距离有没有变小」—— 于是绕路被误判成「卡住了」，
单位走一半就放弃（实测：敌人停在墙外三格，一次都没拆）。

第一反应是「那改用**沿路径还剩多少距离**」——听起来更准确。**但它把拥挤收敛搞坏了**：
每帧的推进都会让 `path` 变短一点点，`stuck_timer` 被一直清零，
12 个单位点到同一点后 **1200 帧都停不下来**（`test_arrival` 的四条断言全红）。

**结论（现在的选择）**：进度仍然用「到终点的直线距离」。
绕路那件事由另一条路解决 —— `update_combat()` 每 `repath_sec` 会重新寻路，
而 `move_to()` 会把 `best_dist` 复位。两条机制各管一段，比「一个更聪明的指标」安全。

**教训**：`jam_giveup_sec` / `settle_max_attempts` / `arrival` 这一套是**互相咬合**的，
牵一发动全身。改之前先跑 `test_arrival` —— 它存在的意义就是这个。

### 5.31 ★ 硬编码坐标的测试会被「地图上多了一样东西」批量打红

**背景**：加区划中心之后，13 个套件里同时红了 7 个、34 项断言。
逐条看下来，**没有一条是游戏逻辑坏了**，全是测试自己的假设过期：

| 假设 | 现实 |
|---|---|
| 「地图上 y=13 那一行是开阔地」 | 中心按 6×4 的规律摆在 (1,1)…(21,13)，**y=13 正好是中心行** |
| 「(5,13) 上没有建筑」 | 那是 C2 的中心 |
| 「大本营周围 8 格里能建满一圈墙」 | 其中一格被中心占了 |
| 「拆完自己点名的墙之后 `target_building` 会是空」 | 旁边对家据点的墙在警戒半径内，自动索敌立刻锁上它 |
| 「驻守单位 5 秒内不会动」 | 它旁边就有敌人，`hold_position` **只管推进 AI，不管迎战** |
| 「敌人会走到墙边开始拆」 | 它半路被玩家的箭塔打死了（那是正确行为） |

**处理原则**（也适用于以后加任何「地图上默认存在的东西」）：

1. **先判断「这是逻辑坏了还是测试假设过期了」** —— 用探针脚本打出真实状态，别猜。
   这一轮花了很久在几个「看起来像 bug」的现象上，其中只有 3 个是真 bug
   （索敌把中心当敌人、出生顺序、编辑器撤销时机）。
2. **测试要挑干净的场地**：能用动态查找（`_find_free_tile`）就别写死坐标；
   实在要写死，就挑一行**没有障碍**的（这轮统一挪到了 `y = 14`）。
3. **要验 A，就把 B 关掉**：验到达与推挤就 `combat_enabled = false`；验城墙就先把
   地图自带的塔与墙摘掉；验箭塔就先把别的塔摘掉。**在测试里写清为什么**，
   否则下一个人会以为那是随手加的。
4. **给「干扰源」写一个共用的辅助函数**（`_clear_zone_centers()` / `_remove_buildings_of_type()`），
   别在每个用例里手搓一遍 —— 手搓的版本迟早会漏掉一处。

### 5.32 ★★ 「Shift 框选又失效了」：5.26 只修了一半（焦点会跑）

**症状（用户第二次报的）**：「编辑器里 Shift + 鼠标左键拖动选中多个格子**又**失效了」。
5.26 修过同一个手势（鼠标 `state` 不带修饰键 + `<B1-Motion>` 不保证发），当时测试全绿。
这次复现出来的是**另一条路**：

```
先在侧边栏点一下（按钮 / 下拉框 / 区块树都会把键盘焦点留在那边）
→ 再按住 Shift 拖画布
→ Shift 的 KeyPress 送给了侧边栏那个控件
→ 画布上的 <KeyPress-Shift_L> 绑定**根本不响**
→ self.shift_held 还是 False
→ 又赶上鼠标事件不带 Shift 位（5.26 那条）⇒ 两条来源一起失效，框选静默不生效
```

**根因**：tk 的键盘事件**只送给「当前有焦点的那个控件」**，再沿父链冒泡。
5.26 把 Shift 绑在 **canvas** 上，等于假设「画布永远有焦点」——而这是错的：
`takefocus=0` 只挡 Tab 键遍历，**挡不住鼠标点击拿焦点**。

**修法**：Shift 的按下 / 松开绑到 **root + canvas 两处**（`_bind_shift_keys()`）。
root 是冒泡的最后一站，焦点在哪个子控件上都会经过它。

**为什么老用例测不出来**（这条比 bug 本身更值得记）：

```python
editor.on_shift_down()        # 直接调回调 —— 绕过了「事件到不到得了」这一层
editor.on_left_down(fake_mouse(..., shift=False))
```

老用例（`t_shift_drag_survives_missing_state_bit`）是**直接调回调**的，
它验的是「回调写了没写对」，而 bug 出在「回调压根没被调用」。
**依赖焦点 / 事件路由的功能，必须走真实事件（`event_generate`）+ 先把焦点摆到出问题的地方。**
新用例 `t_shift_drag_after_sidebar_click()` 就是这么写的，
并且实测过「把 root 那份绑定去掉它就红」。

**通用教训**：
1. **「只绑一个控件」的键盘逻辑，先问一句「焦点会不会跑到别处」** ——
   尤其是编辑器这种「画布 + 侧边栏 + 树 + 输入框」的布局。
2. **同一个症状报告第二次出现时，不要假设上次的修复是对的** ——
   上一轮修的是「信息丢了」，这一轮是「事件根本没送到」，两条完全不同的路。
3. **测试要复现「用户的操作顺序」**（先点侧边栏、再拖画布），
   而不是复现「我以为的操作顺序」（一上来就拖画布）。

### 5.33 ★★ 地图是「设计师手里的活文件」：它在编辑器里被改一次，Godot 测试就红一片

**症状**：跑 Godot 全套突然红了 14 条（6 个套件）。看断言名字像是「地图坏了」，
但打开 `data/test_map.json` 一比才发现：它**被地图编辑器重新导出过** ——
从 17×22 / 374 地块 / 10 区块变成了 **27×22 / 594 地块 / 14 区块**（多了 f1/f2/g1/g2），
玩家大本营也从 (2,2) 挪到了 (7,2)。

**为什么一改就红一片**：测试里散着一批「写死坐标 / 写死数量」的假设：

| 写死的东西 | 换图之后的样子 |
|---|---|
| `EXPECTED_MAP_COLS := 17` | 27（这条是**故意**写死的，它要能抓住「图被换了」） |
| 「(2,2) 是玩家大本营」 | 变成 (7,2) |
| 「地图里正好 10 个区块」 | 14 |
| 「第 9 行的满墙 ≥ 24 段」 | 该行有 27 格，但要排除已被占的格 |
| 「y=13 那一行没有障碍物，可以量直线」 | 新区块的中心挪到了别处 |
| 「整队走 8 格以内，600 帧内该停」 | 出生点离目标更远，实测 694 帧 |

**处理原则**（换图 / 加区块时照着做）：

1. **先分清「逻辑坏了」还是「测试假设过期了」**：用探针把真实状态打出来
   （这一轮 14 条里**一条真 bug 都没有**，全是假设过期；唯一的真问题是下面 5.34 的用例隔离）。
2. **能用「地图自己说的数」就用它**：区块数 = `zones_names.size()`、
   大本营 = `faction_bases[阵营]`、满墙段数 = 该行「可通行且没被占」的格数。
3. **只有一处该写死**：`test_smoke.gd` 的 `EXPECTED_MAP_*` —— 它的作用就是
   「地图被换掉了要有人喊一声」。写死的地方要写清**为什么**。
4. **改完图记得两边都跑**：`run-tests.ps1`（Godot）+ `test_model.py` / `test_app.py`（编辑器）。
   编辑器的用例里也有「374 个地块 / 10 个区块」这种数，同样会红。

**通用教训**：**测试断言的事实，如果它属于「数据」而不是「规则」，就要从数据里读** ——
写死的坐标本质上是把「当时的某一张地图」固化进了测试，换图就是一次集体假失败。

### 5.34 ★★ 战斗会**合法地**把单位从「移动命令」上拉走（测试隔离的坑，第二次）

**症状**：`test_retinue` 的「整队一起走到目标」报「整队都到达了目标附近（3/4）」。
看着像移动坏了，实际上有一个亲兵**被巡逻兵拽去追击**了：

```
n=235  goal=(6.5, 13.5)      ← 原本的移动目标
n=240  goal=(10.96885, 9.749427)   ← 变成「敌人所在的位置」（combat.update_combat → move_to）
n=...  追丢之后就地停住，离目标 8.2 格
```

`combat.update_combat()` 在「够不着目标」时会 `move_to(敌人的位置)` 去追；
敌人被打死 / 走出警戒之后，那次追击就结束了 —— 单位停在半路，**它原来的移动命令已经被覆盖**。
这是**正确**的游戏行为（追击优先），但这一节验的是「一条 move 命令同步给整队」，
不该被巡逻兵搅进来。

**修法**：验纯移动的用例先把「会打架的东西」清干净：

```gdscript
cfg.combat_enabled = false
w.units = _keep_player_units(w)      # 只留玩家这一方，清掉地图预置的守军 / 巡逻兵
```

**为什么以前不红、换图之后才红**：老图上那两个巡逻兵朝北推进，**不经过**这队人要走的路线；
新图（27×22，玩家大本营在 (7,2)）上它们正好穿过 —— 同一个「5.4 测试被正确的防守行为骗了」
的坑，换一张地图就又冒出来一次。

**通用教训**：
1. **「会自己动的东西」都要先清场**：敌人、巡逻兵、会推进的 AI。
   只 `combat_enabled = false` 不够 —— 那是关掉「索敌」，不是关掉「地图上有人」。
2. **失败信息说的是「3/4 到达」，根因却在 combat** —— 遇到「看起来像 A 坏了」的失败，
   先把**那个单位**的 `goal` / `moving` / `target` 按帧打出来，别盯着 A 看。
