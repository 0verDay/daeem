| # | 系统 | 一句话 | 主要落点 | 验收 |
|---|---|---|---|---|
| 1 | **投影数学** | 逻辑格**一格不改**，只把「格 → 屏幕像素」换成 `(x·cell, y·cell·S)`，S ≈ 0.62 | `view/palette.gd`（唯一换算入口） | 无头断言：投影正逆、格矩形尺寸、压扁系数 |

### 1.3 为什么是「纵向压扁」而不是「斜 45° 等距」

- 本项目的地图数据、寻路、区划、雾、占领判定**全部建立在正放方格上**（`data/maps/<id>/map.json` 的
  `terrain` / `zones` / `exists`，`logic/grid.gd` 的四方向 + 八方向方向集）。
- 斜 45° 等距会让「格」变成菱形：`zone_view` 的按格轮廓、`fog_view` 的 1 像素 = 1 格掩码贴图、
  `overlay` 的建造预览矩形、`input_controller` 的框选矩形、格心换算**全都要重写**，
  而且要吃「菱形拼贴缝」「按菱形裁切」这类新的渲染坑。
- 纵向压扁是**同一个坐标系下的仿射变换**：格仍是格、相邻关系仍是四邻/八邻、
  所有「按格画矩形」的代码天然通过。**这是本次能用最小代价拿到「饥荒式俯角」观感的唯一路径。**
- ⚠️ 代价（必须写清楚，避免以后误判）：压扁**不会**带来真正的高度。
  建筑挡住单位靠的是 **Y 排序**（脚点前后），不是三维遮挡；森林里没有树冠挡住单位。

### 1.4 与既有规划的关系

- route.md 第 2.2 节拍板「纯 2D 俯视」时留下的话是：「**回头改的时机**：玩法验证通过、开始做正式美术时。
  届时**逻辑层不动**，只换 `view/`。」—— 本文就是那次回头，**口径完全一致**。
- route.md 第 2.2 节列的「第 3 轮及以后 —— 换 2.5D/3D 美术（只动 `view/`）」= 本文的落实。
- `docs/README.md` 的「占位美术：圆 = 单位、矩形 = 建筑……**换 2.5D/3D 时只动 `view/`**」同源。

## 二、投影数学（本文的地基，只有这一节是新东西）

### 2.1 两套「像素」的区分（★ 最容易出错的地方）

| 名字 | 定义 | 谁用 | 例子 |
|---|---|---|---|
| **逻辑坐标（格）** | `(0,0)` = 地图左上角，一格 = `1.0` | `logic/` 全部、`data/maps/*.json` | `u.pos = (12.35, 7.80)` |
| **世界像素（压扁）** | `world_x = x·cell_px`、`world_y = y·cell_px·S` | `view/` 全部（`Camera2D`、节点位置、`_draw`） | `cell_px=128, S=0.62` ⇒ 一格是 `128 × 79.4` 的矩形 |
| **小地图像素** | 等比缩放 + 居中，**轴等比** | `view/minimap.gd` | 见 6.3 |

- ★ **压扁只发生在「格 → 世界像素」这一步**。`logic/` 里永远没有 `S`，也没有 `cell_px`
  （architecture.md 第五节 / palette.gd 文件头的铁律，这一条**不动摇**）。
- ★ 因此「世界像素」不再等于「逻辑 × cell_px」：**凡是自己写 `x * cell_px` 的地方都要改**
  （只允许出现在 `palette.gd` 与 `input_controller` 的拾取半径换算里，见 4.6）。

### 2.2 正向与逆向

```gdscript
# view/palette.gd（改造后的口径，示意）
## 逻辑坐标（格）→ 世界像素（已压扁）
static func to_px(p: Vector2, cfg) -> Vector2:
    return Vector2(p.x * cfg.cell_px, p.y * cfg.cell_px * cfg.render_squash)

## 世界像素（已压扁）→ 逻辑坐标（格）—— 只给输入换算用
static func to_logic(px: Vector2, cfg) -> Vector2:
    return Vector2(px.x / cfg.cell_px, px.y / (cfg.cell_px * cfg.render_squash))

## 一格在世界像素里的矩形
static func tile_rect(tx: int, ty: int, cfg) -> Rect2:
    return Rect2(Vector2(tx * cfg.cell_px, ty * cfg.cell_px * cfg.render_squash),
                 Vector2(cfg.cell_px, cfg.cell_px * cfg.render_squash))
```

- ★ 逆变换与正变换**必须成对**（`to_logic(to_px(p)) == p`），并且**要有断言** ——
  HTML 版就是栽在「绘制用一套、鼠标换算用另一套」，见 pitfalls 3.1。
- ⚠️ 单位半径（像素）保持 `cfg.unit_radius_of(type) * cfg.cell_px`：
  它在**逻辑上是圆的**，压扁由父变换负责（屏幕上看成椭圆，物理上正确）。
  **不要在 palette 里给它乘 S** —— 那会让「点选判定」与「画出来的形状」各说各话。

### 2.3 为什么用「父节点 scale」承载压扁（而不是每处手乘 S）

```gdscript
# view/game_scene.gd
var content_root: Node2D = null   # 世界内容全部挂在它下面

content_root = Node2D.new()
content_root.name = "ContentRoot"
content_root.scale = Vector2(1.0, cfg.render_squash)   # ★ 压扁只有这一处
content_root.y_sort_enabled = true                     # ★ 深度排序的开关也在这里
add_child(content_root)
# 地形 / 区划 / 建筑 / 单位 / 迷雾 / 覆盖层 全部 add_child(content_root)
# 相机仍然是 game_scene 的直接子节点（在 content_root 之上，不受压扁影响）
```

理由三条，每条都对应一个具体后果：

1. **输入零改动**：`Camera2D.get_global_mouse_position()` 内部就是
   `get_canvas_transform().affine_inverse() * 屏幕点`，而 `get_canvas_transform()` 天然包含
   内容节点的变换 ⇒ `input_controller` 拿到的**已经是压扁后的世界像素**，
   `to_logic()` 一换，屏幕点 → 格子全对。**不自己手算一遍**（camera_rig 文件头那条铁律）。
2. **视觉正确性免费**：`sprite / tile / 图形` 在非均匀缩放下被父变换拉伸，
   不需要逐个改绘制参数；节点位置也只要写压扁后的坐标。
3. **剔除免费**：`unit_view._visible_rect()` 走 `get_global_transform_with_canvas().affine_inverse()`，
   它同样包含父变换 ⇒ 屏幕外剔除在新投影下自动仍然正确。

⚠️ **两个已知的副作用**（各自有对策，见第四节）：

- **线宽、圆、字被一起压扁**：`draw_arc` 画出来是椭圆、`draw_line` 细了 38%、`draw_char` 变成扁字。
  对策 = 局部反向补偿变换（4.2 / 4.3）。
- **`Camera2D.zoom` 与屏幕像素的比例关系变了**：不是错，是「世界像素」的定义变了 ⇒
  镜头参数要按 6.1 重新核一遍。

### 2.4 压扁系数 S 的建议值

| S | 观感 | 备注 |
|---|---|---|
| 1.00 | 现状（正俯视） | 保留为「关掉 2.5D」的回退开关 |
| **0.62** | **推荐**：与饥荒的俯角接近，地块仍认得出是「方格」 | 一格 `128 × 79.4` px；横向视野完全不变，纵向可见格数 ×1.61 |
| 0.55 | 更「平」，纵深更强 | 字 / 血条竖向空间更挤，`UNIT_R` 一类判定要重新看 |
| ≤ 0.45 | 不推荐 | 一格比单位图标还扁，双击与框选手感开始变差 |

★ `S = 0.62` 是**起点**，不是结论：第八节的看图环节要人工确认，必要时只改 `config.json` 一个数。

## 三、逐文件改动清单（★ 一表看全，`logic/` 一栏为空是故意的）

### 3.1 `data/config.json`（新增 `render.*`，并进 `config.gd` 的 `_cache_scalars()`）

| 键 | 建议值 | 含义 | 缺了怎么办 |
|---|---|---|---|
| `render.cell_px` | `128`（不变） | 一格的世界像素**宽** | 已有 |
| `render.screen_squash` | `0.62` | ★ 唯一的压扁系数 S | 缺省 = 1.0（= 完全等于改造前） |
| `render.depth_sort` | `true` | 是否开 Y 排序（关掉 = 全平铺，便于二分定位问题） | 缺省 = true |
| `render.glyph_squash_compensate` | `true` | 字 / 血条 / 标记是否反向补偿（关掉 = 可看到「不补偿长什么样」） | 缺省 = true |
| `render.minimap_squash_view` | `true` | 小地图的视野框是否画成压扁后的形状 | 缺省 = true |

- ★ **必须走 `_cache_scalars()` + `cfg.render_squash` 字段**（architecture.md 铁律 7）：
  这个数出现在**每格、每单位、每帧**的内层循环里（`to_px` / `tile_rect`），
  用 `cfg.num("render.screen_squash")` 就是每帧几万次 `split(".")`。
- ⚠️ 载入之后 `cfg.data` 不再是权威；测试要改开关请直接改字段
  （`cfg.render_squash = 1.0`）—— 与 `cfg.path_diagonal` 那条同源。

| `start_screen.gd` / `main.gd` / `menu_*.gd` | **不动** | 菜单不含世界内容 |

## 四、难点与对策（每一条都写清了「踩了会怎样」）

### 4.1 难点一：字被压成扁片

- **症状**：格宽 128、S = 0.62 时，「枪」字竖向只剩 62%，笔画黏在一起；两栏数字更糊。
- ⚠️ 这是**必然会发生的**，不是可能：父节点的 scale 会一视同仁地作用到 `draw_char` 上。
- **对策**：在**局部**套一层反向变换，让「补偿组」的绘制在压扁空间里按 `1/S` 放大，
  经父变换抵消后回到屏幕 1:1：

```gdscript
# view/unit_view.gd（示意）——补偿组：字 / 血条 / 选中光晕 / 标记
var inv: float = 1.0 / maxf(1e-6, cfg.render_squash)
self.draw_set_transform(p, 0.0, Vector2(1.0, inv))   # p = 该元素的世界锚点
# ↓ 这一组里的所有坐标都写成「以 p 为原点的逻辑像素」，与改造前的数字完全一样
UnitIconRes.draw_char_at(self, _font, ch, Vector2.ZERO, radii[i])
self.draw_set_transform(Vector2.ZERO, 0.0, Vector2.ONE)   # ★ 画完必须复位
```

- ★ **`draw_set_transform` 必须复位**（否则后面所有图元都会歪）。复位只写一次、只在一处，
  建议抽成 `_compensated(anchor, squash)` / `_reset_transform()` 一对，避免漏。
- ⚠️ 线宽也要一起补偿：`draw_line(p, q, col, 2.0 / S)` —— 否则所有描边都细 38%。
- ★ 补偿是**逐元素**的（不同锚点），所以它天然把「同贴图合批」拆散。
  代价评估：补偿组里只有字、血条、标记这几类，**圆盘与地形仍在压扁组**（大头）；
  但 `unit_view` 的「分组绘制」顺序必须重新排过（见 4.3），别把这轮改造做成一次性能回归。

### 4.2 难点二：圆与弧变成椭圆

- **症状**：`overlay` 的移动绿圈、攻击红圈，`building_view` 的区划中心菱形与中心圆点，
  `unit_view` 的选中光晕（那张圆盘贴图）全部压成椭圆。
- **对策分两类**（★ 这一条是**观感口径**，要用户拍板，见 11.2）：
  - **「地面上的东西」（俯视 = 椭圆）**：建造预览矩形、区划中心菱形、区划轮廓线 —— **保持椭圆 / 保持压扁**。
    理由：它们画的是「地面上的范围」，压扁才与地面一致（饥荒里地上的影子也是椭圆的）。
  - **「屏幕上的 UI 标记」**：移动绿圈、攻击叉、选中光晕、调试准星 —— **走补偿，保持正圆**。
    理由：它们是给玩家的界面反馈，不是世界里的物体。

### 4.3 难点三：深度排序与绘制批次互相拉扯

- **现状**（必须尊重的既有性能约定）：`unit_view` 是「**一个 CanvasItem 画全部**」，
  并且**按图元类型 / 按贴图分桶**才合得上批（1000 单位下 `draw_circle ×1000` = 997 draw call / 18.4 ms，
  换贴图后合成一个批次 —— 见 unit_view.gd 文件头与 pitfalls 5.50）。
- **2.5D 想要的**：建筑与单位之间**按脚下 Y 排前后**（绕城墙走时人要挡住墙）。
- **冲突**：Y 排序是**节点级**的（`Node2D.y_sort_enabled` 按子节点的 Y 排序并隔离绘制），
  而「一个节点画全部单位」意味着所有单位只能整体压在建筑之上或之下，**没有中间态**。
- **对策（推荐）**：**建筑进排序空间，单位整体压制** ——
  1. `content_root.y_sort_enabled = true`，它的子节点按 Y 排序；
  2. 地形 / 区划 / 迷雾用 `z_index` 固定在最底（`-100 / -50 / +15` 那一套口径不变）；
  3. `building_view` 的**每个 `BuildingBox` 节点**（已经在树里了）参与排序，位置改用**脚下点**；
  4. `unit_view` 是**一个**节点：它要么整体在所有建筑之前、要么之后。
     ★ 取「单位整体后画（压在建筑之上）」这一档 —— 代价是「单位在建筑北侧时不会被子挡住」，
     好处是 1000 单位的合批与 6 ms/帧的预算**完全不动**。
- **何时该升级到「逐单位排序」**：当「单位被建筑挡住」成为必须的观感时，
  方案是「按行分块」——把单位按 `ty` 分成 N 条带（每条带一个 CanvasItem，插到对应 Y 位置），
  条带内部的合批仍然成立。**这一轮不做**（见 11.4 的拍板项），成本与收益都写在第十一节。
- ★ 无论选哪一档，**「每帧 queue_free + new 重建」是禁止的**（pitfalls 2.3）。

### 4.4 难点四：小地图与主视图不再同比例

- **症状**：主视图压扁后，屏幕上实际覆盖的世界区域是「更方」的一块；
  小地图若仍画正俯视的等比视野框，框里装的地形与玩家看到的**对不上**（既有断言会红）。
- **对策**：小地图**地形 / 建筑 / 单位保持正俯视等比**（RTS 里更好读，与饥荒的大地图习惯一致），
  只把**视野框**画成真实覆盖区（非等比矩形）。
  - `view_rect_world()`（世界像素）→ 除 `(cell_px, cell_px·S)` 得逻辑格尺寸 →
    乘小地图 `scale` → 得到非等比矩形；
  - `to_minimap` / `to_world` **一个字都不改**（它们是「世界格 → 小地图像素」，与主视图投影无关）。
- ★ 这样「视野框 = 屏幕上真正看到的区域」这条契约仍然成立，且与小地图地形成比例一致。

### 4.5 难点五：`S` 出现在内层循环里

- `to_px` / `tile_rect` 被**每格每帧**调用（地形 594~10000 格、单位 1000 个、区划轮廓缓存除外）。
- ★ 所以：`S` 必须来自 `cfg.render_squash`（载入时算好的字段），
  **不许** `cfg.num("render.screen_squash")`、**不许** `Vector2(1, S)` 现构造再除。
- ⚠️ 更狠的一条：`unit_view._draw()` 里现在是 `u.pos * cell_px` **内联**的
  （注释明确写了「不再每单位调一次 `PaletteRes.to_px`」）。
  压扁之后要么保持内联为 `Vector2(u.pos.x * cell_px, u.pos.y * cell_h)`（推荐，两个局部变量），
  要么接受每单位一次静态函数调用 —— **两者择一，别两处各写一套口径**。

### 4.6 难点六：拾取判定与画面不一致

- 点选单位用的是「世界坐标距离 < 逻辑半径 + `unit.hit_pad` 像素」。
- 压扁之后，屏幕上单位是**椭圆**，而判定仍是**圆**：
  在格的 y 方向上，玩家的点击容差实际被放大了 `1/S ≈ 1.61` 倍。
- **对策**：把 `hit_pad` 的像素换算改成「屏幕像素口径」：
  判定圆在压扁空间里的 y 半径 = `逻辑半径 × cell_px·S + hit_pad`，
  x 半径 = `逻辑半径 × cell_px + hit_pad`（即判定也变成椭圆，与看到的形状一致）。
  ★ 落点只有 `input_controller._pick_*_at()` 那三处（实测已集中）。
- ⚠️ 这一条**必须写断言**（见 8.2），否则「看着能点到、实际点不到」这类手感 bug 会一直存在。

## 六、镜头、比例与数值（要重核的那几个数）

### 6.1 视野契约：水平方向一个格都不变

- 现状记录（config 的 `camera._comment`）：1920×1080、`cell_px = 128` 时
  - `zoom 1.6`（最紧）→ 可见 **9.4 × 5.3 格**
  - `zoom 0.8`（最远）→ 可见 **18.8 × 10.5 格**
- 压扁把世界高度乘了 `S`，而 `zoom` 是**等比**的 ⇒ 可见宽度（格数）**完全不变**，
  可见高度（格数）变成 `5.3 / S` 与 `10.5 / S`：
  - `S = 0.62` 时 → 最紧 **9.4 × 8.6 格**、最远 **18.8 × 16.9 格**。
- ★ 结论：**`min_scale / max_scale / start_scale` 一个都不用改**，
  横向上限与「视野大小锁在区间里」这条需求完全保持；
  纵向上看到更多行是压扁的**几何后果**，不是参数漂移。
- ⚠️ 要改的只有 `camera_rig.map_size()`：从 `(cols, rows) * cell_px` 改成
  `(cols * cell_px, rows * cell_px * S)` —— 否则相机夹取（「地图边界点到屏幕中心」那条契约）
  在纵向上会多出 `1/S` 的空白。
- ⚠️ `fit_to_map()` 的注释里写着「F 键现在等价于拉到最远」。压扁后这个结论可能翻转
  （地图世界高度变小 ⇒ fit 需要的倍率变大）。**核对一次**并在注释里写清新的结论。

### 6.2 比例与观感

| 项 | 现状 | 压扁后 | 说明 |
|---|---|---|---|
| 一格 | 128 × 128 px | 128 × 79.4 px | 横向不变 |
| 单位半径 0.1 格 | 12.8 px 圆 | 12.8 × 7.9 px 椭圆 | 物理上正确；觉得太小就调 `unit.types.*.radius`（**那是玩法数值，要单独拍板**） |
| 字（`FONT_SCALE = 1.5`） | ≈19 px | 仍 ≈19 px（补偿后） | 不补偿则 11.9 px，必糊 |
| 建筑本体 | 按 `body_scale` 内缩的方格 | 压扁成扁方格 | 占位阶段可接受；**以后要「伪高度」**（见 7.2） |

### 6.3 小地图的两套比例（写清楚，免得以后再算一遍）

- 小地图地形：`scale = min(W/cols, H/rows)`（**轴等比**，只跟格数有关）→ **不动**。
- 主视图覆盖区（逻辑格）：`w = vp.x / (zoom · cell_px)`、`h = vp.y / (zoom · cell_px · S)`。
- ★ 也就是说：压扁让玩家在**同样宽**的屏幕上看到了**更多行**，
  小地图的视野框会相应地**更高**（而不是更方）。这一条要有断言。

## 七、明确不做的事（写下来是为了防「顺手做了」）

### 7.1 本轮不做

1. **不做斜 45° / 等距 / 旋转**（用户选 A）。
2. **不做俯角滑杆与四向旋转**（用户选「固定角度」）。
3. **不做真正的 3D 或多层高度**：`logic/` 里没有、也不会加「高度」字段。
4. **不改美术资源管线**：不引入图集、序列帧、`.import` 配置。
5. **不动 `data/maps/*.json` 与两个 Python 编辑器**（地图编辑器仍按正放方格工作）。
6. **不动 HUD / UI 布局与流程**（菜单、战役、设置、悬停面板）。

### 7.2 以后可以考虑（记下来，别现在做）

| 项 | 一句话 | 依赖 |
|---|---|---|
| **伪高度** | 给建筑 / 单位在屏幕 y 方向加一点「立面」（本体上沿往上抬几像素），并在脚下画椭圆影 —— 立刻更像 2.5D | 需要「视觉高度」数据（放 `config.json` 的 `render.fake_height.<type>`，**不进 logic**） |
| **森林 / 山体的体积感** | 现在它们只是配色不同的平地；给它们格内画「树冠 + 树影」并参与 Y 排序，才有「林子挡住人」 | 需要「地表装饰物」这一层（放在 `terrain_view` 之后、`building_view` 之前，且要能参与排序） |
| **逐单位排序** | 单位按 `ty` 分条带，条带各自一个 CanvasItem 插进排序空间（4.3 的升级路径） | 需要先量清「条带数 × 每带节点」对合批的影响 |
| **投影落进地图编辑器** | 让 `tools/map_editor` 也能用压扁视角预览（与游戏内所见一致） | 地图编辑器是独立 Python 工具，成本独立 |

## 八、断言与验收

### 8.1 无头断言（`tools/run-tests.ps1`，靠退出码判成败）

| 断言 | 在哪个文件 | 判据 |
|---|---|---|
| 投影正逆一致 | `test_view.gd` | `to_logic(to_px(p)) ≈ p`（含非整数点） |
| 格矩形尺寸 | `test_view.gd` | `tile_rect(...).size == (cell_px, cell_px · S)` |
| ★ **回退等价** | `test_view.gd` | `S = 1.0` 时，`to_px / to_logic / tile_rect` 的结果与改造前**逐位一致**（用同一组样例点） |
| 内容根挂载 | `test_view.gd` | 世界内容在 `content_root` 之下、相机**不在**它之下、`content_root.scale.y == S` |
| HUD 不受影响 | `test_ui.gd` | HUD 各面板几何期望值**一个字不改**仍然通过（HUD 不在 `content_root` 之下） |
| 补偿是逆 | `test_view.gd` | 补偿后的竖直尺寸 × S == 目标屏幕尺寸（数值断言，不画东西） |
| 排序键口径 | `test_view.gd` | 建筑节点的 y == 它那一格**底边**的世界 y |
| 掩码矩形 | `test_fog.gd` | 一次 `draw_texture_rect` 的目标矩形 == `(cols, rows·S) · cell_px` |
| 小地图视野框 | `test_minimap.gd` | 主视图覆盖的格数 × 小地图 `scale` == 框的像素尺寸（两轴分别验） |
| 拾取一致性 | `test_view.gd` 或 `test_ui.gd` | 屏幕点落在「画出来的椭圆」内 ⇒ 一定选中该单位；落在它外 ⇒ 一定不选 |

⚠️ **无头测试的一条硬限制**（pitfalls 5.50 已经吃过一次）：
`_draw()` 内部的错误**不会**让测试失败。所以一切「画出来了没有 / 画了几次 / 画在哪个矩形」
都必须留下**可数的痕迹**（`icon_draw_count` / `icon_disc_count` / `draw_count` 那套），
★ 本轮新增的「补偿组」也要有自己的计数器。

### 8.2 手玩验收清单

1. **位置对齐**：进游戏第一眼，地形格、区划轮廓、建筑、单位、移动绿点**都在它们该在的地方**。
2. **输入对齐**：鼠标悬停任意一格 → 建造预览框正好套住那一格；按 G 的调试准星红叉/绿圈重合。
3. **单位可读**：字不变形、血条是正常粗细、选中光晕是正圆、朝向线看得出来指哪。
4. **深度关系**：把一支部队开到城墙 / 箭塔的北侧与南侧各一次，观察前后遮挡是否符合直觉。
5. **镜头端点**：滚轮到最远 / 最近、方向键平移、边缘滚屏、F 键、Home 键、小地图点击与按住拖动。
6. **迷雾**：没视野的区域仍然整片变暗，且**格子边界随压扁一起变形**（不是一张正方形灰布）。
7. **区划**：占领进度条仍然从底往上长、名字仍然在左上角且**没被压扁**。
8. **UI 零影响**：底栏、命令卡、悬停面板、页签、小地图控件本身**与改造前完全一样**。

## 九、量尺（性能预算不许被这轮改造吃掉）

- 既有基线（记在 `tests/bench_crowd.gd` 的注释里）：**1000 单位、100×100 图**
  - 逻辑 **≈5.9 ms/帧**（目标 ≤6 ms）
  - 实机（开窗、关垂直同步）**68.6 fps（p95 65.5）**
- 本轮要盯的三件事：
  1. **压扁变换本身**：父节点 scale = 零额外开销（不进 GDScript 内层循环）。
  2. **补偿组的 draw call**：字 / 血条本来就按字号分桶，补偿只改变换 → 预期影响很小，
     但 `draw_set_transform` **会打断合批**，所以要**实测**而不是推断。
  3. **Y 排序**：`y_sort_enabled` 只对 `content_root` 的直接子节点排序（地形/区划/建筑/单位/迷雾/覆盖层
     ≈ 上十个节点 + 每栋建筑一个节点，这张图上不到 30 栋）⇒ 预期可忽略。
- ⚠️ 读数字的顺序**不变**（pitfalls 1.6）：先看 `machine drift`（>1.3 就作废），
  再看 `frame buckets`（卡顿感来自长帧），再看分项峰值，最后才看平均。

## 十、风险与回退

| 风险 | 概率 | 后果 | 对策 / 回退 |
|---|---|---|---|
| 补偿变换漏复位，后续图元全歪 | 中 | 画面错乱、且**不一定报错** | 抽成一对函数；新增计数器；看图清单第 3 条 |
| `draw_set_transform` 打散合批 ⇒ 帧率劣化 | 中 | 1000 单位场景掉帧 | M4 实测；必要时把「补偿组」缩到只有字 + 血条 |
| Y 排序让建筑绘制从「批量」变成「逐节点」 | 低 | 建筑多时开销上升 | 建筑本来就是一个节点一栋；`render.depth_sort` 可一键关回平铺 |
| 压扁后单位太小 / 太挤，手感下降 | 中 | 观感不达预期 | 只改 `render.screen_squash`（0.55~0.75 之间扫一遍）；**不动逻辑半径** |
| 拾取椭圆口径没对齐 | 中 | 「看着点得到、实际点不到」 | 8.1 最后一条断言钉住 |
| 有人顺手把 HUD 挂进 `content_root` | 低 | 整个 UI 被压扁 | `test_ui` 期望值不变这条断言会立刻红 |
| 压扁被误当成「高度」 | 中 | 以后有人以为森林能挡人 | 1.3 与 7.2 明确写清「压扁 ≠ 高度」 |

**一档回退（最省事）**：`render.screen_squash = 1.0` ⇒ 画面回到改造前（M1 的硬指标保证这一点）。
**二档回退**：`render.depth_sort = false` + `render.glyph_squash_compensate = false`
⇒ 压扁保留、两个最容易出问题的机制分别关掉，用来二分定位。

## 十一、还要拍板的小项（本文已给出推荐）

| # | 问题 | 推荐 | 备选与代价 |
