## 〇、一页结论

| # | 系统 | 一句话 | 主要落点 | 验收 |
|---|---|---|---|---|
| 1 | **战役数据格式** | 一个战役一个目录，一关一份 JSON；关卡 = 「地图 id + 覆盖层」 | `data/campaigns/<id>/`、`logic/campaign.gd`、`logic/campaign_library.gd`、`logic/level.gd` | 无头断言：扫描 / 载入 / 覆盖规则 / 校验 / 向后兼容 |
| 2 | **关卡装配** | `world` 从「一张图」改成「一张图 + 一份关卡」造出来，玩家席位可以是 1 个或 2 个 | `logic/world.gd` 新增 `create_from_level()` | `tests/test_campaign.gd` |
| 3 | **阵营 AI 附加制** | 两种现有 AI（阵营性 / 将领性）改成**按阵营挂**；难度 = 资源倍率 + 该方 AI 参数；**玩家选中的那一方自动摘掉 AI** | `logic/world.gd`、`logic/faction_ai.gd` | `tests/test_ai.gd` 扩展 |
| 4 | **进攻目标（= 波次）** | **没有触发器、没有时间轴**：给挂阵营 AI 的那一方指定「往哪打」，它的「招募 → 招兵 → 满员 → 行军攻击」循环就是一波又一波 | `logic/faction_ai.gd`（一处入口）、关卡数据 `attack_target` | `tests/test_ai_target.gd` |
| 5 | **目标与胜负** | 只做一种目标：**守住指定区划 N 秒**；**丢掉即判负**；大本营被拆常开判负；额外失败条件可配（第一批：指定区划失守） | `logic/objective.gd` | `tests/test_outcome.gd` |
| 6 | **共享视野** | 迷雾从「按阵营」改成「按同方」（`FactionRes.side_of`）；可玩阵营**必须同方** | `logic/fog.gd` 一处 | `tests/test_fog.gd` 扩展 |
| 7 | **合作网络层** | 哑中继 + **房主权威**；服务器零游戏逻辑；命令上行、20Hz 快照下行 | `net/*.gd` + `server/daeem_relay.py` | `tests/test_protocol.gd`、`tests/test_session.gd` + 本地两进程联调脚本 |
| 8 | **服务器部署** | Python 单文件服务（**自实现 WebSocket，零依赖**）+ nssm 托管，一键部署、日志轮转 | `server/` | 腾讯云上 `nssm start` 后两台机器真的能对局 |
| 9 | **战役编辑器** | `tools/campaign_editor`（Python + tkinter，零依赖，与前两个编辑器同构） | `tools/campaign_editor/` | `test_model.py` + `test_app.py` 全绿 |
| 10 | **界面** | 主界面加「战役」「合作」入口；关卡列表 + 阵营选择；合作建房/加入；关卡内目标面板 | `view/campaign_select.gd`、`view/coop_lobby.gd`、`view/objective_panel.gd`、`view/hud.gd` | `tests/test_ui.gd` 扩展 + 手玩清单 |

**一句话**：先把**单机一关**（挂 AI、指定进攻目标、守住区划、按阵营调难度）跑通，
再把**两个玩家阵营**在本地跑通（不开网络），最后才把这条链路搬到网线上 ——
网络层只搬运**已经验证过**的命令与快照。

### 1.3 由此定下的取舍（连同「为什么」与「什么时候回头改」）

#### 1.3.1 ★ 网络拓扑：**哑中继 + 房主权威**（不做专用权威服务器）

- **选**：两名玩家中的一个当**房主**，房主的进程跑**全部**逻辑：`logic/` 的 tick、两种 AI、目标与胜负判定。
  另一个当**客机**：只把玩家输入变成命令发上行，收 20Hz 快照后 `apply_snapshot` 到本地的 `world` 对象上，
  由现有 `view/` 原样渲染。服务器是**哑中继**：只按「房主 → 全体客机」「客机 → 房主」两条规则转发 JSON，
  **一行游戏逻辑都不 import**。
- **放弃**：专用权威服务器（云上跑 Godot 无头）、客户端预测、回滚、状态压缩、断线重连、反作弊、TLS、账号。
- **为什么**：这是 route.md 2.6 早就拍过的方向（HTML 版实测过 8 人满员、转发零丢失），也最符合「部署快捷、
  开发周期短、测试敏捷」：
  - 服务器**没有规则** ⇒ 不可能出现「服务端与客户端规则不一致」这类最难查的 bug；
  - 服务器是**一个 Python 文件 + nssm 一条命令**，改一行重启即可，不需要在云上装 Godot mono 与整个工程；
  - 「测试敏捷」直接受益：**中继可以在本机起**，两个客户端也能在本机起两个进程
    （`--headless` 的那个甚至可以是不带 `view/` 的纯逻辑客户端）。
- **代价（明确写下来，别以后惊讶）**：
  1. **房主掉线 = 这一局结束**（客机掉线不影响房主那一边）；
  2. 房主的机器性能决定两人的体验（合作关卡的 AI 规模要按「一台机器跑得动」来配）；
  3. 房主是**唯一的真相**，客机的画面有约 50ms 的延迟（20Hz 快照 + 插值）。
- **回头改的时机**：如果以后要求「两人都能掉线重进」或「房主不当权威」，就把房主那一侧的
  `net/host_session.gd` 整体搬到云上的 Godot 无头进程（`logic/` 是纯 `RefCounted`，这一步在架构上是通的）；
  届时**只有 `net/` 与部署脚本要动，`logic/` 与 `view/` 不动**。

#### 1.3.2 ★ 战役 = 有序关卡列表（不做「一张大地图 + 阶段推进」）

- **选**：战役 = 一份 `campaign.json`（元信息 + 关卡顺序）+ 若干**关卡文件**；
  每关引用一张**已存在的地图**（`data/maps/<id>/`），在其上叠加「阵营 / AI 与进攻目标 / 摆放 / 目标与失败条件」。
- **放弃**：一张持续的大地图、关卡之间的状态继承（带兵进下一关、资源结转）。
- **为什么**：一关一份文件才好 diff、才能单关重玩、才能用无头断言一关一关验；
  而「大地图战役」要求地图很大、还要求关卡间持久化，与「目前不做存档」这条直接冲突。
- **回头改的时机**：真要做「大地图战役」时，它是**另一种关卡类型**（`kind: "world_map"`），
  不影响本文这套数据格式。

#### 1.3.3 ★ 关卡 = 「地图 id + 覆盖层」，**不是**把地图数据搬进关卡

- **选**：地图文件（`map.json`）继续拥有**地形 / 区划网格 / 区划中心 / 产能 / 阵营大本营**；
  关卡文件拥有**这一关专属的东西**：玩家里有谁、每个参展阵营挂什么 AI 与往哪打、
  开局摆放、目标与额外失败条件。**覆盖规则**：同一个字段**关卡写了就用关卡的，没写就用地图的**
  （逐字段覆盖，不是整块替换）。
- **放弃**：把 `map.json` 的 `buildings` / `units` / `faction_bases` 全部搬进关卡（单一来源，但会
  让现有「自由对战 / 试炼场」这条路径失去数据、把 30+ 个测试全搅动）。
- **为什么**：现在 `data/maps/frontier/map.json` 里那套对家据点与守军**是给手玩测试用的**，
  它必须继续有效（地图选择条 → 按 test 直接开一局，这条路一个字都不能坏）；
  关卡是**在它之上的另一层**，不是它的替代品。
- **口径写死**（导出校验会拦）：
  - 关卡列出的阵营**必须在**该地图的 `factions` 里（或者关卡显式**追加**阵营）；
  - 关卡里每个**非玩家方**都**必须**有大本营点位 —— 否则会落到 (0,0) 顶掉区块中心
    （route.md 33.5 坑①，已实测）；
  - 关卡的摆放**不许**压在任何区划中心上（编辑器导出前硬拦，与 map_editor 同一条规则）。

#### 1.3.4 ★ AI 是「附加制」；**玩家选中的那一方自动摘掉 AI**

- **选**：每个参展阵营有一个 `ai` 字段，取值 **`faction`（阵营性 AI）/ `general`（将领性 AI）/ `none`（不动）**；
  - `faction` → 复用 `logic/faction_ai.gd`（自己一个资源池、招将 → 招兵 → 升级 → 满员后出兵）；
  - `general` → 复用 `logic/general_ai.gd`（没有资源池、在自己的归属区划里巡逻 / 警戒 / 脱战无消耗招兵）；
  - 难度旋钮 = **资源倍率**（`resource_mult`）+ 那一方自己的 AI 参数覆盖（`faction_ai` / `general_ai`
    两个子对象，缺省继承 `config.json` 的 `ai.faction` / `ai.general`）。
- **★★ 玩家选中哪一方，运行时就把那一方的 `ai` 当成 `none`**：这是「一关的多个参展阵营里选一个来玩」
  这条需求的必然结果 —— 编辑器允许给**任何**参展阵营配 AI（它可能是 AI 局的一方，也可能被玩家选中），
  **摘 AI 这件事只发生在运行时**（装配关卡时按「本局玩家席位」过滤），编辑器**不做**互斥限制。
  ⚠️ 反过来说：`ai` 的配置**不能**写进 `config.json`（那是全局的），必须留在关卡数据里。
- **放弃**：可视化「条件 → 动作」规则引擎、表达式 / 脚本语言、行为树。
- **为什么**：现有两套 AI 的判据必须**互斥**（route.md 33.3 是实测踩出来的），再叠一层规则引擎，
  「谁在管这个将领」会立刻变成三处判据；而用户真正要的「不同阵营挂不同 AI + 调难度 + 指定打哪」
  用**指派 + 倍率 + 一个目标点**就已经完整覆盖（下一条）。

#### 1.3.5 ★★ 不做触发器 / 剧本系统：「波次」= 阵营 AI 的重复进攻 + 一个指定的进攻目标

这是本次规划**最重要的一条修正**。用户的原话是：

> 「按照当前游戏中的『阵营 AI』做，游戏中的敌方 AI 会随机招募将领，该将领会自动招募士兵，
> 随后向目标点行军攻击，**我只需要为某个阵营设置该阵营 AI，并规定其行军攻击的目标点即可**」

- **选**：
  1. 关卡数据里给某一方写 `ai: "faction"` ⇒ 它就跑现有的阵营性 AI（这一步已经存在，只是名单在全局 `config.json` 里）；
  2. **新增一个字段 `attack_target`**：规定这一方的**行军攻击目标**（某个区划 / 某个格 / 某个建筑 / 某方的家）。
     现有代码是「自己挑：离我最近的敌方区划中心，没有就敌方大本营」（`faction_ai._attack_target()`）——
     现在**先问关卡数据，有就用它，没有就退回现有挑选逻辑**（一处入口 + 一处兜底，改动很小）；
  3. **「波次」的口径**（因为用户用了「红点波次」这个词，必须写清它现在指什么）：

     | 用户嘴里的词 | 在数据里的对应 |
     |---|---|
     | 一波红点 | `faction_ai` 的一次**派兵**（`_launch_attack`：挑几位满员将领，对他们下达行军攻击） |
     | 波次间隔 | `attack_repeat_sec`（两次派兵之间的最小间隔） |
     | 每波规模 | `generals` / `min_retinue` / `min_ready` / `ready_mult`（招几个将领、每位满员几人、一次派几位） |
     | 难度 | `resource_mult` + `start_food` / `start_gold`（攒钱快慢决定它多久成型） |
     | 「清完一波再来一波」 | 现有 AI 的自然行为（被打光就重招、攒够再派）—— **不需要额外调度代码** |
     | 多个方向同时来 | **多挂几个 AI 阵营**，各自一个 `attack_target` |

- **放弃**（明确写下，免得以后又绕回来）：
  - 触发器 / 条件-动作系统（`if 条件 then 动作`）；
  - 时间轴刷怪、定时波次、波次强度递增曲线；
  - 剧本化的一次性事件（「第三波开始后守军转攻」这类）——
    **想加的时候它是加法**：在 `faction_ai` 之上再叠一层调度即可，本文的数据格式**不用改**
    （`attack_target` 与 `ai` 参数仍然是那一层的输入）。所以**现在不做，不是现在做不了**。
- **为什么**：用户要的效果，现有 `faction_ai` **已经实现了 90%**（招将 → 招兵 → 满员 → 行军攻击 → 循环）；
  真正缺的只有「**打哪**」这一个自由度。为这件事去写一套触发器解释器 + 编辑器 UI + 词表，
  是典型的「用新系统解决一个字段能解决的问题」，而且会把「谁在管这个将领」变成三处判据。
- **顺带的一条小加法**（值得做，因为它直接服务「红点来袭」的体感）：
  `faction_ai._launch_attack()` 里**发一条事件**（`ai_attack_launched`：哪一方、几个将领、目标是什么），
  界面拿它去播报「边军出兵了，目标 c1」。**这是本文为「波次播报」保留的唯一一处新代码**。

#### 1.3.6 ★ 目标只有一条：守住指定区划 N 秒；**丢掉即判负**；大本营被拆常开判负

- **选**：`objectives` 只有一项：`{kind: "hold_zone", zone: <区划号>, hold_sec: <秒>}`。
  - 判定「归玩家」一律走**同方**：`FactionRes.side_of(owner) == FactionRes.side_of(玩家席位)`
    （合作模式下 p2 守住也算，单机时与 `owner == 自己` 等价）；
  - `held` 只在目标区划归玩家同方时累加；
  - ★ **一旦目标区划不再归玩家同方 ⇒ 当场判负**（用户拍板：连「暂停不清零」都不要）；
  - `held >= hold_sec` ⇒ **当场判胜**（跨过阈值的那一帧生效，不等下一帧）。
- **★ 开局必须是自己的**（用户拍板）：**不做「先占领再守」** —— 编辑器导出时硬拦
  「目标区划的开局归属方与玩家同方」这一条，否则玩家一进关就判负。
  这条同时把「只做『占领 / 守住』里的守」钉死了：**本版没有进攻关**。
- **失败条件两块**：
  1. **常开、不可关**：玩家同方的**大本营全部被拆** ⇒ 负（用户拍板：常开不可关）；
  2. **可配的额外失败条件**（在战役编辑器里配，第一批只做一种）：
     `zone_lost` = 某个**指定的额外区划**一旦不再归玩家同方 ⇒ 负（可以配多个）。
- **为什么「丢掉即负」要从数据结构上就防住开局那一帧**：如果不拦「开局就是自己的」，
  那「丢掉即负」的规则会让一个「目标区划开局在敌手里」的关卡**在第一帧直接判负** ——
  这是一个「规则本身没错、数据写错就炸」的组合，所以**必须在导出校验里拦住**（见 2.5）。

#### 1.3.7 ★ 可玩阵营**必须互为同方**（目标只有一份）

- **选**：一关可以有多个可玩阵营，但它们**必须互为盟友**（在 `allies` 里连成同一方）；
  合作模式的两个玩家**一定**友善（编辑器自动把两个玩家席位写成同方，不用手配）。
  于是目标是**一份**，判定走「玩家同方」。
- **放弃**：为每个可玩阵营分别配一份目标（敌对的两个势力各守自己的地那种设计）。
- **为什么**：用户明确说「两个可玩阵营一定友善，合作模式中的玩家一定相互友善」；
  一份目标 + 同方判定是最简单的口径，也顺手让**迷雾按同方**（1.3.8）与它一致。
- **代价**：想做「选魏或选蜀打同一场、各守各的地」这种关卡，需要**复制一份关卡**（改目标区划与阵营归属）。
  ❓ 这条路要不要留（见 9.2）。

#### 1.3.8 ★ 迷雾改「按同方」

- **选**：`logic/fog.gd` 现在按**阵营**分桶（`_bucket(faction)`）；合作模式要求两人**共享视野** ⇒
  改成按**同方代表**分桶：`FactionRes.side_of(faction)`（这个 API 已经有了，`logic/faction.gd`）。
- **为什么**：改动极小（分桶键 + 查询入口各一处），且**单机行为逐位不变**
  （单机时 `side_of("p1") == "p1"`）；不共享视野会让合作「看不到队友在打什么」，手感差很多。
- ⚠️ 三类查询（`tile_visible` / `unit_visible` / `building_visible`）**必须一起**改；
  `known_buildings`（敌建筑见过一次就永久显示）的铁律不变。

#### 1.3.9 ★ 网络层放哪儿：新增 `net/`（第三层），`logic/` 保持纯

- **选**：新增与 `logic/` / `view/` 平级的 `net/`，放**需要场景树**（WebSocket、定时器）但**不属于渲染**的东西。
- **为什么**：`logic/` 的硬约定是「纯 `RefCounted`、不碰 `Node`」（这是它能无头跑、能被服务器复用的前提），
  而网络显然需要 `Node` / `SceneTree`；塞进 `view/` 又会让「服务器复用」这条后路被 UI 代码污染。
- 落点与职责见 4.2。

#### 1.3.10 ★ 三个编辑器的关系：**不抽公共包**，靠「导出的 JSON」当契约

- **选**：`tools/campaign_editor` 是**新的独立目录**，需要复用地图 JSON 读写与画布代码时**复制一份并按需裁剪**；
  三个工具互不 import。
- **放弃**：抽一个 `tools/common/` 公共包（看起来更 DRY）。
- **为什么**：三个编辑器的**硬约定是「零依赖、单目录、双击 bat 就能跑」**（map_editor / unit_editor 各自
  只有 `__init__.py` + 自己的模块）。抽公共包会让「拷一个目录到别的机器上就能用」变成「要按相对路径 import」，
  而且三个工具的演化速度不同。
- **真正要钉住的契约是数据**：`data/campaigns/` 里的样例 + **往返测试**（读进来 → 写出去 → 逐字段一致）。

#### 1.3.11 ❌ 明确不做（本文范围内）

| 不做 | 为什么 / 什么时候回头 |
|---|---|
| **触发器 / 条件-动作系统、时间轴波次** | ★ 1.3.5：现有阵营 AI 已经覆盖了需求，只缺「打哪」；要在其上叠调度时它是加法，数据格式不用改 |
| 关卡简报、剧情文本、对话、结算界面 | 用户明确说「以后扩展」；关卡数据里留 `briefing` 字段（字符串数组），运行时**暂时不读** |
| 存读档、战役进度存档 | 用户明确说「目前可以不考虑」；**留接口**见 3.10 |
| 断线重连、反作弊、账号、匹配 | 用户明确说不考虑；房间码即口令 |
| TLS（`wss://`）/ 反向代理 | 「最简单最快」；第一版明文 `ws://`，风险见 9.1 风险 2 |
| 专用权威服务器 | 见 1.3.1；架构上留后路 |
| 3 人及以上、观战、录像回放 | 合作固定 2 人；回放等存档那一条一起做 |
| 「每个可玩阵营各配一份目标」 | 1.3.7：可玩阵营必须同方；要敌对多视角就复制关卡 |
| 「先占领再守」的进攻关 | 1.3.6：开局必须就是自己的 |
| 单位全灭 / 关键建筑被拆 / 限时 / 累计阵亡 这几类失败条件 | 第四轮问答里没选；先做 `zone_lost`，它们以后按同一张表加 |
| 可视化规则引擎 / 脚本语言 | 1.3.4 |
| 「大地图战役」 | 1.3.2 |
| 新的兵种 / 建筑 / 科技数值编辑 | 那是 `tools/unit_editor` 的活（战役编辑器只管**摆放、指派与目标**） |
| 换美术、3D | 与本文无关 |

## 二、数据格式（编辑器与运行时的**共同契约**）

> 这一节是全文最重要的部分：**战役编辑器写什么、运行时读什么，都以这一节为准**。
> 写法沿用 `data/maps/<id>/map.json` 的既有风格：字段名小写、`_comment` 写给人看、
> 缺字段有明确默认值、不认识的东西**不冒泡**（一张坏数据不该让整个列表空掉）。

### 2.1 目录约定（与「一个地图一个目录」同构）

```
data/campaigns/<campaign_id>/           ← 目录名 = 战役 id（与地图同一条约定）
├── campaign.json                       ← 战役元信息 + 关卡顺序
└── levels/
    ├── 01_beachhead.json               ← 文件名排序 = 关卡的默认顺序
    ├── 02_river.json
    └── 03_last_stand.json
```

扫描规则（`logic/campaign_library.gd`，**照抄** `logic/map_library.gd` 的四条）：
只认一级子目录；目录里找 `campaign.json` → `<目录名>.json` → 任一 `*.json`；解析失败**跳过不冒泡**；
显示名优先 `name`，没有就用目录名。**加一个战役 = 放一个新目录**，代码与配置一个字都不用改。

### 2.2 `campaign.json` 字段表

```json
{
  "_comment": ["战役元信息。关卡顺序以 levels[] 为准（不是文件名的字典序）。"],
  "name": "东征·第一章",
  "description": "一句话简介（可空）",
  "default_mode": "solo",
  "factions": [
    {"id": "p1",    "name": "赤军", "color": "#5AC8FF", "playable": true},
    {"id": "p2",    "name": "青军", "color": "#FFD166", "playable": true},
    {"id": "enemy", "name": "边军", "color": "#FF6B6B", "playable": false}
  ],
  "levels": [
    {"id": "beachhead", "file": "levels/01_beachhead.json", "name": "第一关·渡口"},
    {"id": "river",     "file": "levels/02_river.json",     "name": "第二关·河防"}
  ],
  "unlock": "in_order"
}
```

| 字段 | 类型 | 缺省 | 谁读它 |
|---|---|---|---|
| `name` | string | 目录名 | `campaign_library` → 主界面的战役选择条 |
| `description` | string | `""` | 战役选择条（显示一行说明） |
| `default_mode` | `"solo"` / `"coop"` | `"solo"` | 编辑器「新建关卡」时的默认值 |
| `factions[]` | 数组 | `[]` | 编辑器 + 运行时（**追加 / 覆盖**地图的 `factions`；`playable` 决定「玩家能选谁」） |
| `levels[]` | 数组（**有序**） | 必填 | 关卡列表；`file` 相对战役目录；`name` 缺省用关卡文件里的 `name` |
| `unlock` | `"in_order"` | `"in_order"` | 第一版只有这一种（顺序解锁） |

### 2.3 关卡 JSON 字段表

```json
{
  "_comment": ["一关 = 一张地图 + 覆盖层。没写的字段一律用地图自带的。"],
  "name": "第一关·渡口",
  "mode": "coop",
  "map": "frontier",

  "players": [
    {"faction": "p1", "base": [7, 2]},
    {"faction": "p2", "base": [19, 19]}
  ],

  "factions": [
    {"id": "enemy", "ai": "faction", "base": [14, 14],
     "resource_mult": 1.3, "start_food": 200, "start_gold": 200,
     "attack_target": {"kind": "zone", "zone": 4},
     "faction_ai": {"generals": 3, "min_retinue": 3, "min_ready": 2,
                    "ready_mult": 0.5, "attack_repeat_sec": 25.0},
     "general_ai": null},

    {"id": "ai", "ai": "general", "base": [22, 4],
     "general_ai": {"patrol_interval_sec": 3.0, "patrol_leash_tiles": 2}}
  ],

  "allies": [["enemy", "ai"]],

  "start_units": [
    {"faction": "enemy", "kind": "general", "general_index": 1, "unit_type": "spearman",
     "x": 3, "y": 3, "ai": "general", "zone": 11},
    {"faction": "enemy", "kind": "guard", "x": 15, "y": 13, "hold": true}
  ],
  "start_buildings": [
    {"type": "base",  "x": 14, "y": 14, "owner": "enemy"},
    {"type": "tower", "x": 14, "y": 12, "owner": "enemy"}
  ],

  "objectives": [
    {"kind": "hold_zone", "zone": 4, "hold_sec": 180}
  ],
  "fail_conditions": [
    {"kind": "zone_lost", "zone": 6}
  ],

  "briefing": []
}
```

| 字段 | 类型 | 缺省 | 语义 / 谁读它 |
|---|---|---|---|
| `name` | string | 文件名 | 关卡列表显示名 |
| `mode` | `"solo"` / `"coop"` | 战役的 `default_mode` | 决定 `players[]` 允许几个席位、以及界面走哪条入口 |
| `map` | string | **必填** | `data/maps/<map>/` 的目录名（= 地图 id，与 `map_library` 同一套） |
| `players[]` | 数组，1~2 项 | 必填 | 玩家席位；**顺序 = 席位顺序**（房主第 1 个、客机第 2 个）；`base` 覆盖地图的 `faction_bases[faction]` |
| `factions[]` | 数组 | `[]` | 参展阵营的 **AI 指派 + 难度 + 开局资源 + 大本营 + 进攻目标**；见 2.4 与 3.6 |
| `allies` | 数组 | 地图的 `allies` | 覆盖地图的盟友关系（对齐 `FactionRes.set_allies`）。★ 合作模式下两个玩家席位**必须**同方（编辑器自动写 / 校验） |
| `start_units[]` | 数组 | `[]` | 开局就在场的单位 / 将领（**追加**在地图 `units` 之后） |
| `start_buildings[]` | 数组 | `[]` | 开局就在场的建筑（**追加**在地图 `buildings` 之后） |
| `objectives[]` | 数组 | 必填 | **恰好 1 项**，且 `kind == "hold_zone"`；见 1.3.6 |
| `fail_conditions[]` | 数组 | `[]` | **额外的**失败条件（大本营被拆那条是常开的，不写在这里）；第一批只支持 `zone_lost` |
| `briefing` | 字符串数组 | `[]` | **第一版运行时一个字都不读**（留给以后做简报；编辑器可编辑） |

#### `start_units[]` 每一项

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `faction` | string | 必填 | 归属 |
| `kind` | string | 必填 | `general` / `general_N`（将领）或兵种 kind（普通单位），沿用现有 `UnitRes.create` 的口径 |
| `general_index` | int | `kind` 里的序号，没有则 `1` | 将领序号（决定用 `unit.general.stats[i]` 哪一套数值） |
| `unit_type` | string | 该 kind 的默认兵种 | 兵种（`config.unit.types` 的键）；决定图标上的那个字与数值 |
| `x` / `y` | int | 必填 | 格坐标 |
| `ai` | `"general"` / `"none"` | `"none"` | `general` ⇒ 挂将领性 AI（**同时**要 `zone`） |
| `zone` | int | `-1` | 归属区划（`general` 用；与现有 `map.units[].zone` 同义） |
| `hold` | bool | `false` | 原地不动（与现有 `map.units[].hold` 同义） |
| `name` | string | 自动 | 显示名（不写就用 `kind` 推） |

⚠️ 硬规则（三条，都来自已实测的坑）：
1. `ai: "general"` **必须**同时给 `zone`，否则「将领性 AI 没有归属区划」= 它会在原地发呆
   （route.md 33.3 的互斥判据）；
2. 挂了 `general` AI 的单位**自动** `hold = true`（现状就是这么落的：`world.reset()` 里
   `garrison_zone_id >= 0` ⇒ 同时置 `hold_position`），别在数据里写相反的组合；
3. 摆放**不许**压在任何区划中心格上（`_spawn_zone_centers()` 只在**任何单位出生之前**建中心，
   叠格会静默建不出来 —— route.md 那一大段说明）。

### 2.4 进攻目标（`attack_target`）—— 这就是「波次」的全部配置

```json
"attack_target": {"kind": "zone", "zone": 4}
```

| `kind` | 载荷 | 目标点怎么算 |
|---|---|---|
| `zone` | `zone`: 区划号 | 该区划的**中心格**（与现有 `_attack_target()` 取的是同一种点） |
| `point` | `x`, `y` | 直接是这一格（行军到那一点） |
| `building` | `x`, `y` | 这一格上的建筑（先靠近再拆） |
| `base` | `faction` | 某一方的大本营所在格 |
| **不写** | — | **现状**：离自己最近的敌方区划中心；没有敌方区划 → 敌方大本营（一个字都不改） |

一个阵营**只能有一个** `attack_target`（要多个方向就多挂一个 AI 阵营）。

> ★ 「波次」在这个数据格式里**没有独立字段** —— 它就是「这一方挂着阵营 AI」+「它的 `attack_target` 指着哪」
> 这两件事的组合，节奏与规模全在 `faction_ai` 那几个参数里（1.3.5 的那张对照表）。
> 这样做的直接好处：**编辑器不需要发明新概念**，只有「挂 AI」「选目标」两个动作。

### 2.5 导出校验（编辑器**硬拦截**清单）

导出前逐条检查，任一不过就**不许写文件**并在界面上指出是哪个战役 / 哪一关 / 哪一项
（与 map_editor 的「叠格」拦截同一套做法）：

| # | 检查 | 拒因文案（示例） | 级别 |
|---|---|---|---|
| 1 | 每关的 `map` 在 `data/maps/` 里真的存在 | 「地图 `xxx` 不存在」 | 拦 |
| 2 | `mode: "solo"` 时 `players` 恰好 1 项；`"coop"` 时恰好 2 项 | 「单人关只能有一个玩家席位」 | 拦 |
| 3 | 两个玩家席位**不能是同一个 faction** | 「两个玩家不能占同一阵营」 | 拦 |

### 3.2 关卡装配：`world.gd` 新增 `create_from_level()`

```gdscript
# logic/world.gd
static func create_from_level(cfg, campaign, level, my_faction: String,
        roster: Array, with_ai: bool = true) -> RefCounted
```

它做的事情（**按顺序**，顺序本身是硬约定）：

1. 载入地图（`MapLibrary` / `MapData`），把**关卡的覆盖层**合并进去：
   `factions`（追加 / 覆盖）→ 大本营（`players[].base` + `factions[].base` 一起写进 `faction_bases`）→
   `start_units` / `start_buildings` **追加**到地图的 `units` / `buildings` 之后；
2. `FactionRes.set_allies(level.allies)`（关卡没写就用地图的 —— `reset()` 里已经是「先清后写」，沿用）；
3. ★ **按本局玩家席位摘 AI**：`roster` 里的每一个 faction，其 `ai` 一律按 `none` 处理
   （哪怕关卡数据里写了 `faction`）—— 这是 1.3.4 那条拍板的唯一落点；
4. ★ **按关卡数据建 AI 名单**：`config.ai.factions` 仍然算，但**关卡里显式写了 `ai: "faction"` 的阵营优先**，
   并带上它的 `resource_mult` / `start_food` / `start_gold` / `attack_target`；
5. 调现有 `reset(my_faction, roster)`：玩家席位**可能是 2 个** ⇒ 两个大本营都建、两支部队都出生；
6. 末尾（`reset` 的收口之后）建 `objective_state` 并 `objective.setup()` ——
   与 `fog.update()`、`FactionAiRes.setup()` 那一串**同一个位置**，
   保证「reset 结束 = 一切是热的」这条契约不破（HUD 在第一帧 tick 之前读到的就是对的）；
7. `world.tick()` 的末尾按顺序推进：`faction_ai.update()` / `general_ai`（挂在单位上，随 tick）
   → `objective.update()`（**目标最后判**，这样「这一帧刚守满」能立刻结算）。

⚠️ 现有那条契约要继续成立：**不带 AI 的世界（`with_ai = false`）与加战役之前逐位一致**
（测试 / 基准都走这条路）。所以新状态在 `with_ai = false` 且 `level == null` 时必须是
「空且不影响任何旧行为」。

### 3.3 阵营 AI 的进攻目标（改 `faction_ai` 的哪几处）

现状（`logic/faction_ai.gd`）：`_decide()` 的四段优先级（招将 → 招兵 → 升级 → 出兵）已经完整，
出兵那一段走 `_launch_attack()`，而**打哪**由 `_attack_target(world, faction)` 自己挑
（离自己最近的**敌方区划中心**；没有敌方区划 → 敌方大本营；判据用
`FactionRes.same_side_for_attack(...)` 取反，**盟友的地不算敌方**）。

改动只有两处：

```gdscript
# ① 目标：先问关卡数据，没有就退回现有挑选逻辑
static func _attack_target(world, faction: String) -> Variant:
    var t: Variant = world.level_attack_target(faction)   # 关卡写了就用它（已解析成"目标格"）
    if t != null:
        return t
    return _attack_target_default(world, faction)         # ← 现在的这段逻辑原样搬进来，一个字不改

# ② 出兵时发一条事件（给界面播报「红点来袭」用；逻辑层只给参数，文案在 view/）
static func _launch_attack(world, cfg, fc, generals) -> void:
    ...现有逻辑...
    world.emit_event({"kind": "ai_attack_launched", "faction": fc["faction"],
                      "leaders": launched.size(), "target": target_label})
```

⚠️ 三条不能破：
1. **缺省必须逐位不变**（没写 `attack_target` 的关卡 / 不做战役的老路径）；
2. `attack_target` 解析出来的目标**必须过滤掉「不可达」**——现有 `_attack_target()` 已经在做这件事
   （跳过没有中心格的区划、没有敌方区划就退大本营），新入口要把「关卡给的目标」也过一遍同一套过滤，
   否则会出现「AI 对着一个走不到的点原地发呆」（这类症状在 HTML 版出现过）；
3. 出兵仍然走现成的 `order_attack_move`（行军攻击），**不要**新写一套命令。

**「波次」的节奏与规模**（全部是既有参数，编辑器把它们暴露出来即可，不改代码）：
`generals` / `min_retinue` / `min_ready` / `ready_mult` / `attack_repeat_sec` / `resource_mult` /
`start_food` / `start_gold`（对照表见 1.3.5）。
❓ 要不要在编辑器里做一个「这一关大概多久成形、每波大概几个兵」的**估算提示**（纯展示，不参与运行）——见 9.2。

### 3.4 目标与胜负：`logic/objective.gd`

状态（进快照，字段短名）：

```gdscript
{
  "kind": "hold_zone",
  "zone": 4,             # 区划序号（zone_list 里的下标，与快照按序号对齐同一套）
  "hold_sec": 180.0,
  "held": 0.0,           # 已经守住的秒数
  "state": "running",    # running / won / lost
  "reason": ""           # 判负时是哪一条：base_destroyed / zone_lost:6 / objective_lost
}
```

规则（写死，逐条进断言）：

1. **开局校验**（编辑器拦一遍，运行时再兜底一遍）：目标区划的开局归属方必须与玩家**同方**；
   运行时若发现不成立 ⇒ 立刻 `lost`，`reason = "objective_never_held"`（**别静默**：
   这是数据写错，要留一条痕迹）；
2. `held += dt` **仅当**目标区划归玩家同方；
3. ★ **目标区划一旦不再归玩家同方 ⇒ 立刻 `lost`**（`reason = "objective_lost"`）——
   用户拍板「丢掉即判失败」，连暂停都没有；
4. `held >= hold_sec` ⇒ 立刻 `won`；
5. **常开失败条件**：玩家同方的大本营**全部**被拆 ⇒ `lost`，`reason = "base_destroyed"`
   （★ 常开**不可关**，用户拍板）；
6. **额外失败条件**（`fail_conditions[]`，第一批只做 `zone_lost`）：指定的区划一旦不再归玩家同方
   ⇒ `lost`，`reason = "zone_lost:<zone>"`（可以配多个，谁先触发算谁的）；
7. 结算后 `world` 继续 tick（不做 UI 冻结）；界面读 `state` / `reason` 播报一次并进入「本关结束」态
   （第一版 = 一行提示 + 一个回关卡列表的按钮，**不做结算面板**）。

> ★ **为什么只有「大本营被拆」是常开的**：它是「这一局还能不能继续」的底线判据
> （大本营没了就再也建不了东西）；其余失败条件都是**关卡设计者的调味**，所以可配。
> ★ 单位全灭 / 关键建筑被拆 / 限时 / 累计阵亡 这四类**以后按同一张表加**：加一个 `kind` +
> 一条求值分支 + 编辑器里一个下拉项，**数据结构不用变**（`fail_conditions[]` 已经是数组）。

### 3.6 按阵营挂 AI 与难度（含迁移口径）

**关卡里的形状**（见 2.3 的 `factions[]`）：

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `id` | string | 必填 | 阵营 id |
| `ai` | `"faction"` / `"general"` / `"none"` | `"none"` | **本文新增的核心字段**；★ 运行时对「本局玩家席位」一律按 `none` 处理 |
| `base` | `[x,y]` | 地图的 `faction_bases[id]` | 该方大本营（**校验硬拦**：非玩家方必须有） |
| `resource_mult` | float | `1.0` | 难度旋钮（只乘产能收入，沿用 `faction_ai._income` 的口径） |
| `start_food` / `start_gold` | int | `0` | 开局资源（写进 `world.ai_resources[id]`） |
| `attack_target` | 对象或省略 | 省略 = 现状 | 行军攻击目标（2.4） |
| `faction_ai` | 对象或 `null` | 继承 `config.ai.faction` | 该方自己的阵营性 AI 参数（**波次节奏与规模就在这里**） |
| `general_ai` | 对象或 `null` | 继承 `config.ai.general` | 该方将领性 AI 的**默认**参数（单位上的摆放可再覆盖） |

**迁移口径（向后兼容，别破）**：

1. **玩家席位永远不挂 AI**：`FactionRes.is_player_faction` 那条硬规则保留；
   ★ 与旧版的差别只在**判定时机**：旧版是「配置里就不该出现玩家方」，新版是
   「关卡里可以给任何阵营配 AI，**装配时按本局席位摘掉**」（1.3.4）；
2. 关卡没写 `ai` 的阵营：**照旧**用 `config.ai.factions[]` 那一套（现状），也就是说
   「不做战役、直接按 test 开一局」的行为**逐位不变**；
3. `config.ai.factions[].base` 与 `_register_config_bases()` **保留**（它是「地图没给这一方点位时」的兜底），
   关卡给了就用关卡的 —— **同一条覆盖规则，只有一处实现**（`logic/level.gd` 的合并函数）；
4. `general_ai` 的**归属区划**仍然只能来自「单位 / 关卡的摆放」（`garrison_zone_id`），
   不接受「全局给一个区划」这种写法（那会让一个阵营的所有将领挤在同一块地里）。

### 3.7 玩家的资源池要从「一个字典」改成「按席位」

现状：`world.resources` 是**一个**字典（本机席位），`world.ai_resources` 是 AI 的按阵营字典。
合作模式需要「p1、p2 各自的钱」（用户已拍板：资源各自独立）。落点：

| 改动 | 说明 |
|---|---|
| `world.player_resources: {faction: {food, gold}}` | 新增；玩家席位各一份（1 个或 2 个） |
| `world.resource_pool_for(faction)` | **已经是**所有扣费 / 退款的唯一入口 ⇒ 加一条分支：玩家席位查 `player_resources`；AI 阵营查 `ai_resources`；都没有 ⇒ `null`（资源无限）。**这是唯一改动点**，招募 / 升级 / 特化的扣费一行都不用改 |
| `world.resources` | 保留为「**本机席位**那一份」的别名（`view/` 读它，一个字不用改） |
| `world.owned_tiles` | 同理（本机席位的），HUD 不动 |
| 每帧产出 | `_refresh_production()` 已经按阵营算（`zones.production_of(faction)`）⇒ 给每个玩家席位各加一次，本机席位同步到 `world.resources` |

> ★ 这条改动的好处：**「谁下单扣谁的钱」这条判据不用重写**，合作模式天然就对了；
> 客机侧只显示自己那一份（快照里也只发玩家席位那两份，**AI 的资源池不下发**）。

### 3.8 快照要补什么（照 `logic/snapshot.gd` 现在的口径逐项对）

现有快照已有：`units[]`（含 `tk/tr/tt/tq` 招募队列、`ld` 队长、`fa` 朝向）、`buildings[]`、`zones[]`
（含 `o/p/cf/cs/pop`）、`res`、`owned`、`time`。**要补的**：

| 新增字段 | 形状 | 为什么必须发（不发会怎样） |
|---|---|---|
| `pres` | `{"p1":[food,gold], "p2":[…]}` | 现有的 `res` 是一个池 ⇒ 合作里客机看到的可能是**别人的钱**。只发**玩家席位**那一份，AI 池不发 |
| `obj` | `{zone, held, sec, state, reason}` | 客机要画「守住进度条」与「已守 92/180 秒」，以及**判负原因**；不发 = 客机的目标面板永远是 0 |

| `events` | 一次性事件数组（`notice` / `ai_attack_launched` / `level_end`） | 客机也要看到「边军出兵了」和胜负播报；房主把事件塞进快照，客机消费后清空 |

⚠️ 三条既有铁律继续有效（写进断言）：
1. **缺字段 = 保持本地现状**（不要当成 0 / false）；
2. **只发结果不发过程**（不发 `path`）；
3. 字段名继续用短名（省带宽 + 逼自己只同步必要的）。

### 3.9 事件与播报（逻辑层不写 UI 文案）

现状：`world.tick()` 返回事件数组，目前只翻译三条（`recruit_rejected` / `order_rejected` / `unit_recruited`）。
本文新增两条 + 沿用一条，**同样只给「事件 + 参数」，文案在 `view/` 一处**：

| 事件 | 载荷 | 界面落点 |
|---|---|---|
| `ai_attack_launched` | `faction`, `leaders`, `target` | 底栏提示带：「边军出兵了（3 位将领 → c1）」= **红点来袭的体感**（1.3.5 的唯一一处新代码） |
| `objective_progress` | `zone`, `held`, `hold_sec` | 目标面板刷新（也可以每帧直接读状态，事件只用于「刚过半」这类播报） |
| `level_end` | `result`(`win`/`lose`), `reason` | 一行提示（胜 / 负 + 原因）+ 回关卡列表的按钮（**不做结算面板**） |

### 3.10 存读档与战役进度的「留口子」（本文**不做**，只把结构留对）

用户明确说「目前可以不考虑存读档和进度存档，但要留出可扩展的部分」。留口子的方式**不是**先写一半代码，
而是**让数据结构天然可存**：

| 将来要做的东西 | 现在就把它摆在对的位置 |
|---|---|
| 进度存档（通关到哪一关） | 进度 = `{campaign_id: [已通关 level_id]}`，与存档文件长什么样无关；界面靠它算「哪些关可点」。⇒ 现在就把「哪些关可点」写成一个**纯函数**（`campaign_library.unlocked_levels(campaign, progress)`），将来把 `progress` 从「本会话内存」换成「读文件」即可，界面一行不改 |
| 单局存档 / 读档 | 已经有了：`logic/snapshot.gd` 的 `to_snapshot` / `apply_snapshot`（**现在就往返无损、且有断言**）。将来的存档 = 快照 + 四样元数据（`campaign_id` / `level_id` / 玩家席位 / `world.time`）。⇒ 所以**关卡装配必须可重放**：同一份关卡数据 + 同一份快照 ⇒ 同一个世界 |
| 录像 / 回放 | 房主权威的天然副产品：开局那一包 `start`（含关卡数据）+ 后续命令流 = 一份完整录像。⇒ 所以协议里的 `cmd` **现在就带 `seq` 与时间戳**（见 4.3） |
| 多人进度 | 以后若要「进度跟人走」才需要账号；现在**不引入任何账号概念**（房间码即身份） |

⚠️ 一条硬要求：**不许**为了「以后好存档」而把随机性引进来 —— 出兵成形、AI 决策
**都不许**用「随机数决定结果」（站位轮询、按距离排序这类确定性的写法都可以）。
理由：房主权威下客机不需要确定性，但**存档 / 回放需要**；现在写成确定的，将来就不用返工。

## 四、合作模式的网络层

### 4.1 拓扑与职责（一张表说清「谁做什么」）

| 角色 | 跑什么 | 不跑什么 |
|---|---|---|
| **房主**（`players[0]`） | 整个 `logic/`：tick、两种 AI、目标与胜负判定；本机输入 → 命令；**20Hz 广播快照**；校验客机命令 | 不做专用服务器那一套（无可信第三方、无鉴权） |
| **客机**（`players[1]`） | 本机输入 → 命令（上行）；收快照 → `apply_snapshot` → 现有 `view/` 原样渲染；本地算迷雾（迷雾是**派生数据**，各端各算一遍） | **不 tick 世界**、不跑 AI、不判胜负 |
| **中继服务器** | 连接管理、房间、按两条规则转发 JSON、健康检查 | **一行游戏逻辑都不 import**；不解析游戏内容（只看信封） |

> ★ 客机也持有一个 `world` 对象（用**同一份地图 + 同一份关卡**造出来），
> 目的是让**现有 `view/` 一个字不改地读它**；客机那个 world 只被 `apply_snapshot` 写。

### 4.2 新增 `net/` 层（与 `logic/`、`view/` 平级）

| 文件 | 类型 | 职责 |
|---|---|---|
| `net/protocol.gd` | 纯 `RefCounted` | 消息类型常量、协议版本号、编解码与**校验**（信封字段、必填字段）；**无头可测** |
| `net/relay_client.gd` | `Node` | 包一层 `WebSocketPeer`：连接、发送 JSON、收包、断开；**不做自动重连**（用户明确不要） |
| `net/host_session.gd` | `Node` | 房间生命周期、席位分配、收客机命令（校验后交给 `command_processor`）、20Hz 发快照、事件广播 |
| `net/client_session.gd` | `Node` | 上行命令、下行快照（交给 `snapshot.apply_snapshot`）、房主离开时收摊 |
| `net/lobby.gd` | `Node` | 建房 / 加入 / 房间码 / 准备状态（与 `view/coop_lobby.gd` 配合：逻辑在这里、显示在那里） |

**命令流怎么接上现有的边界**（这是全篇最关键的一处接线）：

```
现在：  view/input_controller.gd  --命令-->  logic/command_processor.gd（直接执行）
改造：  view/input_controller.gd  --命令-->  net/session（本机是房主？）
                                              ├─ 房主：直接交给 command_processor（本机席位 = 自己的 faction）
                                              └─ 客机：封成 {type:"cmd", by:"p2", seq:n, body:{...}} 上行
```

- ⚠️ 命令**要带 `by: faction`**：房主收到后校验「这条命令的 `by` 是不是这个连接被分配的席位」——
  不是就丢弃（这不是反作弊，是**防自己写错**：两个人同时下单时，谁的钱被扣必须唯一确定）。
- ⚠️ 命令仍然**只放意图不放结果**（route.md 4.1 那条：客机只说「哪些单位、走到哪个点」，
  路径由房主算）—— 沿用，一个字不改。
- ★ 落点：**只有一处**分派（`view/game_scene.gd` 里把命令交给谁那一句）；新增 `net/` 之后
  **单机路径 = 「房主 + 0 个客机」**，也就是说单机走的代码和联机完全一样，
  不会出现「单机能玩、联机一开就崩」这种最烦人的分叉。

### 4.3 协议（消息表）

一条消息 = JSON 对象，**信封**固定四个字段：`{"v":1, "t":"<类型>", "seq":n, "ts":ms, "body":{…}}`
（`ts` 现在就用上：它是「以后做录像」的前提，见 3.10）。

| `t` | 方向 | body | 说明 |
|---|---|---|---|
| `hello` | 客户端 → 中继 | `{proto:1, game:"daeem", build:"<git 短 hash>"}` | 握手；`build` 不一致时中继**拒绝**（版本不一致的两个客户端进同一局 = 各种诡异 bug） |
| `create_room` | 客户端 → 中继 | `{mode:"coop", level:"<campaign>/<level_id>"}` | 建房（房主） |
| `join_room` | 客户端 → 中继 | `{room:"ABC123"}` | 加入（客机） |
| `room_state` | 中继 → 双方 | `{room, host_seat, guest_seat, ready:{…}}` | 房间成员与准备状态 |
| `ready` | 客户端 → 中继 | `{ready:true}` | 准备 |
| `start` | 房主 → 中继 | `{campaign, level_id, level_data:{…}}` | 开局；★ **关卡数据由房主发**（这样「客机没有那个战役目录」也能玩） |
| `cmd` | 客机 → 房主 | `{by:"p2", seq, ts, body:{kind, …}}` | 玩家命令 |
| `snap` | 房主 → 全体客机 | `{seq, snap:{…}}` | 20Hz 世界快照 |
| `event` | 房主 → 全体客机 | `{items:[…]}` | 播报 / 胜负（与快照同一条通道，只是**立刻**发，不等下一个 20Hz） |
| `ping` / `pong` | 双向 | `{t}` | 保活 + 显示延迟 |
| `bye` | 双向 | `{reason}` | 主动离开；房主发 `bye` = 这一局结束 |
| `err` | 中继 → 客户端 | `{code, msg}` | 房间不存在 / 房间满 / 版本不符 / 房间已开局 |

### 4.4 时序、节流与「谁等谁」

| 项 | 口径 |
|---|---|
| 快照频率 | **20Hz**（50ms 一包）；「只发变化」这件事**第一版不做**（全量发，先跑通；带宽见 9.1 风险 3） |
| 命令上行 | 立即发，不等下一帧；房主按收到顺序执行（同一帧内多条 = 按 `seq` 排序执行） |
| 时间基准 | 客机**不用**自己的时钟推逻辑：位置由快照 + 现有插值表现；`world.time` 以快照里的为准 |
| 暂停 | 第一版**不做**合作暂停（要双方同意机制，属于「以后」）；单人模式照旧可暂停 |
| 延迟显示 | HUD 右上角一个小数字（`ping` 的往返），便于手玩时判断「卡了还是网差」 |
| 开局 | 房主 `start` → 双方各自进关；客机**不等**地图加载完（它不 tick） |

### 4.5 服务器：单文件中继（Python，**零依赖**）

`server/daeem_relay.py`（一个文件，标准库 + `asyncio`）：

- **WebSocket（RFC6455）自实现**（用户拍板）：只做服务端需要的那一小块
  （握手 / 掩码解包 / 文本帧 / ping-pong / close）。HTML 版就是这么干的
  （`dev_html/net/serve.py`，已随旧版删除，思路在 route.md 2.6 里记着）。
  ⚠️ 自实现的部分**必须有测试**：握手（含 `Sec-WebSocket-Key` 的 SHA-1 + base64）、
  分片帧、掩码、长度 126 / 127 的扩展长度、close 握手 —— 五条各一个用例（`server/test_relay.py`）。
- 路由：
  - `GET /health` → `200 {"ok":true,"rooms":n,"players":n,"uptime":s}`（给运维与监控用）
  - `GET /rooms` → 房间列表（房间码 / 模式 / 关卡 / 人数 / 是否已开局；**不暴露 IP**）
    —— ★ **界面上不做列表**（用户拍板），这个接口只给运维 curl。
  - `WS /ws` → 游戏连接（上面的消息表）
- 转发规则**只有两条**（route.md 2.6 的原话）：
  ① 房主发的游戏消息 → 该房间全体客机；② 客机发的 → 房主。其余消息（握手 / 房间 / 准备）由中继自己处理。
- 房间码：**6 位大写字母数字**（去掉易混的 `0/O/1/I`），冲突就重掷；
  一个房间最多 1 房主 + 1 客机（合作固定 2 人，房间满了返回 `err`）。
- 日志：一条连接一行（时间 / 房间 / 座位 / 收发字节数 / 断开原因），**不打游戏内容**。
- 配置：`--host/--port/--max-rooms/--log-level`，其余全在命令行；**不写配置文件**
  （「一条命令起」是这条取舍的核心）。

### 4.6 nssm 部署（腾讯云 Windows）

```powershell
# 一次性（在服务器上，管理员 PowerShell）
nssm install DAEEMRelay "C:\Python312\python.exe" "C:\daeem\server\daeem_relay.py --port 8770 --max-rooms 64"
nssm set DAEEMRelay AppDirectory  C:\daeem\server
nssm set DAEEMRelay AppStdout     C:\daeem\logs\relay.out.log
nssm set DAEEMRelay AppStderr     C:\daeem\logs\relay.err.log
nssm set DAEEMRelay AppRotateFiles 1
nssm set DAEEMRelay AppRotateBytes 10485760
nssm set DAEEMRelay Start SERVICE_AUTO_START
nssm start DAEEMRelay

# 验证
curl http://127.0.0.1:8770/health
```

- 腾讯云**安全组**要放行 TCP 8770（第一版明文 `ws://`，用户已知悉取舍）。
- 部署脚本：`server/deploy.ps1`（把 `daeem_relay.py` 拷过去 + 重装服务 + 重启，**幂等**，
  可反复跑；把上面那一串固化成脚本，避免手抄）。
- 运维三件事：`nssm status DAEEMRelay` / `curl /health` / 日志尾部。
  **不做**：自动更新、监控告警、多实例负载均衡（房间数很少）。
- ⚠️ 中继重启 = 所有房间掉线（**不做重连**，与取舍一致）；升级中继要在没人玩的时候做。

### 4.7 异常与边界（第一版就写死，别留模糊）

| 情况 | 行为 |
|---|---|
| 房主掉线 / 主动退出 | 房主发 `bye` → 中继广播 → 客机回到主界面并提示「房主已离开」；**客机不接管** |
| 客机掉线 | 房主那一局**继续**（AI 照跑、目标照判），只是少一个人；房主界面提示「队友已掉线」 |
| 中继掉线 | 双方都回到主界面（提示「与服务器断开」）：**不做重连** |
| 版本不一致 | `hello` 时 `build` 不同 ⇒ 中继拒绝，提示「两边版本不一致，请更新」 |
| 房间不存在 / 已满 / 已开局 | `err` 三种码，界面一行提示 |
| 客机发来非法命令（`by` 对不上 / 字段缺） | 房主**丢弃并记一行日志**（不崩、不回错误给客户端 —— 免得被人拿来做探测） |
| 客机的 `world` 与房主不一致（单位数差太多） | 第一版**不做**校验（有 `snap` 就是真相）；只在 `ping` 里带一个 `unit_count`，两边差 > 20% 时 HUD 弹一行黄字（**便宜的自我诊断**） |

### 4.8 怎么让联机测试「敏捷」（这是本文的一条硬要求）

| 层次 | 手段 |
|---|---|
| 协议逻辑 | `tests/test_protocol.gd`：**纯 `RefCounted`**，把消息编码 / 解码 / 校验 / 非法输入当断言跑（无 socket） |
| 房主 / 客机会话 | `tests/test_session.gd`：用**假连接**（一个把消息记进数组的桩）跑「两条命令 + 三次快照」，验「客机命令被校验 / 快照能往返 / 房主离开使客机收摊」 |
| 中继本身 | `server/test_relay.py`：握手 / 帧 / 掩码 / 扩展长度 / close 五条（自实现的 WebSocket 必须有测试） |
| 端到端 | `server/run-local.ps1`：本机起中继 + 起两个客户端（一个正常窗口、一个 `--headless` 逻辑客机） |
| 真机 | `server/README.md` 里的手玩清单：两台机器（或一台机器 + 云服务器）走一遍完整流程 |

> ★ 「本机两个进程能互相看到并打起来」这条**必须在 M7.5 就成立**，
> 不要等到「上服务器」那一步才发现协议有问题（route.md 第 1 轮的验收标准就是这个）。

├── __init__.py          ← 照 unit_editor 那份（几句说明 + 版本）
├── __main__.py          ← `python -m tools.campaign_editor`
├── app.py               ← 界面（页签、画布、表格、校验对话框）

> 而且「校验逻辑」只有一份 —— 界面只是它的一个消费者。

### 6.2 页面（页签）结构

| 页签 | 内容 | 关键交互 |
|---|---|---|
| ① **战役** | 战役名 / 简介 / 默认模式 / 关卡顺序 | 新建战役、选目录、上下箭头排关卡顺序、增删关卡 |
| ② **关卡** | 当前关：名字 / 模式（单人·合作）/ 地图（下拉，扫 `data/maps/`）/ **目标**（守住哪个区划 + 多少秒）/ **额外失败条件**（列表，第一批只有「指定区划失守」，点一下加一条） | 选地图后**自动重载**画布；模式一改，玩家席位数跟着变；目标区划在画布上高亮 |
| ③ **阵营与 AI** | 每一方一行：可玩？/ 颜色 / 大本营点位 / **AI 类型**（无·阵营性·将领性）/ 资源倍率 / 开局资源 / **进攻目标**（下拉：最近敌方区划〔默认〕/ 指定区划 / 指定格 / 某方的家）/ AI 参数（折叠的「高级」区，缺省 = 继承 config） | 玩家席位单独一栏（1 或 2 个）；非玩家方的大本营没填 → **导出拦截**；★ 给「可玩」阵营配 AI 是**允许**的（运行时按选中的席位摘掉，见 1.3.4），界面上给一句灰字说明 |
| ④ **摆放** | 画布：点一下放一个单位 / 将领 / 建筑；选中后可改归属 / 兵种 / 将领序号 / `zone` / `hold` / 是否挂将领性 AI；★ 另有一个「**设进攻目标**」模式：选中某一方，在地图上点一个区划 / 格，直接把它设成该方的 `attack_target` | 与 map_editor 的画布同一套手势（滚轮以光标为锚点缩放、中键拖动、右键删除） |
| ⑤ **校验与导出** | 跑 2.5 那 16 条，逐条显示「通过 / 警告 / 拦截」；通过才允许写文件 | 写文件后显示路径与改动行数；**「一键打开地图编辑器」**也在这页（给当前关的地图） |

> ★ 「进攻目标」在两处都能改（③ 的下拉 / ④ 的画布点选），**底层是同一个字段**：
> 编辑器要保证「在这个页面改了，切到另一个页面看到的是同一个值」（这是最容易写出不一致的地方）。

### 6.3 画布上的交互（对齐 map_editor 的既有手势）

| 手势 | 行为 |
|---|---|
| 左键点空格 | 按当前「画笔」放置：单位 / 将领 / 建筑 |
| 左键点已有的 | 选中（右侧属性面板显示它的全部字段） |
| 右键点已有的 | 删除（**大本营不算「已有」**：它在阵营页里改，不允许在摆放页删 —— 免得出现「没有大本营」的关卡） |
| 滚轮 | 缩放（与 map_editor 同一套：以光标为锚点） |
| 中键拖动 / 空格拖动 | 平移 |
| 悬停 | 底部状态栏显示「格坐标 / 这一格的区划 id / 上面有什么」 |
| 「设进攻目标」模式 | 点区划 → 设成该方的进攻目标；点空格 → 设成 `point` 目标；`Esc` 退出该模式 |

> ★ 画布**只画关卡层**（摆放 + 出生点 + 目标区划高亮 + 各 AI 阵营的进攻目标箭头），
> 地形 / 区划 / 中心**从地图读出来画成背景**；要改地形就一键跳 map_editor。
> 这条分工要写在编辑器界面上（而不是只写在 README 里）。

### 6.4 与另两个编辑器的关系（含一键跳转）

| 关系 | 做法 |
|---|---|
| 地图 | **只引用** `data/maps/<id>/`；「一键打开地图编辑器」= `subprocess.Popen([python, map_editor 目录, "--map", <id>])` ⇒ **要给 `map_editor` 加一个 `--map <id>` 启动参数**（小改动；现在它开的是自己记着的上一张图） |
| 数值（兵种 / 建筑 / 科技） | **只读** `data/config.json`（拿兵种列表、将领序号、建筑类型、AI 参数默认值来填下拉框）；要改数值请开 unit_editor |
| 导出的 JSON | 与运行时**逐字段**对齐（本文第二节）；`levelfile.py` 的往返测试是这条契约的守门人 |

### 6.5 测试（沿用另两个编辑器那套「无界面 + 有界面」两套断言）

`test_model.py`（不开窗，跑得快）要覆盖：

| # | 断言组 | 盯什么 |
|---|---|---|
| 1 | 载入 / 保存 / 往返 | 读进来 → 写出去 → **逐字段一致**；LF 行尾；无 BOM；**不写多余字段** |
| 2 | 覆盖规则 | 关卡没写 `factions` → 用地图的；写了 → 逐字段覆盖（含 `base` / `allies`） |
| 3 | 校验 16 条 | 每条**各造一个坏样例**，确认它真被拦 / 被警告（**别只测「合法数据能过」**）；★ 第 7 / 8 条（可玩阵营同方、目标区划开局归属）必须各有一个反例 |
| 4 | AI 指派 | `faction` / `general` / `none` 三种取值能存能读；玩家席位也能配 AI（不拦，只有在**运行时**摘掉） |
| 5 | 进攻目标 | 四种 `kind` 的往返；缺省（不写）不落任何字段；引用不存在的区划要被拦 |
| 6 | 目标与失败条件 | `objectives` 恰好 1 项的强制；`fail_conditions` 里 `zone == 目标区划` 要被拦 |
| 7 | 向后兼容 | 老地图（没有 `exists` / `allies`）与「不做战役」的路径不受影响 |
| 8 | 坏输入 | 坏 JSON / 文件不存在 / 目录被删 → **说清楚而不是静默崩** |
| 9 | ★ 真文件不被测试改坏 | 整场测试结束后 `data/campaigns/**` 与 `data/config.json` 的字节与开始时一致（unit_editor 里那条兜底断言的同款） |

`test_app.py`（开窗，跑到最后 `withdraw()`）要覆盖：页签切换、画布放置 / 删除 / 缩放、
「设进攻目标」模式、③ 与 ④ 两处改同一个字段的一致性、导出拦截对话框、
一键跳转（**用假 subprocess**，不真起地图编辑器）、侧边栏滚动（照 `unit_editor/test_app.py`
那套「装得下就不许滚」的做法）。

### 6.6 已知取舍

1. **不做撤销 / 重做**（用户拍板；另两个编辑器也没有，数据都在 JSON 里）；
2. **不做剧本预览**（不能「在编辑器里按一下播放看 AI 会不会打过来」）—— 预览要靠进游戏跑一关；
3. 摆放**不做自动避让**（允许你在中心格上放东西，但**导出会拦**）；
4. **不做「每方一份目标」**（1.3.7：可玩阵营必须同方）；
5. ❓ 要不要一个「这一关大概多久成形 / 每波几个兵」的**估算提示**（只读展示，不参与运行）——见 9.2。

### 7.4 手玩验收清单（自动化覆盖不到的部分）

- [ ] 战役入口：主界面 →【战役】→ 看到扫描出来的战役（新建一个目录就多一项）
- [ ] 阵营选择：同一关用**不同可玩阵营**各进一次，AI 的一方确实在动（招募 / 出兵 / 巡逻）

- [ ] **波次体感**：两三波之间能看出「被打光 → 重招 → 补满 → 再来」的循环；底栏出现「边军出兵了」
- [ ] **目标面板**：进度条跟着走；守满 → 胜利播报；★ 把目标区划丢掉 → **立刻判负**（不是暂停）

- [ ] 合作：两台机器（一台走腾讯云中继）建房 → 加入 → 开局；双方各自看到**同一个世界**、
      各自的钱、**共享的视野**；一人打、另一人看得见
- [ ] 掉线：关掉客机 → 房主那一边照常能打（有提示）；关掉房主 → 客机回主界面并提示
- [ ] 编辑器：从零建一个战役（选图 → 摆 2 个玩家大本营 → 挂 1~2 个 AI 阵营并设进攻目标 →
      设目标与一条额外失败条件）→ 导出 → 进游戏**真的能按你写的那样跑**（这是编辑器唯一的验收标准）
- [ ] 一键跳转：编辑器里点「打开地图编辑器」→ 起的是**当前这一关**的地图
- [ ] 回归：地图选择条 → 按 test 直接开一局（**老路径一个字没变**）；`1/2/3`、招募、科技、升级全都照旧

## 九、风险与不做的事

### 9.1 风险（每条给对策）

| # | 风险 | 对策 |
|---|---|---|
| 1 | **房主权威的代价**：房主掉线就结束；房主的机器决定两人体验 | 合作关卡的 AI 规模按「一台机器跑得动」配；`logic/` 保持纯 `RefCounted`，以后要搬专用服务器只动 `net/` |
| 2 | **明文 `ws://` + 无鉴权**：知道房间码就能进，同房间的两个人能看到彼此的消息 | 6 位随机房间码（去掉易混字符）；房间 2 人即满；房主可踢人；**不做反作弊**（用户取舍）；以后要 `wss` 就在前面挂反向代理，客户端只改 URL |
| 3 | **快照膨胀**（新增 6 组字段 + 20Hz 全量） | 先量再优化：`run-local.ps1` 里打一行「每秒字节数」，超过阈值（比如 200KB/s）再上「只发变化」；**不提前优化** |
| 4 | ★ **AI 的「重复出兵」被数据放大**：如果编辑器允许给阵营 AI 配 `attack_repeat_sec` 很小 + 资源倍率很高，会出现「兵一波接一波不停」 | 编辑器在 ③ 的「高级」区给出**参数说明与推荐区间**（把 `config.json` 里那几个默认值当推荐值显示）；导出给一条**警告**（「这一方的出兵间隔 2s 且资源 3.0×，可能压不住」）—— ★ 是**警告不是拦截**（这是设计者的自由） |
| 5 | **两个数据源漂开**（地图 vs 关卡的大本营 / 阵营 / 摆放） | 覆盖规则**只有一处实现**（`logic/level.gd` 的合并函数），`world` 不自己判断；导出校验拦「非玩家方没有大本营」（route.md 33.5 坑①） |
| 6 | **规则与数据的组合炸**（「丢掉即负」+ 目标开局不归己方 = 第一帧就输） | 导出校验第 8 条**硬拦**；运行时再兜底一次并留 `objective_never_held` 痕迹（两道，别只靠一道） |
| 7 | **三个编辑器的重复代码** | 接受（零依赖优先，见 1.3.10）；契约钉在**导出的 JSON + 往返测试**上，不钉在共享代码上 |
| 8 | **自实现的 WebSocket 有坑**（掩码 / 分片 / 扩展长度） | `server/test_relay.py` 五条断言（4.5）；★ 中继**只跑文本帧 + 小消息**，不收二进制、不做压缩扩展 —— 把自实现的范围缩到最小 |
| 9 | **联机时序测不到** | `test_protocol.gd` / `test_session.gd`（纯 RefCounted + 假连接）+ `run-local.ps1`（真中继 + 两个进程）；**不许**出现「只在真机才跑得到的联机代码」 |
| 10 | **关卡做不出来**（编辑器能力不足，还是要手写 JSON） | M7.3 的验收就是「用编辑器从零建出 M7.2 那一关」，做不出来就不算完成 |
| 11 | **字体 / UI 度量老问题**（新面板的字被裁） | 所有新面板的几何进 `ui_layout.gd`；新面板一律配「装得下」断言；**在能跑测试的机器上**先跑 `tools/setup-font.ps1`（它现在会顺带 `--import`） |

### 9.2 ❓ 还要拍板的小项（各节里标 ❓ 的都在这里）

| # | 小项 | 本文的默认做法 |
|---|---|---|
| 1 | 编辑器要不要做「这一关大概多久成形 / 每波几个兵」的**估算提示**（纯展示） | 建议做（成本极低，能少踩「AI 半天不出兵」这种调参坑），但可以不做 |
