## 〇、一页结论

| # | 系统 | 一句话 | 主要落点 | 验收 |
|---|---|---|---|---|
| 1 | **投影** | 逻辑格**一格不改**，世界是 `y = 0` 的水平地面；「格 → 屏幕」交给一台**真实 `Camera3D`** | `view/palette.gd`（实例类，持有相机） | 无头断言：往返误差 < 0.05 px（实测 **0.0002 px**） |

**一句话**：把「格 → 屏幕」这件事整个交给**引擎的相机**（引擎负责投影、求交与相机数学），

HUD 与输入层靠一个**只满足最小接口的相机替身**原样复用 —— 于是这一轮动的是 `view/`，
`logic/` 与地图数据一个字都没动。

## 一、目标与用户口径

### 1.1 用户原话 → 可验收的条目

| 用户原话 | 拆成可验收的条目 |
|---|---|
| 「游戏内视角改成**真 3D 场景**」 | ① 游戏内的世界是一个 `Node3D` 子树；② 相机是一台真实的 `Camera3D`；③ 不再有「把 2D 画布压扁 / 转菱形 / 手算透视」这类替代品 |
| 「地面**一整块** PlaneMesh + 烘贴图」 | ④ 地面 draw call = 1，与格数无关；⑤ 网格线 / 区块归属是**贴图上的像素**，不是几何线框 |
| 「建筑做成 3D 网格」 | ⑥ 建筑是立起来的立方块（`BoxMesh`），底边贴地；⑦ 尺寸仍由 logic 的 `body_scale` 决定 |
| 「1000 单位 MultiMesh + billboard 合批」 | ⑧ 1000 个单位保持**个位数 draw call**；⑨ 立牌自动面向相机、保持直立 |
| 「相机固定俯角，只能平移与缩放」 | ⑩ 没有俯角滑杆、没有四向旋转；⑪ 平移**不改变**投影（否则就是上一版的「下滑时地块越来越大」） |
| 「`logic/` 一行不改」 | ⑫ `logic/` 的玩法代码零改动（只有既有的 `render.*` 缓存字段被读）；⑬ `data/maps/*.json` 零改动 |
| 「单位要立起来，**不投阴影**」 | ⑭ 立牌底边贴地（不浮空、不陷进地里）；⑮ 材质 `SHADING_MODE_UNSHADED`，不开任何阴影 |
| 「**用透视**，不是正交」 | ⑯ 竖直视场角 + 近大远小是真的（同一格在画面下方比上方大）；⑰ 用户已确认接受这个「同一格大小随位置变」的后果 |

### 1.2 已拍板的硬约束（★ 四条）

| # | 约束 | 为什么它必须钉死 |
|---|---|---|
| 1 | ★★ **换算只有一处**：正向（格 → 屏幕）与逆向（屏幕 → 格）必须由**同一个相机**导出 | HTML 版栽在「画用一套、鼠标换算用另一套」；上一版手算透视又栽在「拖框起点随相机漂」——两次都是同一个根因 |
| 2 | ★★ **`logic/` 里没有像素、没有相机、没有高度** | 逻辑坐标永远是「格」；一旦 logic 里出现 `cell_px` 或 `cam_height`，坐标单位混用就开始了（pitfalls 3.1） |
| 3 | ★★ **相机姿态与高度只由 config 决定**，平移只动 X / Z | 「格在屏幕上占多大」必须与「相机在哪」无关，这是「下滑时地块不变大」的**唯一**保证 |
| 4 | ★★ **`view/` 是唯一允许出现世界 / 屏幕坐标的地方** | 与 architecture.md 第五节一致；这一轮新增的六个文件全部遵守 |

### 1.3 为什么是「真 3D」，而不是继续修 2D

这一轮之前，游戏内视角被**改过三次**，三次都是「在 2D 坐标系里模拟纵深」，三次都撞在同一个天花板下。
完整脉络记在 [`docs/route.md`](docs/route.md) 第四十一节（含每次的实测数字），这里只留结论：

| 版本 | 做法 | 为什么做 | 为什么被推翻 |
|---|---|---|---|
| 第 1 版 · **仿射压扁** | 父节点 `scale = (1, 0.70)`，世界纵向压扁 | 用一个变换拿到「俯角观感」，代码改动最小（实测：**A/B 差 1.9 ms，没有性能代价**） | ⚠️ **压扁 ≠ 高度**：建筑挡人靠 Y 排序、森林没有树冠、地平线永远不会出现 |
| 第 2 版 · **菱形等距** | 每格画成一个菱形多边形（世界空间保持轴对齐） | 能画「斜着的地块」，观感更像等距 RTS | ⚠️ 几何线框会**互相穿插**（斜着的区块轮廓最明显）；逐格几何让「1 万格地图」的代价回到格数上 |
| 第 3 版 · **手算真透视** | 在 `logic/config.gd` 里推公式：`u = x / (A + y·B)` | 真的有了近大远小（参考图里墙是梯形） | ⚠️ 两个真问题：**①「向下滑动时地块越来越大」（深度项让收缩过强）② 拖框起点在相机移动时自己漂**（起点是格坐标，每次重投影都要用同一条链路） |
| 第 4 版 · **真 3D（本版）** | 世界是 `y = 0` 平面 + 真实 `Camera3D`；投影与求交**交给引擎** | 引擎里投影 / 求交 / 相机数学**只有一份实现**，不存在「算得不一样」 | —— |

★ 本文这一轮**不做**「把 3D 渲染成 2D 贴图再贴回来」那类折中：既然要真 3D，就让 3D 栈自己成体系。

⚠️ 一条必须写清楚的历史结论：**第 1 版那条「用父节点变换承载投影不会有性能代价」的实测结论仍然成立**，
只是这一版**不再需要它**了 —— 现在的投影不落在任何一个父节点上，而是引擎的相机。

## 二、架构决定与理由（本文的正文）

### 2.1 为什么投影交给引擎，而不是继续手算

`view/palette.gd` 从「静态函数集合」重写成**实例类**：`PaletteRes.create(cfg, cam: Camera3D)`，
换算只有两条路：

```gdscript
# 格 → 屏幕：引擎把世界点投到屏幕上
func to_px(logic_pos: Vector2) -> Vector2:
    return cam.unproject_position(to_world(logic_pos))

# 屏幕 → 格：从相机往地面打一条射线求交（地面是 y = 0）
func to_logic(screen_px: Vector2) -> Variant:
    var origin: Vector3 = cam.project_ray_origin(screen_px)
    var dir: Vector3 = cam.project_ray_normal(screen_px)
    if absf(dir.y) < 1e-9: return null          # 射线与地面平行 ⇒ 没有交点
    var t: float = -origin.y / dir.y
    if t <= 0.0: return null
    return world_to_logic(origin + dir * t)
```

**理由（三条，每条都对应一个具体后果）**：

1. **只有一份实现**：投影、求交、相机的近平面 / 远平面 / fov / 宽高比全在引擎里。
   手算那版要自己维护 `proj_a / proj_b / proj_zero_y / proj_offset` 四个量，改任何一处都要重新推公式；
   这一版改投影只需要**动相机**。
2. **不存在「画用一套、点用另一套」**：`to_px` 与 `to_logic` 是同一台相机的正反两面，
   所以「鼠标点在哪」与「画面上的东西在哪」天然对齐 —— 这正是本项目历史上最容易错位的地方。
3. **输入层零改动**：`view/input_controller.gd` 只依赖 `to_px` / `to_logic` / `center_on_px` 三个调用，
   换掉投影实现之后它的点选、框选、建造预览、悬停格全部照旧工作。

★ **相机不俯仰旋转的等价性**：俯角由**相机位置**表达（沿 `cam_up` 退开 `d`），
朝向由 `look_at_from_position(位置, 目标, 世界 UP)` 推出来，`rotation` 里没有任何旋转分量；
平移只沿世界 X / Z ⇒ 同一个格在任何位置看到的**屏幕尺寸完全相同**（实测逐位不变，见 4.1）。
这样「相机在同一高度」这件事不需要额外保证 —— 它是这台相机的物理事实。

⚠️ **`to_logic` 会返回 `null`**（射线与地面平行 / 交点在相机后面）。调用方**必须**处理：
`game_scene3d.center_on_screen` / `pan_screen` / `zoom_at` 三处都做了判空。
本项目的相机永远是俯视的，正常不会发生，但「不处理」的写法会在相机贴到地平线时静默移位。

### 2.2 为什么地面是「一块平面 + 一张贴图」，而不是「每格一个 Mesh」

`view/ground_view.gd` 的做法：**一个 `PlaneMesh`（全图大小）+ 一张烘出来的 `ImageTexture`**。

| 理由 | 具体后果 |
|---|---|
| **1 次 draw call** | 100×100 的图也是同一个平面；显示成本与格数**无关** |
| **网格线与区块轮廓是贴图上的像素** | 天然连续，**不可能**出现「斜着的区块线互相穿插」那种乱线 —— 那正是上一版几何线框的病 |
| **三层可以按需重烘** | 地形底色 + 区块归属一张图（归属变了才重烘）；迷雾另一张图（自己一个签名） |
| **顶点数恒定** | 每格一个 Mesh 意味着 1 万格 = 1 万个顶点块，剔除、排序、批次全跟着格数走 |

实现上必须记住的四条（都写在文件里，这里汇总）：

- **贴图 1 像素 = 1 格**在逻辑上（`u = 格 x / cols`、`v = 格 y / rows`），
  但**烘图分辨率是 8 像素/格**（`PX_PER_TILE = 8`）：1 像素/格时一格在世界里是 128 单位、
  屏幕上可能有 30~50 px ⇒ 放大 30~50 倍**必然糊**（实测如此）。8 像素/格时 27×22 的图 = 216×176，
  光栅化仍然是「几千像素」级别；上限 `MAX_TEX_PX = 4096`。
- ⚠️ **`PlaneMesh` 的 UV 是 v 向上增大的**，而贴图的 (`px`, `py`) 对应格 (`px`, `py`) 是**向下**的
  ⇒ 材质的 `uv1_scale.y = -1` + `uv1_offset.y = 1` 把 v 翻过来。写错的表现是「地图上下颠倒」。
- **地图外的格子（`exists = false`）烘成透明** ⇒ 露出来的是世界背景，而不是一圈方块。
- **迷雾是另一块平面**，抬高 1.5 个世界单位避免与地面 z-fighting（闪面）。

### 2.3 为什么迷雾**单独一层**

| 层 | 变化频率 | 重烘触发 |
|---|---|---|
| 地形 + 区块归属 | **很少**（归属变了才变） | `_zone_signature()`：区块归属列表 |
| 战争迷雾 | **每帧都在变**（单位一走视野就动） | `_fog_signature()`：抽样 18 个格的有视野位 |

如果烘进同一张贴图，那么**单位一走就要重烘整张地形图** —— 纯粹的浪费。
分开之后：地形图只在归属变化时重烘，迷雾图按自己的签名重烘。
★ 两块平面**各 1 次 draw call**，所以拆开的代价可以忽略。

三条实现口径：

- **迷雾用 alpha 混合，不用 scissor**：scissor 会把边缘切成硬齿，而迷雾的边缘本来就该柔和；
- **迷雾贴图用 NEAREST 过滤**（它是「1 像素 = 1 格」的硬数据，线性插值会糊掉边界）；
  地面贴图相反，用**线性 + 各向异性**（网格线是斜的，NEAREST 会出锯齿）；
- ⚠️ **签名是抽样**（16 个固定格 + 首尾两格），代价是「只在被抽样的格上变化」可能漏检
  （下一次别的格变化会补上）。对「大块连续变化」的迷雾足够灵敏；
  真要严格就得走 `logic/fog.gd` 的版本号（那是 logic 的事，本版不动）。

★ **重烘必须节流**（`REBAKE_INTERVAL_FRAMES = 15`，约 0.25 秒查一次）：
「变了才重烘」的函数内部虽然会短路，但**判断本身不便宜** ——
`_zone_signature()` 要遍历全部区块并拼字符串、`_fog_signature()` 要做 18 次 `tile_visible` 加拼字符串，
而这两个数据一秒钟也变不了几次。归属与迷雾的观感延迟在 0.25 秒内，玩家察觉不到。

### 2.4 为什么建筑的「视觉高度 ≠ 逻辑高度」

`view/building_view_3d.gd` 是 `MultiMeshInstance3D` + 一个单位 `BoxMesh`，
靠**逐实例的非等比缩放** `Basis().scaled(Vector3(w, h, w))` 表达每栋建筑的尺寸差异 ⇒ **1 次 draw call**。

★★ **高度是纯表现的常量**，写在 `config.json` 的 `render.building_height.<type>`，缺省走一张类型表
（城墙 0.55 格 / 箭塔 1.15 / 大本营 1.35 / 区划中心 0.35 / 其他 1.0）。
它**不参与**寻路、碰撞、攻击 —— 那些全部读 `logic/building.gd` 的 `body_scale`（一格里的**平面块**）。

| 这条边界为什么重要 | 后果 |
|---|---|
| 视觉上立起来 ≠ 逻辑上有高度 | 城墙不会因为「看起来有 0.55 格高」就挡住投射物或视线；地图数据里没有、也不该有高度字段 |
| 尺寸只有一个来源 | 方块的宽 / 深 = `格宽 × body_scale`，与 2D 版的碰撞本体**同一个数**；这里不许再写一套内缩量 |
| 摆法只有一条 | 立方体以中心为原点 ⇒ 位置抬高到 `h/2 + 0.6`，即「底边贴地 + 一点点避免 z-fighting」 |

⚠️ **代价写在脸上**：所有建筑都是方块（城墙也是方块）。这符合「先程序化占位」的口径 ——
项目现在**没有任何 3D 美术资源**，真模型（每种一个 `.glb`）是空谈。
以后有模型了，只需把 `_box` 换成对应 mesh，并给每种类型一个 MultiMesh。

### 2.5 为什么单位按「阵营 × 将领」分桶

★★ **`MultiMesh` 的所有实例共用同一个 mesh ⇒ 同一张贴图**，它**不支持逐实例贴图**。
而兵人立牌要做到「阵营色 + 将领更粗的描边」，就必须有多张图。
⇒ 做法是：**每种变体一个 `MultiMeshInstance3D`**（各自一张贴图），
变体数 = 阵营数 × 2（是否将领）。本项目阵营数是个位数 ⇒ **仍然只有个位数 draw call**，
1000 个单位全部塞在这些 MultiMesh 里，一个实例一个单位。

| 决定 | 理由 |
|---|---|
| **颜色烘进贴图**（`unit_sprite_3d.bake(阵营色, 是否将领, 描边色)`） | 将领与普通兵的**形状**不同（肩更宽 + 头顶一撮缨）⇒ 必须两张图 ⇒ 也就没必要再用逐实例染色 |
| 贴图是**程序化 SDF 光栅化**的 64×96 白剪影 + 深色描边 | 不引入任何美术资源；「并集取最小」的距离场写法在 `view/unit_icon.gd` 里已经用过一次，同一个模式 |
| 烘图**有缓存**（键 = 阵营色 + 是否将领 + 描边色） | 切换阵营 / 重开一局都不会重复光栅化 |
| 立起来 + 面向相机走材质的 `billboard_mode = BILLBOARD_ENABLED` | 引擎自带（绕 Y 轴转向相机、保持直立），**不需要自己写 shader** |
| `TRANSPARENCY_ALPHA_SCISSOR` + 阈值 0.35 | 立牌的透明区不参与混合排序；`cull_mode = CULL_DISABLED` 是因为 billboard 在极端角度下可能看到背面 |
| 立牌原点在**中心** ⇒ `w.y = 立牌高/2` | 底边贴地；贴图**最底一行几乎没有实体**（脚不顶到底边）所以不会陷进地里 —— `test_view3d` 钉着这一条 |

★ **两处实测出来的性能优化**（1000 单位时 `_process` 曾占 36.6 ms）：

1. **位置与所在批次都没变就不重写实例**：待命单位占多数时（1000 个里真正在动的可能只有几十个），
   省掉的是「每帧每单位一次 `set_instance_transform` + 一次 `to_world`」。
   实测：**1003 个实例的一帧只写 303 次**（见 4.2）。
   ⚠️ 缓存必须**逐槽位跟着实例下标走**（实例下标每帧都可能变：单位死亡 / 被迷雾挡住会让桶里的顺序变），
   所以缓存键要带下标。
2. **分桶键用预拼好的字符串**（`"阵营|是否将领"`）：每帧拼 1000 次 `"%s|%d" % [...]` 是纯浪费。

★ **战争迷雾在渲染层只是一次剔除**：看不见的敌方单位**一个实例都不占**
（判据只在 `logic/fog.gd` 的 `unit_visible`，渲染层不自作主张）。

### 2.6 为什么覆盖层（选中圈 / 标记 / 拖框）留在**屏幕空间**

`view/overlay_view_3d.gd` 是 `CanvasLayer` 上的一个 `Control`，不在 3D 子树里。

| 理由 | 具体后果 |
|---|---|
| 它们是**界面反馈**，不是世界里的东西 | 玩家要的是「我的部队在哪、点到哪」；跟着地面倾斜会难读，也容易与地形混淆 |
| 屏幕空间天然 1:1、不受透视影响 | 圈是正圆、血条是正水平条、字永远正着朝玩家 |
| 不必为每个标记建 3D 节点 | 1000 个单位全选时那就是 1000 个节点 |
| 定位走 `palette.to_px(格)` | 与「鼠标点在哪」**同一条投影链路** ⇒ 标记与鼠标天然对齐 |

⚠️ **透视下「一个格」在屏幕上不是矩形，是梯形** ⇒ 必须**逐个角投**：

```gdscript
# ✅ 四角分别投
palette.to_px(Vector2(tx, ty)) ... palette.to_px(Vector2(tx + 1, ty + 1))
# ❌ 只投中心再套一个宽高固定的矩形 —— 四角都是错的
```

同一条也约束 `palette.gd` 的返回类型：`tile_poly` / `quad_poly` / `building_poly` 返回的是
**四个点**（`PackedVector2Array`），不是 `Rect2`。★ 这是「3D 化」在本项目留下的一处**接口形状**变化。

### 2.7 为什么 HUD 能**整个复用**（本版最省的一条路）

HUD 是 `CanvasLayer` 上的 `Control`，**本来就不吃任何 Node2D / Node3D 变换** ——
它对世界的唯一依赖是「通过 `camera_rig` 知道我现在看的是哪一块」。
于是只要把 `camera_rig` 换成一个 **3D 替身**、并把 `palette` 交给小地图，
整个 HUD（编队面板 / 指令卡 / 科技树 / 详情面板 / 小地图）**一行都不用改**。

替身只需要三个成员（`game_scene3d.gd` 的 `CameraFacade`）：

```gdscript
func center_on_px(screen_px: Vector2) -> void   # 2D 版语义：把镜头中心移到屏幕像素点
func get_viewport_rect() -> Rect2               # ★ 小地图取视野四角要用它
var cam: Camera3D                               # minimap 在没有 palette 时才去读它的 zoom/position
```

★★ **为什么是「替身」而不是「让 input_controller 直接收 Camera3D」**：
那一改要动 1000 多行的输入层，而它承载着 1000+ 项断言。**接口最小化**在这里远比「结构更干净」划算。

⚠️ `get_viewport_rect()` **不能省**：`minimap.gd` 用它取视口四角，缺了视野框会**静默**变成 0×0 空矩形
（实测如此，而且不报任何错）。替身里那行 `var vp: Viewport = scene.cam.get_viewport()`
**必须显式标类型**（`scene` 是无类型引用，否则就是第 6 号类型推断坑，见 pitfalls 10.6）。

### 2.8 相机：固定俯角，只平移 + 缩放

```gdscript
# 俯角由**位置**表达：沿 cam_up 退开 d；朝向由 look_at 从「位置 + 目标 + 世界 UP」推出来
var cam_up := Vector3(0.0, sin(cfg.cam_pitch), cos(cfg.cam_pitch)).normalized()
var d: float = cfg.cam_height * zoom
cam.near = 1.0
cam.far = maxf(cam.far, d * 2.5 + 1000.0)        # ⚠️ 必须跟着距离走（默认 4000，见 pitfalls 10.1）
cam.look_at_from_position(target + cam_up * d, target, Vector3.UP)
cam.fov = rad_to_deg(cfg.cam_fov)                # ★ 必须在 look_at_from_position **之后**设
```

| 口径 | 做法 | 为什么 |
|---|---|---|
| 平移 | 屏幕位移 → 两端都反算成格，两者之差就是这一步该走的地面位移 | 手感与缩放无关；且平移**不动**高度与姿态 |
| 缩放 | `zoom ∈ [0.35, 3.0]`，以**光标下的地面点**为锚点（缩放前后它留在同一屏幕位置） | 缩放不改变俯角，只改变「一格占多大」 |
| 开场 | 对准**地图中心**，不是大本营 | 大本营在地图一角，对准它会让整张地图偏到画面一角（实测：地图只占右下 1/3，上半屏全是背景） |
| 方向键 | 按**屏幕像素位移**走 `pan_screen()` | 「上」永远对应画面上的「向上走」 |

★ **平移量分解到地面上**：`pan_screen` 把「屏幕中心」与「中心 + delta」两点都反算成格，
两者之差就是地面位移 —— 于是相机的俯角、高度、fov **一个都不变**，
「同一个格在任何位置看到的屏幕尺寸相同」这条不变量自动成立。

### 2.9 3D 场景树与每帧主循环

```
GameScene3D (Node3D)
  ├── Camera3D            ← 固定俯角：只平移 + 缩放，不俯仰旋转
  ├── GroundView3D        ← 一块 PlaneMesh（地形）+ 一块（迷雾），各 1 次 draw call
  ├── UnitView3D          ← MultiMeshInstance3D × 变体数 + billboard
  ├── BuildingView3D      ← MultiMeshInstance3D（BoxMesh）
  ├── OverlayLayer → Overlay3D   ← CanvasLayer：选中圈 / 标记 / 拖框（屏幕空间）
  ├── InputController     ← **复用 2D 那版**（只依赖 palette 的 to_px / to_logic 与相机替身）
  └── Hud (CanvasLayer)   ← **复用 2D 那版**（一行未改）
```

`_process` 的六步（顺序本身就是契约）：

1. **输入**：轮询鼠标（只有 `input_controller` 允许读鼠标）；
2. **逻辑**：`logic_dt = minf(dt, cfg.sim_max_dt)` 夹住（帧一慢 dt 就大 → 这一帧活更多 = 死亡螺旋），
   然后 `world.tick(logic_dt)` + 消费事件；
3. **视图**：`units.sync()` / `buildings.sync()`（位置会变）；
4. **覆盖层**：把纯本地 UI 状态塞给它，它只画；
5. **地面 / 迷雾重烘**：每 15 帧查一次签名（见 2.3）；
6. **相机**：方向键平移 + 边缘滚屏 + 滚轮缩放。

★ 这与 2D 版 `game_scene.gd` 是同一条思路：**world 是权威，视图只读它**，这里不写任何玩法规则。

### 3.1 为什么还要留一份 `view/palette2d.gd`

`view/palette.gd` 改成实例类之后，仓库里那**一整套 2D 遗留栈**
（`game_scene.gd` / `camera_rig.gd` / `terrain_view.gd` / `zone_view.gd` / `fog_view.gd` /
`overlay.gd` / `unit_view.gd` / `building_view.gd` / `minimap.gd`）调用的是**老 palette 的静态签名**
（`PaletteRes.to_px(pos, cfg)` 这种）⇒ 那**整个文件解析失败**，
而 Parse Error 会**连带**把依赖它的脚本一起变成 `Compilation failed`（pitfalls 10.5）。

★★ **方向（很关键，别走错）**：**不要**让 2D 遗留栈去适配 3D 语义。
正确做法是 —— 遗留栈继续用它自己那套 2D 换算，只是把出处从「已经改成实例类的 palette」
搬到 `palette2d.gd`，**一份实现、一处存放**。理由：

- 遗留栈本来就是 2D 的（格 → 像素就是 `pos * cfg.cell_px`，没有透视）；
  把它接到 3D 相机上等于让一套死代码依赖另一条活链路，两边都会更难改；
- 这些文件只在**无头测试**里被引用（一整套集成测试跑的是 `view/main.tscn` → `viewport/game_scene.gd`）；
- 「换算只有一处」这条铁律仍然成立：本该在 `palette.gd` 里的 2D 口径，
  现在完整地落在 `palette2d.gd`，而不是散进九个文件的私有函数各写一份。

⚠️ `palette2d.gd` **只服务遗留 2D 栈**。新写的 3D 代码一律不许 `preload` 它 ——
要用投影请走 `view/palette.gd` 的实例 API。

## 四、实测数字（全部是这一轮真跑出来的，不是推算）

### 4.1 投影与相机不变量

| 项 | 实测 | 怎么量的 | 判据 |
|---|---|---|---|
| 投影往返误差（屏幕 → 格 → 屏幕） | **0.0002 px** | 5 个采样点（中心 / 四角附近），`_tmp_3d_probe.gd` 与 `test_view3d._test_projection_roundtrip` | < 0.05 px |
| 相机高度平移后 | **逐位不变** | 相机沿地面挪 500 / -300 单位，比 `position.y` | 相等（`is_equal_approx`） |
| 同一格的屏幕宽度 | y=2 行 → y=20 行 = **1.28 倍** | 量同一列各行的「一格宽」 | ① 近处必须更大（透视应有）；② **收缩比 < 2.0**（大了就是上一版那个 bug） |
| 相机基向量 | 单位正交、`up.y > 0` | 平移前后逐位比对 | 姿态不随平移改变 |
| 屏幕四角 | 全部能打到地面（不是 `null`） | `to_logic(Vector2(0,0))` | 俯视相机不该有地平线之上的射线 |

★ **1.28 倍是透视的必然结果，已与用户确认接受**：同一个格在画面下方（离相机近）比上方大。
它不是 bug —— 上一版被报「下滑时地块越来越大」说的是**同一格在相机移动后变大**，两件事完全不同，
`test_view3d` 用两条独立断言把它们分开钉。

### 4.2 1000 个单位的渲染账

| 项 | 实测 |
|---|---|
| draw call / 帧 | **11** |
| 节点数 | **23** |
| 显存 | **78.5 MB** |
| 单位实例数 | 1003（含世界里原有的单位） |
| 单位的**批次数** | **2** |
| 建筑的批次数 | 个位数（按「阵营 / 类型」分桶） |
| 每帧真的写了几次实例变换 | **303**（脏检查生效：其余实例位置没变，跳过 `set_instance_transform`） |
| 地面 / 迷雾重烘次数 | 各自很小（节流 + 签名生效；不节流时这两个数会跟着帧数涨） |

★ **合批的判据是可算的**，不要靠感觉：`draw call ≈ 地面 1 + 迷雾 1 + 单位批次数 + 建筑批次数`。
超出很多就说明有东西在偷偷逐实例绘制。
⚠️ 这也解释了「`DAEEM_HIDE` 藏掉地面 + 迷雾只省 0.6~0.9 ms」—— 那两层本来就只有 2 次 draw call。

### 4.3 帧时间是「逻辑」的线性函数（本轮最重要的结论）

`tests/bench_fps_3d.gd`，100×100 图、关垂直同步、单位聚成一团：

| 单位数 | 帧时间 |
|---|---|
| 1 | **4.01 ms** |
| 250 | **32.82 ms** |
| 1000 | **82.35 ms** |

拟合：**≈ 4 ms + 0.078 ms × 单位数**（两个端点的斜率一致 ⇒ 瓶颈是**每单位成本**，
而不是某个固定开销）。
⚠️ 250 那一点比这条直线高约 9 ms —— 单点计时有噪声（先看 machine drift，见 4.5），
下判断请以两端点为准。

**`DAEEM_HIDE` 的图层二分**（这是定位固定渲染开销的唯一手段）：

| 藏掉的层 | 省下的时间 |
|---|---|
| `ground,fog` | **0.6 ~ 0.9 ms** |
| `units` / `buildings` | 同量级（合批之后它们本来就只有几次 draw call） |

★★ **结论**：**渲染不是瓶颈**。82 ms 里有 80 ms 左右在 `_process`（逻辑 + 视图同步），
而视图同步已经被 4.2 的脏检查压到很小 ⇒ **瓶颈在 `logic/` 的每单位成本**，
而这一轮 `logic/` 是硬约束「一行不改」。
⇒ 想上 60 fps 必须去降「每单位的逐帧成本」，那是**下一轮**的活（见第六节）。

## 五、断言与验收

### 5.1 无头断言（`tests/test_view3d.gd`）

★★ 这个文件的理由：3D 栈里最容易**静默失败**的三类东西都不报错、也不改任何逻辑状态 ——
① `MultiMesh` 的实例数写错（写成 0 就什么都不画，画面只剩地面）；
② 分桶键写错（每种变体各建一批 ⇒ 合批失效，性能悄悄退化）；
③ 相机不变量被破坏（俯角 / 高度被平移带动 ⇒ 「下滑时地块变大」那类观感 bug）。
所以全部用**可数的痕迹**与**可复算的不变量**来钉，而不是「跑一遍没炸就算过」。

| 组 | 钉什么 |
|---|---|
| 一、兵人贴图 | 烘得出来；普通兵有实质剪影（不透明像素 > 100）；**将领更大**；阵营色真的烘进去了（取样点 `r > g + 0.2`）；同一组参数命中缓存（拿到同一张）；★ **贴图最底一行几乎没有实体**（⇒ 抬到贴地时不会陷进去） |
| 二、投影往返 | `to_logic` / `to_px` 闭合（最大误差 < 0.05 px）；屏幕左上角也能打到地面 |
| 三、相机不变量 | 近处格更大（1.0 < 收缩比 < 2.0）；平移不动高度；相机基是单位正交基且 `up.y > 0`；★ 平移前后同一格的**像素宽逐位不变** |
| 四、单位 MultiMesh | 实例数 = 可见单位数（不等于 0）；批次数 ≤ 阵营数 × 2；累计创建的批次数也没超；迷雾剔除的诊断计数 |
| 五、建筑 MultiMesh | 建筑真的画了出去；批次数 ≤ 建筑数；★ 方块宽 = 格宽 × `body_scale`（logic 的权威值）；底边贴地 |
| 六、地面贴图 | 烘的格数 = 全图格数；贴图宽 = 格数 × `PX_PER_TILE`；分辨率**高于** 1 像素/格；区块归属变了会重烘；迷雾层节点存在 |
| 七、HUD 与小地图 | HUD 挂进了 3D 场景；小地图**拿到了 3D 投影助手**（否则视野框停在错位置）；视野框有面积且与地图有交集；★ 相机挪走之后**视野框跟着挪** |

⚠️ 挂节点必须在 `await process_frame` **之后**（`_initialize()` 阶段 `root.add_child()` 会**静默失效**，
pitfalls 1.2）；相机更是必须**先进树**才有视口（pitfalls 10.3）。

### 5.2 实机量尺（`tests/bench_fps_3d.gd`）

- **不用 `--headless`**（要真的渲染）；环境变量：`DAEEM_FPS_UNITS`（默认 1000）、
  `DAEEM_FPS_FRAMES`（默认 180）、`DAEEM_HIDE`（逗号分隔：`ground` / `fog` / `units` / `buildings`）；
- **分项计时**：`logic` / `units` / `buildings` / `ground` / `rest` 各记一次（`Time.get_ticks_usec()`）；
- 读法顺序见 4.5；`DAEEM_HIDE` 的读法见 4.3。

★ 为什么另起一份而不是改 `bench_fps.gd`：老的基准加载 **2D 遗留栈**，
它在 100×100 图 + 1000 单位下打出的成绩是 2D 栈的真实记录（20096 draw call / 2567 MB 显存），
**不该被改动**，两份可以对着看。

### 5.3 手玩验收清单

1. **位置对齐**：进游戏第一眼，地面、区块归属、建筑、单位、移动标记**都在它们该在的地方**；
2. **输入对齐**：鼠标悬停任意一格 → 建造预览框正好套住那一格（透视下它是**梯形**，不是矩形）；
3. **单位可读**：兵人立起来、底边贴地、面向相机；将领有缨、描边更粗；
4. **近大远小**：滚轮到最远 / 最近各看一遍，画面下方的格比上方大，但**同一格不随相机平移改变大小**；
5. **迷雾**：没视野的区域整片变暗，且**边界随地面一起变形**（不是一张正方形灰布）；
6. **HUD 零影响**：底栏 / 命令卡 / 悬停面板 / 页签 / 小地图控件本身**与改造前完全一样**，
   小地图的视野框跟着主视图走。
